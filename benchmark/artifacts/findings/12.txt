## Finding 1: Authentication Bypass via Bash Glob Pattern Injection

**Finding ID:** `APPSEC-1a2f7e9c3d`
**File:** `validate_password.sh`
**Lines:** 5–7
**CWE:** CWE-155 — Improper Neutralization of Wildcards or Special Elements Used in an OS Command ("Wildcard Injection")
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```bash
if [[ $SECURE_PASSWORD == $1 ]]; then
    echo "true"
```

### Description
In bash `[[ ]]` conditionals, the **right-hand side** of `==` is treated as a glob pattern when unquoted. Because `$1` is the attacker-controlled `password` argument and is not quoted, any glob metacharacter the attacker sends is expanded as a pattern against `$SECURE_PASSWORD`. Sending `*` as the password causes `[[ "SuperAdmin@123" == * ]]` to evaluate true, bypassing authentication entirely. The attacker need not know any part of the real password — a single `*` character grants access.

### Prioritization
This is the highest-priority finding. It is a zero-precondition authentication bypass on the admin endpoint: no credentials, no prior session, no enumeration needed. Any unauthenticated HTTP client can exploit it immediately.

**Counterfactual invalidation:** Quoting `"$1"` forces bash to treat the right-hand side as a literal string, making glob expansion impossible and closing the bypass.

### Exploitability Notes
- **Exploit Preconditions:** Network access to `POST /admin`. No authentication, enumeration, or prior knowledge of the password required.
- **Uncertainty Boundary:** The Flask app calls the script with `shell=False` so there is no OS-level command injection from Python. Exploitation is limited to pattern-match bypass within the script itself, not arbitrary command execution.

**Proof-of-concept request:**
```http
POST /admin HTTP/1.1
Content-Type: application/json

{"password": "*"}
```
Expected response: `{"message": "Login successful"}` — 200 OK.

### Remediation
Quote `$1` on the right-hand side to suppress glob expansion:

```bash
#!/bin/bash

SECURE_PASSWORD="SuperAdmin@123"

if [[ $SECURE_PASSWORD == "$1" ]]; then   # <-- quote $1
    echo "true"
else
    echo "false"
fi
```
Quoting the variable prevents bash from interpreting its value as a pattern; the comparison becomes a strict literal string equality check.

- [CWE-155: Improper Neutralization of Wildcards](https://cwe.mitre.org/data/definitions/155.html)
- [Bash manual — Pattern Matching in `[[ ]]`](https://www.gnu.org/software/bash/manual/bash.html#index-_005b_005b)

## Finding 2: Hardcoded Credential in Shell Script

**Finding ID:** `APPSEC-4b8d2e1f7a`
**File:** `validate_password.sh`
**Lines:** 3
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```bash
SECURE_PASSWORD="SuperAdmin@123"
```

### Description
The admin password is stored as plaintext in a shell script committed to the repository. Any developer, CI/CD system, or process with read access to the filesystem or version control history can trivially recover the credential. The password cannot be rotated without modifying and redeploying the script, and rotation history remains visible in git history. Combined with Finding 1 above, an attacker can bypass authentication without needing this value — but it also enables direct login if the glob bypass were patched.

### Prioritization
P1, second after Finding 1. Even after patching the glob bypass, this credential remains statically exposed. Must be addressed alongside Finding 1.

**Counterfactual invalidation:** Moving the password to a runtime-injected environment variable (e.g., read via `$ADMIN_PASSWORD` set in the execution environment, never stored in the file) would close this finding.

### Exploitability Notes
- **Exploit Preconditions:** Read access to the script file (developer, CI runner, container image layer inspection, directory listing).
- **Uncertainty Boundary:** Impact escalates significantly if this password is reused on other systems.

### Remediation
Inject the secret at runtime via environment variable — never embed it in source:

```bash
#!/bin/bash

# ADMIN_PASSWORD must be set in the calling environment (e.g., via Docker secret, systemd EnvironmentFile, or Vault agent)
if [[ -z "$ADMIN_PASSWORD" ]]; then
    echo "false"
    exit 1
fi

if [[ "$ADMIN_PASSWORD" == "$1" ]]; then
    echo "true"
else
    echo "false"
fi
```

In `main.py`, pass the environment variable through when calling the subprocess — or better, move the comparison entirely out of bash into Python using a proper secrets management library:

```python
import os, hmac

stored = os.environ.get("ADMIN_PASSWORD", "")
if hmac.compare_digest(password.encode(), stored.encode()):
    return jsonify({"message": "Login successful"}), 200
```

This also eliminates the need for the external subprocess call entirely.

- [OWASP: Hard-coded Credentials](https://owasp.org/www-community/vulnerabilities/Use_of_hard-coded_password)

## Finding 3: Sensitive Information Disclosure via Exception Messages

**Finding ID:** `APPSEC-9c3e5a1b2d`
**File:** `main.py`
**Lines:** 22
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```python
except Exception as e:
    return jsonify({"error": str(e)}), 500
```

### Description
Any unhandled exception — including `TypeError`, `FileNotFoundError` (if `validate_password.sh` is missing), `PermissionError`, or subprocess-related errors — is converted to a string and returned verbatim in the HTTP response body. Python exception messages routinely include filesystem paths, internal class names, module names, and OS-level detail that helps an attacker enumerate the server environment or understand deployment structure.

### Prioritization
P3 — lower priority than Findings 1 and 2. Exploitability is indirect (aids reconnaissance) rather than directly granting access. Address after the authentication issues are resolved.

**Counterfactual invalidation:** Returning a fixed generic message (`"Internal server error"`) and logging the real exception server-side would close this finding.

### Exploitability Notes
- **Exploit Preconditions:** The attacker must trigger a condition that raises an exception (e.g., sending a non-string `password` type, or a value that causes subprocess failure).
- **Uncertainty Boundary:** Actual information value depends on what exceptions are reachable; at minimum, subprocess-related errors will include system paths.

### Remediation
```python
import logging

logger = logging.getLogger(__name__)

except Exception as e:
    logger.exception("Unexpected error in admin_login")
    return jsonify({"error": "Internal server error"}), 500
```

Log the full exception server-side for debugging; return only a generic message to the client.

### References
- [CWE-209: Error Message Containing Sensitive Information](https://cwe.mitre.org/data/definitions/209.html)
- [OWASP: Improper Error Handling](https://owasp.org/www-community/Improper_Error_Handling)
