## Finding 1: Bash Glob Pattern Authentication Bypass

**File:** `validate_password.sh`  
**Lines:** 5–5  
**CWE:** CWE-289 — Authentication Bypass by Alternate Name  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** CRITICAL  
**Confidence:** HIGH

### Vulnerable Code
```bash
if [[ $SECURE_PASSWORD == $1 ]]; then
```

### Description
In bash's `[[ ]]` compound command, the right-hand operand of `==` is treated as a **glob pattern** when it is unquoted. Since `$1` holds the attacker-supplied password and is unquoted here, any glob pattern passed as the password will be matched against the hardcoded string `SuperAdmin@123`. Sending the password `*` matches every string and unconditionally returns `"true"`, granting the attacker a successful login response without knowing the real credential. More targeted patterns like `SuperAdmin*` or `S*` also match, enabling low-noise attacks.

### Prioritization
Highest priority. This is a zero-precondition remote authentication bypass: a single unauthenticated HTTP POST with `{"password": "*"}` achieves full admin login. Remediation is a one-character fix but the impact is complete.

### Exploitability Notes
- **Exploit Preconditions:** The `/admin` endpoint is network-reachable. No prior account or session required.
- **Uncertainty Boundary:** None — the glob expansion behavior of unquoted `[[ == ]]` RHS is specified and stable across all bash versions in use.
- **Attacker input shape:** `POST /admin` with body `{"password": "*"}` or `{"password": "SuperAdmin*"}`
- **Counterfactual:** Quoting `"$1"` in the comparison (see remediation) makes the bash comparison treat the input as a literal string, eliminating glob expansion entirely.

### Remediation
Quote the right-hand operand to force literal string comparison:

```bash
#!/bin/bash

SECURE_PASSWORD="SuperAdmin@123"

if [[ $SECURE_PASSWORD == "$1" ]]; then
    echo "true"
else
    echo "false"
fi
```

Quoting `"$1"` disables glob pattern interpretation on that side of `==`, so `*` is compared as the three-character string `*`, not as a wildcard. Longer-term, replace the entire shell-based auth with a proper password hashing comparison in Python (see Finding 2).

### References
- [Bash Manual — Conditional Constructs](https://www.gnu.org/software/bash/manual/bash.html#Conditional-Constructs): "Any part of the pattern may be quoted to force the quoted portion to be matched as a string."
- [CWE-289: Authentication Bypass by Alternate Name](https://cwe.mitre.org/data/definitions/289.html)

## Finding 2: Hardcoded Admin Password in Source Code

**File:** `validate_password.sh`  
**Lines:** 3–3  
**CWE:** CWE-798 — Use of Hard-coded Credentials  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```bash
SECURE_PASSWORD="SuperAdmin@123"
```

### Description
The admin password is stored as a plaintext literal in a committed source file. Anyone with read access to the repository, a deployment artifact, a container image, or the server filesystem obtains the credential immediately. The password is also not hashed — it is compared directly against the user input — so there is no hashing layer that would slow an attacker who reads the file. Additionally, the password cannot be rotated without a code change and redeployment.

### Prioritization
P1 alongside Finding 1. Both are independently exploitable. Finding 1 makes the password itself unnecessary for an attacker, but Finding 2 exposes the credential to any reader of source, logs, or artifacts, and survives a fix to Finding 1 if not also remediated.

### Exploitability Notes
- **Exploit Preconditions:** Read access to the source repository, CI logs, container layer, or filesystem.
- **Uncertainty Boundary:** If the repository is fully private with no external access, the exposed surface is smaller — but insider threat and supply-chain risk remain.
- **Counterfactual:** Moving the credential to an environment variable and hashing it before comparison removes the hardcoded secret from source entirely.

### Remediation
Store credentials outside source code and compare using a proper password hash:

```python
# main.py — read secret from environment, compare with bcrypt
import os, bcrypt
from flask import Flask, request, jsonify

app = Flask(__name__)

# Set at deploy time: ADMIN_PASSWORD_HASH=$(python -c "import bcrypt; print(bcrypt.hashpw(b'<password>', bcrypt.gensalt(12)).decode())")
ADMIN_PASSWORD_HASH = os.environ["ADMIN_PASSWORD_HASH"].encode()

@app.route('/admin', methods=['POST'])
def admin_login():
    data = request.get_json(silent=True) or {}
    password = data.get('password', '')
    if not password:
        return jsonify({"error": "Password is required"}), 400
    if bcrypt.checkpw(password.encode(), ADMIN_PASSWORD_HASH):
        return jsonify({"message": "Login successful"}), 200
    return jsonify({"error": "Access Denied"}), 403
```

This eliminates `validate_password.sh` entirely, stores no plaintext credential in source, and uses bcrypt (cost ≥ 12) which is slow enough to resist offline attacks if the hash is ever leaked. Add `bcrypt` to `Pipfile`.

### References
- [OWASP: Hardcoded Passwords](https://owasp.org/www-community/vulnerabilities/Use_of_hard-coded_password)
- [CWE-798: Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html)

## Finding 3: Exception Details Leaked to Client

**File:** `main.py`  
**Lines:** 25–26  
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P3  
**Severity:** LOW  
**Confidence:** HIGH

### Vulnerable Code
```python
    except Exception as e:
        return jsonify({"error": str(e)}), 500
```

### Description
Any unhandled exception is serialized via `str(e)` and returned to the HTTP client. Python exceptions commonly include internal file paths (e.g., from `FileNotFoundError`), missing environment variable names, subprocess errors, or Flask internals. An attacker who can trigger a 500 response (for example by sending malformed JSON or a non-existent script path) receives server-side path and configuration details that assist in further attacks.

### Prioritization
P3 — low exploitability on its own. Remediate after Findings 1 and 2.

### Exploitability Notes
- **Exploit Preconditions:** Ability to send a request that triggers an exception (e.g., malformed `Content-Type`, or `validate_password.sh` not found).
- **Uncertainty Boundary:** Actual leakage content depends on which exception is triggered; some exceptions carry negligible detail.
- **Attacker input shape:** `POST /admin` with body `not-json` or missing `Content-Type: application/json` header.

### Remediation
Return a generic error message; log the full exception server-side only:

```python
import logging
logger = logging.getLogger(__name__)

    except Exception as e:
        logger.exception("Unexpected error in admin_login")
        return jsonify({"error": "Internal server error"}), 500
```

### References
- [CWE-209: Error Message Information Exposure](https://cwe.mitre.org/data/definitions/209.html)
