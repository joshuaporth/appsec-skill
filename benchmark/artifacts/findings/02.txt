## Finding 1: Server-Side Request Forgery (SSRF)

**Finding ID:** `APPSEC-a3f9c1e4b8`
**File:** `main.js`
**Lines:** 19–31
**CWE:** CWE-918 — Server-Side Request Forgery (SSRF)
**OWASP Category:** A10:2021 – Server-Side Request Forgery
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.get('/fetch-data', async (req, res) => {
    const url = req.query.url;
    console.log(`Received request for /fetch-data with URL: ${url}`);
    
    try {
        const response = await axios.get(url);
        res.send(response.data);
```

### Description
The `url` query parameter is read directly from the attacker-controlled request at line 20 and passed without any validation, allowlisting, or blocklisting to `axios.get()` at line 24. The full response body is then returned to the caller at line 25 (`res.send(response.data)`), making this a **non-blind (full-read) SSRF**. An attacker can instruct the server to issue HTTP requests to any reachable target: internal services on the container network, the Docker host, or — in cloud-hosted deployments — the instance metadata endpoint (`http://169.254.169.254/latest/meta-data/iam/security-credentials/`). The full response is exfiltrated to the attacker in every case. No authentication is required to reach this endpoint.

### Prioritization
This is the highest-priority finding. Full-read SSRF with no preconditions is immediately exploitable. In a cloud environment (AWS/GCP/Azure), a single request can retrieve IAM credentials, leading to full account compromise. Even outside cloud, the attacker gains a read proxy into the private Docker network.

### Exploitability Notes
- **Exploit Preconditions:** None. The endpoint is unauthenticated and reachable over the network. Any attacker who can send an HTTP GET request can exploit this.
- **Uncertainty Boundary:** Impact on internal network depends on what other services are co-hosted. Cloud metadata endpoint exploitation depends on the deployment environment (cloud vs. bare-metal). Axios does not follow `file://` URLs by default, so local file read via `file:///etc/passwd` is unlikely but not ruled out without confirming the axios version's redirect handling.

### Remediation
Implement a strict domain/scheme allowlist before passing any URL to axios. Never permit user-supplied URLs to be fetched server-side without explicit, narrow approval:

```javascript
const { URL } = require('url');

// Strict allowlist — only permit requests to known safe external hosts
const ALLOWED_HOSTS = new Set(['api.example.com', 'data.example.com']);

app.get('/fetch-data', async (req, res) => {
    const rawUrl = req.query.url;

    let parsed;
    try {
        parsed = new URL(rawUrl);
    } catch {
        return res.status(400).send('Invalid URL');
    }

    // Reject non-HTTP(S) schemes (blocks file://, ftp://, gopher://, etc.)
    if (parsed.protocol !== 'https:' && parsed.protocol !== 'http:') {
        return res.status(400).send('Unsupported scheme');
    }

    // Block all hosts except the explicit allowlist
    if (!ALLOWED_HOSTS.has(parsed.hostname)) {
        return res.status(403).send('Host not permitted');
    }

    try {
        const response = await axios.get(parsed.href);
        res.send(response.data);
    } catch (error) {
        res.status(500).send('Error fetching data');
    }
});
```

If a dynamic allowlist is not feasible for the use case, consider whether the application genuinely needs a server-side fetch proxy at all — if the frontend can fetch the data directly, remove this endpoint entirely.

**Counterfactual invalidation:** Restricting `axios.get()` to a fixed set of pre-configured URLs (not user-supplied) would eliminate this finding entirely.

- [CWE-918: Server-Side Request Forgery](https://cwe.mitre.org/data/definitions/918.html)

## Finding 2: Sensitive Data in Server Logs (Full URL Logged)

**Finding ID:** `APPSEC-b72d3a9c15`
**File:** `main.js`
**Lines:** 21, 26, 28
**CWE:** CWE-532 — Insertion of Sensitive Information into Log File
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
console.log(`Received request for /fetch-data with URL: ${url}`);
// ...
console.log(`Data fetched and sent for URL: ${url}`);
// ...
console.error(`Error fetching data from URL: ${url}`, error);
```

### Description
The raw user-supplied `url` value is interpolated into log messages at lines 21, 26, and 28. URLs frequently carry credentials in query parameters (e.g., `?token=Bearer-abc123`, `?api_key=secret`). Logging these values exposes secrets to anyone with access to log storage or aggregation systems, which often have weaker access controls than the application itself. This is compounded by the SSRF vulnerability — an attacker who can direct the server to fetch an internal URL with a token in the query string will see that token appear in logs.

### Prioritization
Lower priority than the SSRF (Finding 1). Remediate after addressing the SSRF. The risk here is conditional on URLs containing sensitive query parameters, which is common in API-based workflows.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must have read access to application logs, or an internal user with log access must be malicious/compromised.
- **Uncertainty Boundary:** Impact depends on whether callers pass credentials in URL query parameters and whether log infrastructure is adequately protected.

### Remediation
Log only the host/path, stripping query parameters and fragments before writing to the log:

```javascript
const { URL } = require('url');

function safeLogUrl(rawUrl) {
    try {
        const parsed = new URL(rawUrl);
        return `${parsed.protocol}//${parsed.host}${parsed.pathname}`;
    } catch {
        return '[invalid URL]';
    }
}

// Then replace all console.log/error calls:
console.log(`Received request for /fetch-data with URL: ${safeLogUrl(url)}`);
```

### References
- [CWE-532: Insertion of Sensitive Information into Log File](https://cwe.mitre.org/data/definitions/532.html)

## Finding 3: Missing HTTP Security Headers (`helmet` not used)

**Finding ID:** `APPSEC-c1e8d4f230`
**File:** `main.js`
**Lines:** 1–5
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** INFO
**Confidence:** HIGH

### Vulnerable Code
```javascript
const express = require('express');
const axios = require('axios');

const app = express();
```

### Description
The Express application does not include `helmet` middleware. As a result, responses omit security headers including `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security`, and `Content-Security-Policy`. While the current endpoints return JSON or proxied binary content (limiting immediate XSS risk), the absence of these headers is a defense-in-depth failure that becomes meaningful if the application grows to serve HTML.

### Prioritization
Lowest priority — no immediate exploitable impact given the current endpoint behavior. Address after the two higher-priority findings.

### Exploitability Notes
- **Exploit Preconditions:** Requires additional vulnerabilities (e.g., XSS introduction) for these missing headers to become exploitable.
- **Uncertainty Boundary:** Impact is entirely contingent on future feature additions that render HTML.

### Remediation
```javascript
const helmet = require('helmet');
// npm install helmet

const app = express();
app.use(helmet()); // Sets 11 security headers by default
```

### References
- [helmet.js](https://helmetjs.github.io/)
- [OWASP Security Headers](https://owasp.org/www-project-secure-headers/)

## Finding 4: Container Runs as Root

**Finding ID:** `APPSEC-d5a2b6f891`
**File:** `Dockerfile`
**Lines:** 1–21
**CWE:** CWE-250 — Execution with Unnecessary Privileges
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```dockerfile
FROM node:18
WORKDIR /usr/src/app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "main.js"]
```

### Description
The Dockerfile contains no `USER` directive, so the Node.js process runs as root inside the container. If an attacker achieves code execution through SSRF chaining or a future vulnerability, they will have root privileges within the container, substantially increasing the blast radius of any breakout or lateral movement attempt.

### Prioritization
Low severity in isolation but materially worsens the impact of the SSRF finding (Finding 1). The SSRF may be exploitable to read container-internal files or trigger further RCE in some scenarios; root execution removes a significant containment layer.

### Exploitability Notes
- **Exploit Preconditions:** Requires a separate code execution vector to matter.
- **Uncertainty Boundary:** Actual containment depends on Docker daemon configuration and kernel capabilities granted to the container.

### Remediation
```dockerfile
FROM node:18

WORKDIR /usr/src/app

COPY package*.json ./
RUN npm install

COPY . .

# Drop to a non-root user
RUN chown -R node:node /usr/src/app
USER node

EXPOSE 3000
CMD ["node", "main.js"]
```

### References
- [Docker Security Best Practices — Non-root](https://docs.docker.com/develop/security-best-practices/)
- [CWE-250](https://cwe.mitre.org/data/definitions/250.html)
