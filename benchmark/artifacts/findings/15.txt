## Finding 1: HTTP Response Splitting / CRLF Header Injection

**Finding ID:** `APPSEC-a3f7c29b1e`
**File:** `nginx.conf`
**Lines:** 14–16
**CWE:** CWE-113 — Improper Neutralization of CRLF Sequences in HTTP Headers
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```nginx
location /payment {
    return 302 http://payment-api$uri;
}
```

### Description
The `$uri` variable in Nginx stores the normalized request URI, which includes percent-decoded characters from the attacker-supplied path. Because `$uri` is interpolated directly into the `Location` response header via `return 302`, an attacker who sends `%0d%0a` (CR+LF) in the path component can inject a second line into the HTTP response — splitting the response and inserting arbitrary headers. For example, a request to `/payment/%0d%0aX-Injected:%20evil` could produce a response containing a forged `X-Injected` header, and chaining two `Location:` values can additionally function as an open redirect. The exploitability is version-dependent: Nginx ≥ ~1.19.3 rejects requests with bare CRLF in paths with a 400, but because `docker-compose.yml` uses the unpinned `image: nginx`, an older or pinned-to-older-cache image remains vulnerable; the pattern is dangerous by construction regardless.

### Prioritization
This is the highest-severity finding in the codebase. The attack surface is the external HTTP port 80, requires no authentication, and the pattern is a well-known anti-pattern with a direct, short exploit path. All other findings rank below this one by exploitability and impact.

### Exploitability Notes
- **Exploit Preconditions:** Nginx version must decode `%0d%0a` in path before writing the Location header (pre-1.19.3 behavior, or non-latest image tag). Attacker needs HTTP access to port 80.
- **Uncertainty Boundary:** Exact exploitability depends on the Nginx version pulled by `image: nginx`. Modern `latest` (1.25+) likely rejects CRLF in paths. An older cached image or pinned-old image restores full exploitability.

**Counterfactual:** Replacing `return 302 http://payment-api$uri;` with a fixed redirect target or strictly mapped path eliminates this finding entirely.

**Attacker input shape:** `GET /payment/%0d%0aLocation:%20http://evil.com HTTP/1.1`

### Remediation
Use a fixed path or an allowlisted mapping rather than interpolating `$uri` directly. If the intent is to forward the payment path suffix to an internal service, use `proxy_pass` instead of `return`:

```nginx
# Option A — Fixed redirect (if path suffix is not needed downstream)
location /payment {
    return 302 http://payment-api/payment;
}

# Option B — Proxy to internal service, no header injection possible
location /payment {
    proxy_pass http://payment-api;
}

# Option C — If you must redirect with path, use $request_uri only after
# validating it matches a strict allowlist, and prefer proxy_pass
location ~* ^/payment(/.*)?$ {
    proxy_pass http://payment-api$1;
}
```

The root fix: never interpolate `$uri`, `$request_uri`, or any request-derived variable directly into a `return` directive or `add_header` value without a sanitization or structural constraint that prevents CRLF from reaching the emitted headers.

- https://owasp.org/www-community/attacks/HTTP_Response_Splitting
- https://nginx.org/en/docs/http/ngx_http_core_module.html#var_uri

## Finding 2: Flask Application Directly Exposed, Bypassing Nginx

**Finding ID:** `APPSEC-b8d42f1c7a`
**File:** `docker-compose.yml`
**Lines:** 6
**CWE:** CWE-284 — Improper Access Control
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```yaml
flask-app:
  build: .
  ports:
    - "5000:5000"
```

### Description
The `ports: "5000:5000"` mapping binds Flask directly to `0.0.0.0:5000` on the Docker host, making the application accessible on port 5000 to any host with network access — completely bypassing Nginx. Because Nginx enforces the `/payment` redirect logic and is the intended sole entry point, any controls or routing logic implemented at the Nginx layer (including future auth middleware, IP filtering, or route rewrites) are silently circumvented by direct port-5000 access. The current Flask app only returns `"Hello World!"` so practical impact is low today, but the architectural gap is a persistent risk for all future routes.

### Prioritization
Lower priority than Finding 1 because the current Flask app has no sensitive routes. However, this is an architectural issue — any future route added to Flask inherits this exposure by default.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the Docker host on port 5000.
- **Uncertainty Boundary:** If the host is behind a firewall that blocks port 5000 externally, practical impact is reduced to internal/lateral movement only.

**Counterfactual:** Removing the `ports` mapping (or changing it to `127.0.0.1:5000:5000`) removes direct external access to Flask.

### Remediation
Remove the external port binding so Flask is only reachable through Nginx on the Docker bridge network:

```yaml
# Before
flask-app:
  ports:
    - "5000:5000"

# After — no ports mapping; Flask is reachable only within app-network
flask-app:
  build: .
  networks:
    - app-network
  # Remove the ports: block entirely, or bind only to loopback for debugging:
  # ports:
  #   - "127.0.0.1:5000:5000"
```

Nginx should communicate with Flask using the Docker service name: `proxy_pass http://flask-app:5000;` (updating `host.docker.internal` to the service name for proper internal resolution).

### References
- https://cwe.mitre.org/data/definitions/284.html
- https://docs.docker.com/compose/compose-file/05-services/#ports

## Finding 3: Missing HTTP Security Response Headers

**Finding ID:** `APPSEC-c5e81d3f29`
**File:** `nginx.conf`
**Lines:** 1–18
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://host.docker.internal:5000;
    }
    # No security headers configured anywhere
}
```

### Description
The Nginx configuration emits no security response headers. There is no `Content-Security-Policy`, no `X-Frame-Options`, no `X-Content-Type-Options`, and no `Strict-Transport-Security`. Additionally, the server listens only on HTTP (port 80) with no HTTPS redirect, meaning session cookies and any future authenticated traffic transit over plaintext. An attacker on the network path can perform MITM, and the browser has no policy preventing clickjacking or MIME sniffing attacks.

### Prioritization
Lowest priority of confirmed findings. No direct attacker-controlled data path leads to exploitation here — these are defense-in-depth controls. Remediate after Findings 1 and 2.

### Exploitability Notes
- **Exploit Preconditions:** Secondary attacker preconditions (MITM position, victim browsing the app, malicious iframe embedding).
- **Uncertainty Boundary:** Impact depends on what future features the app develops (e.g., authenticated endpoints make missing HSTS and CSP significantly more impactful).

### Remediation
Add a `add_header` block in the Nginx `server` context:

```nginx
server {
    listen 80;
    server_name example.com;

    # Security headers
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
    add_header Content-Security-Policy "default-src 'self'" always;
    # Enable HSTS only after HTTPS is configured:
    # add_header Strict-Transport-Security "max-age=63072000; includeSubDomains" always;

    location / {
        proxy_pass http://flask-app:5000;
    }
}
```

### References
- https://owasp.org/www-project-secure-headers/
- https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy

## Finding 4: Payment Redirect Target Uses Plaintext HTTP

**Finding ID:** `APPSEC-d1a94b7e3c`
**File:** `nginx.conf`
**Lines:** 15
**CWE:** CWE-319 — Cleartext Transmission of Sensitive Information
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P3
**Severity:** INFO
**Confidence:** MEDIUM

### Vulnerable Code
```nginx
return 302 http://payment-api$uri;
```

### Description
The redirect target for the `/payment` endpoint uses a plaintext `http://` URL. If `payment-api` is an internal Docker service, intra-cluster communication over HTTP is a common pattern, but any payment tokens, session cookies, or PII transmitted in the redirect chain travel unencrypted. If `payment-api` is or ever becomes externally addressable, this exposes payment flow traffic to interception.

### Prioritization
Lowest finding. The internal-only nature of `payment-api` reduces immediate risk, and Finding 1 (CRLF injection in the same line) is the primary concern for this directive.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must be on the network path between the Nginx container and the payment-api service.
- **Uncertainty Boundary:** Whether `payment-api` is internal-only or externally reachable is not determinable from the config.

### Remediation
Use HTTPS for payment-related communication, even internally:

```nginx
return 302 https://payment-api$uri;
```

Or configure TLS between the Nginx upstream and payment-api if that service supports it.

### References
- https://cwe.mitre.org/data/definitions/319.html
