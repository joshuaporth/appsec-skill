## Finding 1: CORS — Credentialed Origin Reflection

**Finding ID:** `APPSEC-f7c3d29e1a`
**File:** `main.js`
**Lines:** 16–22
**CWE:** CWE-942 — Permissive Cross-domain Policy with Untrusted Domains
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.use((req, res, next) => {
    const origin = req.get('Origin');
    if (origin) {
        res.header('Access-Control-Allow-Origin', origin); 
        res.header('Access-Control-Allow-Credentials', 'true'); 
    }
    next();
});
```

### Description
The CORS middleware unconditionally reflects the attacker-controlled `Origin` request header into `Access-Control-Allow-Origin` while simultaneously setting `Access-Control-Allow-Credentials: true`. This is the textbook credentialed origin reflection anti-pattern: because the browser sees an exact-match origin with credentials allowed, it permits any cross-origin page to make authenticated requests and read the full response. Combined with Finding 2 (`sameSite: "none"` on the auth cookie), an attacker page at `https://evil.com` can issue `fetch('http://localhost:3000/api-key', {credentials: 'include'})`, receive the victim's `auth` cookie automatically, and read the JSON response containing the API key — with no user interaction beyond visiting the attacker's site. The `get-api-key.req` artifact directly demonstrates this attack vector (`Origin: https://test.com` + `Cookie: auth=admin`).

### Prioritization
P1 — highest priority. This is directly and trivially exploitable from any origin with no preconditions beyond the victim having an active session. Findings 3 and 4 are secondary.

### Exploitability Notes
- **Exploit Preconditions:** Victim must have a valid `auth` cookie (obtained via `/mock-login` or a real login flow). Attacker hosts a page the victim visits.
- **Uncertainty Boundary:** If an upstream reverse proxy strips or overwrites the `Origin` header before Express sees it, exploitability would be reduced — but no such proxy is in scope.

### Remediation
Replace the wildcard reflection with an explicit allowlist. `Access-Control-Allow-Credentials: true` must never be paired with a dynamically reflected origin.

```javascript
const ALLOWED_ORIGINS = new Set([
  'https://your-frontend.example.com',
]);

app.use((req, res, next) => {
    const origin = req.get('Origin');
    if (origin && ALLOWED_ORIGINS.has(origin)) {
        res.header('Access-Control-Allow-Origin', origin);
        res.header('Access-Control-Allow-Credentials', 'true');
        res.header('Vary', 'Origin'); // required for correct caching
    }
    next();
});
```

**Counterfactual invalidation:** If `ALLOWED_ORIGINS.has(origin)` gates the reflection, an attacker-controlled origin never appears in the response header and the browser blocks the cross-origin read.

### References
- https://owasp.org/www-community/attacks/CORS_OriginHeaderScrutiny
- https://cwe.mitre.org/data/definitions/942.html

## Finding 2: Authentication Cookie Set With `SameSite=None`

**Finding ID:** `APPSEC-b8e2a47c1d`
**File:** `main.js`
**Lines:** 27
**CWE:** CWE-1275 — Sensitive Cookie with Improper SameSite Attribute
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
res.cookie('auth', users.admin.username, { httpOnly: true, secure: true, sameSite: "none"});
```

### Description
The authentication cookie is issued with `sameSite: "none"`, which explicitly instructs the browser to attach this cookie on all cross-site requests, including those initiated by third-party pages. This directly enables the CORS-based theft in Finding 1: without `sameSite: "none"`, the browser would withhold the `auth` cookie on the cross-origin `fetch` from `evil.com`, stopping the attack even if the CORS headers were misconfigured. With both issues present together, the exploit chain is complete with zero user interaction beyond visiting a malicious page. The `secure: true` flag is correct and necessary, but it does not mitigate the cross-site exposure.

### Prioritization
P1 — co-primary with Finding 1. These two issues form a complete attack chain together. Remediating either one independently breaks the chain; remediating both is required for defense-in-depth.

### Exploitability Notes
- **Exploit Preconditions:** Victim must have an `auth` cookie. The `/mock-login` endpoint means any user can obtain one with no credentials.
- **Uncertainty Boundary:** Some browsers have begun partitioning third-party cookies by default; behavior may vary by browser version and user settings.

### Remediation
Change `sameSite` from `"none"` to `"strict"` (or `"lax"` if cross-site GET navigation must carry the cookie). `sameSite: "none"` is only appropriate for cookies that must intentionally work in third-party/embedded contexts (e.g., payment iframes).

```javascript
res.cookie('auth', users.admin.username, {
    httpOnly: true,
    secure: true,
    sameSite: "strict"   // was "none" — prevents cross-site request cookie attachment
});
```

**Counterfactual invalidation:** With `sameSite: "strict"`, the browser withholds the `auth` cookie on the cross-origin fetch from `evil.com`, preventing the CORS-based read of the API key even if the CORS headers remain misconfigured.

### References
- https://developer.mozilla.org/en-US/docs/Web/HTTP/Cookies#samesite_attribute
- https://cwe.mitre.org/data/definitions/1275.html

## Finding 3: Unauthenticated `/mock-login` Grants Admin Session to Any Caller

**Finding ID:** `APPSEC-4d9b2c7f3e`
**File:** `main.js`
**Lines:** 26–29
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.get('/mock-login', (req, res) => {
    res.cookie('auth', users.admin.username, { httpOnly: true, secure: true, sameSite: "none"});
    return res.status(200).json({ message: 'Login successful!' });;
});
```

### Description
`/mock-login` unconditionally issues a valid `auth=admin` session cookie to any caller, no credentials required. The code comment acknowledges this as a placeholder ("imagine this is a fully grown login"), but as deployed the endpoint constitutes a complete authentication bypass: any unauthenticated actor can obtain an admin session in one unauthenticated GET request and then retrieve the API key from `/api-key`. This also provides the prerequisite session needed to make Finding 1 exploitable from any origin.

### Prioritization
P2. The CORS and SameSite issues (Findings 1–2) are the primary attack path for external attackers. This finding additionally allows direct, unauthenticated API key retrieval by any party who can reach the server.

### Exploitability Notes
- **Exploit Preconditions:** Network access to `GET /mock-login`. No credentials, tokens, or prior session required.
- **Uncertainty Boundary:** Code is explicitly marked as a challenge placeholder; in a production replacement, real credential verification would gate this endpoint.

### Remediation
Replace the automatic cookie issuance with credential validation before granting a session. The pattern below shows the minimum-viable shape; substitute a real user store and a password-hash comparison.

```javascript
app.post('/login', async (req, res) => {
    const { username, password } = req.body;
    const user = users[username];
    if (!user || !await bcrypt.compare(password, user.passwordHash)) {
        return res.status(401).json({ message: 'Invalid credentials' });
    }
    res.cookie('auth', user.username, {
        httpOnly: true,
        secure: true,
        sameSite: 'strict'
    });
    return res.status(200).json({ message: 'Login successful!' });
});
```

### References
- https://cwe.mitre.org/data/definitions/306.html
- https://owasp.org/www-project-top-ten/2021/A07_2021-Identification_and_Authentication_Failures

## Finding 4: Hardcoded API Key in Source

**Finding ID:** `APPSEC-1a5c9e3f7b`
**File:** `main.js`
**Lines:** 9–14
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
const users = {
  admin: {
    username: 'admin',
    apiKey: '<some-secret-API-key>'
  }
};
```

### Description
The API key (and the entire user store) is hardcoded directly in the application source. Any developer with read access to the repository, any CI log that prints this file, or any accidental exposure of source code immediately reveals the credential. Rotation requires a code change and a redeployment rather than a secrets-store update. The code comment acknowledges intent to move this to a database, but the current form constitutes a static secret embedded in version-controlled code.

### Prioritization
P2. The CORS and SameSite findings allow runtime theft of the API key; this finding allows static theft from source. Both paths must be closed.

### Exploitability Notes
- **Exploit Preconditions:** Read access to the source file (repo, CI artifact, deployed bundle).
- **Uncertainty Boundary:** The placeholder value `<some-secret-API-key>` suggests the real key has not yet been committed; this finding applies when the real value is substituted.

### Remediation
Load secrets from environment variables (or a secrets manager) at startup; never commit them to source.

```javascript
// Load from environment at startup — never hardcode
const API_KEY = process.env.ADMIN_API_KEY;
if (!API_KEY) throw new Error('ADMIN_API_KEY environment variable is required');

// Resolve users from DB at request time; for this shape:
async function getUserByUsername(username) {
    return db.query('SELECT username, api_key FROM users WHERE username = $1', [username]);
}
```

## Finding 5: Missing HTTP Security Headers (No `helmet`)

**Finding ID:** `APPSEC-9e2d5a1c4b`
**File:** `main.js`
**Lines:** 1–6
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
const express = require('express');
const cookieParser = require('cookie-parser');
const app = express();
// No helmet() or equivalent security header middleware
app.use(cookieParser());
```

### Description
The application sets no defensive HTTP response headers. Missing headers include `X-Content-Type-Options: nosniff` (MIME sniffing), `X-Frame-Options` / `Content-Security-Policy frame-ancestors` (clickjacking), `Strict-Transport-Security` (HTTPS downgrade), and a `Content-Security-Policy` (XSS restriction). While none of these directly enable the primary attack chains above, their absence reduces defense-in-depth and is trivially fixed.

### Prioritization
P3. Address after Findings 1–4. No standalone exploit path; these are defense-in-depth controls.

### Exploitability Notes
- **Exploit Preconditions:** Requires other vulnerabilities (e.g., XSS entry point) to be meaningfully exploited.
- **Uncertainty Boundary:** Impact depends on the full application context; headers matter more at higher complexity.

### Remediation
Add `helmet` as the first middleware:

```bash
npm install helmet
```

```javascript
const helmet = require('helmet');
app.use(helmet()); // sets X-Content-Type-Options, X-Frame-Options, HSTS, and more
app.use(cookieParser());
```

### References
- https://helmetjs.github.io/
- https://owasp.org/www-project-secure-headers/
