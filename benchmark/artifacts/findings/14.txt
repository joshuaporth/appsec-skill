## Finding 1: Missing Authentication and Authorization

**Finding ID:** `APPSEC-b4d590cd5121`
**File:** `main.js`
**Lines:** 15–41
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post('/transfer', (req, res) => {
  const { from, to, amount } = req.body;

  if (typeof from !== 'number' || typeof to !== 'number' || typeof amount !== 'number' || amount <= 0) {
    return res.status(400).json({ message: 'Invalid input' });
  }
  
  db.get("SELECT balance FROM accounts WHERE id = ?", [from], (err, row) => {
    ...
    db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], ...
```

### Description
Neither `/transfer` nor `/balance/:id` has any authentication or authorization gate. Any anonymous HTTP client can POST `{ "from": 1, "to": 2, "amount": 1000 }` and drain account 1 with zero preconditions. There is no session check, API key, JWT, or any mechanism verifying the caller owns the `from` account. The `from` field is entirely attacker-controlled, allowing transfers from arbitrary accounts to any destination.

### Prioritization
Highest priority. This is a complete auth bypass with no preconditions — an unauthenticated attacker on the network can empty any account in a single request. All other findings are secondary to this one.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 3000. That is the only requirement.
- **Uncertainty Boundary:** If an external reverse proxy enforces authentication before traffic reaches this service (not evidenced in docker-compose.yml), impact is reduced — but the application itself provides zero defense in depth.

### Remediation
Add authentication middleware. At minimum, require a bearer token that is bound to an account identity, and enforce that `req.body.from` matches the authenticated account:

```javascript
const crypto = require('crypto');

// At startup: issue tokens bound to account IDs (use a real auth system in production)
const TOKENS = new Map([
  ['token-account-1', 1],
  ['token-account-2', 2],
]);

function requireAuth(req, res, next) {
  const header = req.headers.authorization || '';
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  const accountId = token ? TOKENS.get(token) : null;
  if (!accountId) return res.status(401).json({ message: 'Unauthorized' });
  req.authenticatedAccountId = accountId;
  next();
}

app.post('/transfer', requireAuth, (req, res) => {
  const { from, to, amount } = req.body;
  // Enforce ownership: caller can only transfer from their own account
  if (from !== req.authenticatedAccountId) {
    return res.status(403).json({ message: 'Forbidden' });
  }
  // ... rest of transfer logic
});
```

## Finding 2: Race Condition / TOCTOU on Balance Transfer (Negative Balance / Double Spend)

**Finding ID:** `APPSEC-9dad4235543f`
**File:** `main.js`
**Lines:** 22–32
**CWE:** CWE-362 — Concurrent Execution Using Shared Resource with Improper Synchronization (TOCTOU)
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
db.get("SELECT balance FROM accounts WHERE id = ?", [from], (err, row) => {
    if (!row) return res.status(400).json({ message: 'Invalid from account' });

    if (row.balance < amount) return res.status(400).json({ message: 'Insufficient funds' });

    db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {      
      db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {        
        res.status(200).json({ message: 'Transfer successful' });
      });
    });
  });
```

### Description
The SELECT (balance check) and both UPDATEs are three separate, non-transactional database operations. Under concurrent requests, two `POST /transfer` calls for the same `from` account can interleave: both read `balance = 1000`, both pass the sufficiency check, then both proceed to deduct — driving the balance to a negative value (e.g., two concurrent withdrawals of 900 each produce a final balance of −800). An attacker who can issue rapid parallel requests can double-spend funds or force accounts into negative balances far beyond what they hold.

### Prioritization
P1, second only to the missing authentication finding. Resolving auth first limits who can exploit this, but even with authentication this TOCTOU must be independently fixed to preserve financial integrity.

### Exploitability Notes
- **Exploit Preconditions:** Ability to send concurrent HTTP requests (trivially done with `Promise.all` or any HTTP benchmark tool). Account must exist.
- **Uncertainty Boundary:** SQLite serializes writes at the file level, but the Node.js `sqlite3` library schedules callbacks asynchronously. The SELECT and UPDATE are in separate event-loop turns, creating a real interleaving window. Race is reliably triggerable with even modest concurrency.
- **Counterfactual invalidation:** Wrapping all three operations in a single SQLite `BEGIN IMMEDIATE` / `COMMIT` transaction eliminates the race.

### Remediation
Wrap the entire check-and-update sequence in an atomic transaction. Use `BEGIN IMMEDIATE` so that SQLite acquires a write lock before any reads:

```javascript
app.post('/transfer', (req, res) => {
  const { from, to, amount } = req.body;

  if (!Number.isFinite(from) || !Number.isInteger(from) ||
      !Number.isFinite(to)   || !Number.isInteger(to)   ||
      !Number.isFinite(amount) || amount <= 0) {
    return res.status(400).json({ message: 'Invalid input' });
  }

  db.serialize(() => {
    db.run("BEGIN IMMEDIATE", (err) => {
      if (err) return res.status(500).json({ message: 'Transaction error' });

      db.get("SELECT balance FROM accounts WHERE id = ?", [from], (err, row) => {
        if (err || !row) {
          return db.run("ROLLBACK", () =>
            res.status(400).json({ message: 'Invalid from account' }));
        }
        if (row.balance < amount) {
          return db.run("ROLLBACK", () =>
            res.status(400).json({ message: 'Insufficient funds' }));
        }

        db.get("SELECT id FROM accounts WHERE id = ?", [to], (err, toRow) => {
          if (err || !toRow) {
            return db.run("ROLLBACK", () =>
              res.status(400).json({ message: 'Invalid to account' }));
          }

          db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {
            if (err) return db.run("ROLLBACK", () => res.status(500).json({ message: 'Transfer failed' }));

            db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {
              if (err) return db.run("ROLLBACK", () => res.status(500).json({ message: 'Transfer failed' }));

              db.run("COMMIT", (err) => {
                if (err) return res.status(500).json({ message: 'Commit failed' });
                res.status(200).json({ message: 'Transfer successful' });
              });
            });
          });
        });
      });
    });
  });
});
```

## Finding 3: Silent Fund Destruction on Transfer to Non-Existent Account

**Finding ID:** `APPSEC-17659317d48f`
**File:** `main.js`
**Lines:** 27–30
**CWE:** CWE-754 — Improper Check for Unusual or Exceptional Conditions
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {      
  db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {        
    res.status(200).json({ message: 'Transfer successful' });
  });
});
```

### Description
The `from` account is validated to exist before the transfer, but the `to` account is never checked. If a caller supplies a non-existent `to` ID, the deduction `UPDATE` removes funds from `from` (rows affected = 1), but the credit `UPDATE` silently affects zero rows. The code returns HTTP 200 "Transfer successful" regardless. The result is that funds are permanently destroyed from the source account with no credit to any recipient. An attacker or misconfigured client can deliberately drain an account by specifying a bogus `to` value (e.g., `{ "from": 1, "to": 9999, "amount": 1000 }`).

### Prioritization
P2 — lower priority than the auth bypass and race condition, but independently exploitable once those are addressed (or even now, since there is no auth). Remediation is included in the transaction-based fix shown in Finding 2.

### Exploitability Notes
- **Exploit Preconditions:** Network access; knowledge of a valid `from` account ID (both IDs are guessable sequential integers).
- **Uncertainty Boundary:** None — this is a straightforward logic gap with no unknown runtime factors.
- **Counterfactual invalidation:** Validating `to` account existence before deducting from `from` (inside the same transaction) eliminates this.

### Remediation
Validate the `to` account exists before executing either UPDATE, inside the same transaction (see the `SELECT id FROM accounts WHERE id = ?` check in the transaction block shown in Finding 2's remediation).

- https://cwe.mitre.org/data/definitions/754.html

## Finding 4: `NaN` Bypasses Amount Validation — Potential Balance Corruption

**Finding ID:** `APPSEC-ed894aa9b750`
**File:** `main.js`
**Lines:** 18–19
**CWE:** CWE-20 — Improper Input Validation
**OWASP Category:** A03:2021 – Injection / A04:2021 – Insecure Design
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```javascript
if (typeof from !== 'number' || typeof to !== 'number' || typeof amount !== 'number' || amount <= 0) {
    return res.status(400).json({ message: 'Invalid input' });
}
```

### Description
In JavaScript, `typeof NaN === 'number'` is `true`, and `NaN <= 0` evaluates to `false`. This means `amount = NaN` passes both guards and reaches the SQLite layer. The node-sqlite3 library binds JavaScript `NaN` as SQL `NULL`. When SQLite executes `UPDATE accounts SET balance = balance - NULL`, the result is `NULL` (any arithmetic with NULL yields NULL), setting the `balance` column to `NULL` and corrupting the account record. The same applies to `Infinity` and `-Infinity`, which node-sqlite3 also coerces to NULL. An attacker can corrupt an account balance to NULL by POSTing `{ "from": 1, "to": 2, "amount": NaN }` (the JSON value `NaN` is not valid JSON but some parsers accept it; the attack also works via `{ "amount": null }` if the `typeof` check is somehow bypassed through other means).

*Note: JSON does not allow `NaN` as a literal value per RFC 8259, so a strict JSON parser will reject it. However `Infinity` and `-Infinity` are similarly invalid, and the strict behavior depends on the exact body-parser/JSON.parse version. Confidence is MEDIUM pending verification of parser behavior.*

### Prioritization
P2 — exploitability is conditional on JSON parser acceptance of `NaN`/`Infinity`, which RFC 8259-compliant parsers reject. The fix is trivial and closes the gap regardless of parser behavior.

### Exploitability Notes
- **Exploit Preconditions:** JSON parser that accepts `NaN` or `Infinity` literals, OR a way to supply a numeric-typed JS `NaN` before the check.
- **Uncertainty Boundary:** Node.js's built-in `JSON.parse` rejects `NaN`/`Infinity` as invalid JSON, so body-parser's default behavior may block this at the parse layer. Confidence is MEDIUM — the logic gap is real; exploitability depends on runtime parser strictness.
- **Counterfactual invalidation:** Replacing `typeof amount === 'number'` with `Number.isFinite(amount)` closes this completely.

### Remediation
Use `Number.isFinite()` which returns `false` for `NaN`, `Infinity`, and `-Infinity`:

```javascript
// Before
if (typeof from !== 'number' || typeof to !== 'number' || typeof amount !== 'number' || amount <= 0) {

// After
if (!Number.isFinite(from) || !Number.isInteger(from) ||
    !Number.isFinite(to)   || !Number.isInteger(to)   ||
    !Number.isFinite(amount) || amount <= 0) {
```

Also enforce that `from !== to` (transferring to self is meaningless and could hide accounting bugs).

- https://cwe.mitre.org/data/definitions/20.html
- https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/isFinite
