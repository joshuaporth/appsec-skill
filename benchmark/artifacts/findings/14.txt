## Finding 1: Race Condition / TOCTOU on Fund Transfer

**File:** `main.js`
**Lines:** 22–33
**CWE:** CWE-362 — Concurrent Execution Using Shared Resource with Improper Synchronization (TOCTOU)
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
db.get("SELECT balance FROM accounts WHERE id = ?", [from], (err, row) => {
    if (!row) return res.status(400).json({ message: 'Invalid from account' });

    if (row.balance < amount) return res.status(400).json({ message: 'Insufficient funds' });

    db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {      
      db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {        
        res.status(200).json({ message: 'Transfer successful' });
      });
    });
  });
```

### Description
The transfer logic performs a three-step check-then-act sequence (SELECT, then two UPDATEs) outside of any database transaction. Because Node.js I/O is non-blocking, multiple concurrent requests can each pass the balance check (`row.balance < amount`) before any debit is applied, then each proceed to decrement the balance independently. For example, with account 1 holding a balance of 1000, an attacker sending 10 simultaneous `POST /transfer` requests with `amount: 1000` will have all 10 pass the balance check (all reading 1000), then all 10 debit 1000, driving the balance to -9000. No atomic protection exists at the SQL layer and no row lock is held between the SELECT and UPDATE.

### Prioritization
P1 — Highest priority. This is immediately exploitable without any credentials (see Finding 2), requires only concurrent HTTP requests, and causes unbounded financial loss.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can send concurrent HTTP requests (e.g., via `Promise.all` or `curl --parallel`). No authentication is required (see Finding 2).
- **Uncertainty Boundary:** SQLite's default journal mode is DELETE (not WAL). In WAL mode, concurrent reads are less blocked; in either mode, the async callback model in Node.js means the SELECT and UPDATE are separate I/O operations with no implicit lock between them.

### Remediation
Wrap the entire transfer in an explicit SQLite transaction and replace the SELECT + conditional + UPDATE pattern with a single conditional UPDATE:

```javascript
app.post('/transfer', (req, res) => {
  const { from, to, amount } = req.body;

  if (typeof from !== 'number' || typeof to !== 'number' || typeof amount !== 'number' || amount <= 0) {
    return res.status(400).json({ message: 'Invalid input' });
  }

  db.serialize(() => {
    db.run("BEGIN EXCLUSIVE TRANSACTION");

    db.run(
      "UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?",
      [amount, from, amount],
      function (err) {
        if (err || this.changes === 0) {
          db.run("ROLLBACK");
          return res.status(400).json({ message: 'Insufficient funds or invalid account' });
        }

        db.run(
          "UPDATE accounts SET balance = balance + ? WHERE id = ?",
          [amount, to],
          function (err) {
            if (err || this.changes === 0) {
              db.run("ROLLBACK");
              return res.status(400).json({ message: 'Invalid destination account' });
            }
            db.run("COMMIT");
            res.status(200).json({ message: 'Transfer successful' });
          }
        );
      }
    );
  });
});
```

Using `BEGIN EXCLUSIVE TRANSACTION` holds a write lock for the duration, and the `AND balance >= ?` guard makes the debit atomic — if balance is insufficient, zero rows are modified (`this.changes === 0`).

**Counterfactual:** If the SELECT were eliminated and the debit performed as `UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?` inside a transaction checked via `this.changes`, the TOCTOU window closes entirely.

- [CWE-362: Race Condition](https://cwe.mitre.org/data/definitions/362.html)
- [OWASP Race Conditions](https://owasp.org/www-community/vulnerabilities/Race_Conditions)

## Finding 2: Missing Authentication on All Endpoints

**File:** `main.js`
**Lines:** 15–41
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post('/transfer', (req, res) => {
  const { from, to, amount } = req.body;
  // No authentication check — any caller proceeds
  ...
});

app.get('/balance/:id', (req, res) => {
  // No authentication check — balance of any account is readable
  ...
});
```

### Description
Neither the `/transfer` nor `/balance/:id` endpoint verifies the caller's identity. There is no session middleware, JWT verification, API key check, or any other authentication gate anywhere in the application. Any unauthenticated actor who can reach port 3000 can initiate fund transfers from any account and read any account's balance. Combined with Finding 3 (no ownership check on `from`), this means a complete financial takeover is possible with a single HTTP request.

### Prioritization
P1 — Co-equal with Finding 1. Authentication is the first gate for a financial API; its absence nullifies every downstream control.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 3000. No prior account or session needed.
- **Uncertainty Boundary:** Docker port mapping (`3000:3000`) in `docker-compose.yml` exposes the service on all interfaces by default; deployment behind a firewall or private VPC would limit attacker reach but not eliminate the vulnerability.

### Remediation
Add authentication middleware to all sensitive routes. Example using a static API token (replace with a full auth system for production):

```javascript
const VALID_TOKEN = process.env.API_TOKEN; // set in environment, not hardcoded

function authenticate(req, res, next) {
  const token = req.headers['authorization'];
  if (!token || token !== `Bearer ${VALID_TOKEN}`) {
    return res.status(401).json({ message: 'Unauthorized' });
  }
  next();
}

app.post('/transfer', authenticate, (req, res) => { ... });
app.get('/balance/:id', authenticate, (req, res) => { ... });
```

For a real system, use a proper session library (e.g., `express-session` with a secure store) or a JWT library with signature verification, and tie the authenticated identity to account ownership (see Finding 3).

**Counterfactual:** Adding `authenticate` middleware to both routes removes the missing-authentication vector entirely.

## Finding 3: Broken Object-Level Authorization — `from` Account Not Ownership-Verified

**File:** `main.js`
**Lines:** 16, 22–33
**CWE:** CWE-862 — Missing Authorization (IDOR)
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post('/transfer', (req, res) => {
  const { from, to, amount } = req.body;
  // 'from' is trusted from user input with no ownership check
  db.get("SELECT balance FROM accounts WHERE id = ?", [from], (err, row) => {
```

### Description
The `from` account ID is taken directly from the user-supplied request body with no check that the authenticated caller owns or is authorized to debit that account. Even if authentication were added (Finding 2), a caller authenticated as account 2 could include `"from": 1` in the body and transfer funds from account 1 without restriction. This is a classic IDOR: the object reference (`from`) is user-controlled and server-side ownership is never enforced. An attacker can empty any account by setting `from` to the victim's account ID.

### Prioritization
P1 — Even after addressing Finding 2, this finding independently enables account takeover. Both must be fixed.

### Exploitability Notes
- **Exploit Preconditions:** After authentication is added: attacker has a valid session/token for any account. Without authentication (current state): no preconditions at all.
- **Uncertainty Boundary:** None — the code directly uses the user-supplied `from` value without any server-side lookup of the caller's account.

### Remediation
After adding authentication, bind the `from` account to the authenticated user's identity server-side — never accept it from the request body:

```javascript
app.post('/transfer', authenticate, (req, res) => {
  const from = req.user.accountId; // derived from verified auth token, NOT from req.body
  const { to, amount } = req.body;
  ...
});
```

If the API legitimately allows initiating transfers on behalf of other accounts (e.g., admin functionality), add an explicit authorization check:

```javascript
if (req.user.accountId !== from && !req.user.isAdmin) {
  return res.status(403).json({ message: 'Forbidden' });
}
```

**Counterfactual:** Deriving `from` from `req.user` (populated by auth middleware) rather than `req.body` removes the IDOR entirely.

## Finding 4: Transfer to Nonexistent Account Silently Destroys Funds

**File:** `main.js`
**Lines:** 27–31
**CWE:** CWE-754 — Improper Check for Unusual or Exceptional Conditions
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {      
  db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {        
    res.status(200).json({ message: 'Transfer successful' });
  });
});
```

### Description
The `to` account is never validated for existence before the transfer begins. If `to` refers to an account ID that does not exist, the credit UPDATE silently affects zero rows while the debit UPDATE has already committed. The response still returns `200 Transfer successful`, so the caller (or attacker) receives no indication of failure. Money is permanently destroyed from `from` with no record of where it went. An attacker with no authentication (current state) could trigger this intentionally against any account as an act of financial sabotage.

### Prioritization
P2 — Lower than Findings 1–3 because it requires Findings 1–3 to be exploitable by an external attacker. Becomes the next highest priority once auth and TOCTOU are resolved. The remediation in Finding 1 (checking `this.changes` after the credit UPDATE and rolling back on failure) also fixes this finding.

### Exploitability Notes
- **Exploit Preconditions:** Access to the API (unauthenticated in current state). Knowledge of a valid `from` account ID.
- **Uncertainty Boundary:** Requires the sender to specify a non-existent `to` account ID. Currently trivial since account IDs are guessable integers.

### Remediation
The transactional remediation in Finding 1 already addresses this: checking `this.changes === 0` after the credit UPDATE triggers a `ROLLBACK`, preventing the debit from persisting if the credit fails. Additionally, validate the `to` account at the start of the transaction:

```javascript
db.get("SELECT id FROM accounts WHERE id = ?", [to], (err, toRow) => {
  if (!toRow) {
    db.run("ROLLBACK");
    return res.status(400).json({ message: 'Invalid destination account' });
  }
  // proceed with debit
});
```

## Finding 5: Missing Security Headers (No Helmet)

**File:** `main.js`
**Lines:** 5–6
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
const app = express();
app.use(bodyParser.json());
// No helmet() or security header middleware
```

### Description
Express is initialized without `helmet` or equivalent middleware. By default Express sets `X-Powered-By: Express` (server fingerprinting) and omits `X-Content-Type-Options`, `X-Frame-Options`, `Content-Security-Policy`, and `Strict-Transport-Security`. While none of these alone enable direct exploitation of this API, their absence widens the attack surface for browser-based attack chains and facilitates fingerprinting.

### Prioritization
P3 — Lowest priority. Remediating Findings 1–4 first is essential; this is a hardening measure.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can observe HTTP response headers or trick a browser into loading the API endpoint in a framed or cross-origin context.
- **Uncertainty Boundary:** Impact depends on whether this API is consumed from a browser context and what adjacent application surfaces exist.

### Remediation
```javascript
const helmet = require('helmet');
app.use(helmet());
// helmet() enables X-Content-Type-Options, X-Frame-Options, HSTS, removes X-Powered-By, and more
```

Add `helmet` to `package.json`: `npm install helmet`

### Description
All three database callback `err` parameters are captured but never inspected. If a database error occurs — for example a locked database, constraint violation, or disk I/O failure — the code continues into the success path. In the UPDATE callbacks, this means the response always returns `200 Transfer successful` regardless of whether the SQL actually executed, potentially masking data corruption or enabling a hung response if `res` is not reliably called in all error paths.

### Prioritization
P3 — No direct security exploit, but error suppression can mask the impact of other failures and makes debugging harder under attack conditions.

### Remediation
```javascript

  if (err) return res.status(500).json({ message: 'Database error' });
  if (!row) return res.status(400).json({ message: 'Invalid from account' });
  ...
  db.run("UPDATE accounts SET balance = balance - ? WHERE id = ?", [amount, from], (err) => {
    if (err) return res.status(500).json({ message: 'Transfer failed' });
    db.run("UPDATE accounts SET balance = balance + ? WHERE id = ?", [amount, to], (err) => {
      if (err) return res.status(500).json({ message: 'Transfer failed' });
      res.status(200).json({ message: 'Transfer successful' });
    });
  });

```

Note: the transactional fix in Finding 1 makes this more robust by allowing a `ROLLBACK` on error.
