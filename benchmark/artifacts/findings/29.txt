## Finding 1: Mass Assignment — Security-Sensitive `paid` Field Writable From Client

**Finding ID:** `APPSEC-8c3fa12e91`  
**File:** `main.py`  
**Lines:** 41–45  
**CWE:** CWE-915 — Improperly Controlled Modification of Dynamically-Determined Object Attributes  
**OWASP Category:** A03:2021 – Injection / A01:2021 – Broken Access Control  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH  

### Vulnerable Code
```python
def create_invoice():
    data = request.json or {}

    # Amount is server-controlled (e.g., from the authenticated user's plan/contract)
    data["amount"] = get_amount_for_current_user()
    invoice = Invoice(**data)
```

### Description
The `create_invoice` handler reads the entire JSON request body into `data`, overwrites only `amount` with a server-side value, then passes the full dict as keyword arguments to the `Invoice` ORM constructor. The `Invoice` model has a `paid` boolean column (line 18, default `False`) that is never explicitly set server-side. An attacker can include `"paid": true` in the POST body — after `amount` is overwritten the key survives — and the SQLAlchemy model will accept it, persisting an invoice that is permanently pre-marked as paid without any real payment having occurred. The developer comment calls out amount as "server-controlled" but does not protect the equally sensitive `paid` field, making this a targeted oversight.

Attacker-controlled input shape:
```json
POST /invoices
{"customer_name":"evil","billing_address":"1 Free St","vat_id":"XX000","description":"free","paid":true}
```

Result: new row inserted with `paid = 1`, bypassing all payment logic.

### Prioritization
This is the highest-priority finding. It enables direct financial fraud (invoices created pre-paid without payment) with no preconditions beyond the ability to send an HTTP POST. The impact is concrete and the exploit is trivial.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must be able to reach `POST /invoices`. No authentication is enforced (see Finding 2), so this is unauthenticated by default.
- **Uncertainty Boundary:** If a separate middleware layer validates and strips unknown/forbidden fields before this handler runs, exploitability would be reduced — but no such layer is visible in scope.

### Counterfactual Invalidation
If `invoice = Invoice(**data)` were replaced with explicit field extraction *and* `paid` were hard-coded server-side, this finding would not be valid.

### Remediation
Explicitly map only allowlisted, non-sensitive fields from the request, and set security-sensitive state fields server-side unconditionally:

```python
@app.route("/invoices", methods=["POST"])
def create_invoice():
    data = request.json or {}

    invoice = Invoice(
        customer_name=data.get("customer_name"),
        billing_address=data.get("billing_address"),
        vat_id=data.get("vat_id"),
        description=data.get("description"),
        amount=get_amount_for_current_user(),  # server-controlled
        paid=False,                            # server-controlled; never from client
    )

    db.session.add(invoice)
    db.session.commit()
    return jsonify(invoice.to_dict()), 201
```

This approach ensures that regardless of what keys the client supplies, only the explicitly named fields are accepted, and `paid` (and `amount`) are always server-determined.

- https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/
- https://cwe.mitre.org/data/definitions/915.html

## Finding 2: Missing Authentication on All Endpoints

**Finding ID:** `APPSEC-2d9b47c051`  
**File:** `main.py`  
**Lines:** 39–63  
**CWE:** CWE-306 — Missing Authentication for Critical Function  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH  

### Vulnerable Code
```python
@app.route("/invoices", methods=["POST"])
def create_invoice():
    data = request.json or {}
    ...

@app.route("/invoices", methods=["GET"])
def list_invoices():
    invoices = Invoice.query.all()
    ...

@app.route("/pay/<int:invoice_id>", methods=["POST"])
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.get_or_404(invoice_id)
    invoice.paid = True
    ...
```

### Description
None of the three state-changing or data-access routes enforce any authentication check — no session cookie validation, no bearer token check, no `@login_required` decorator, and no before-request guard. The comment at line 67 ("imagine proper authentication and authorization to be in place") is a developer note about intent, not an implemented control. Any unauthenticated HTTP client can create invoices, retrieve every invoice record in the database (including PII), and mark arbitrary invoices as paid.

### Prioritization
P1 alongside Finding 1. Without authentication, all other access control findings are trivially exploitable by any network-adjacent attacker, not just authenticated users.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 5000. No credentials required.
- **Uncertainty Boundary:** An upstream reverse proxy or API gateway could enforce auth before requests reach Flask. None is visible in scope; `docker-compose.yml` exposes port 5000 directly.

### Counterfactual Invalidation
Adding a `@login_required` decorator (or equivalent before-request check) to each route, or a global `before_request` guard, would eliminate the unauthenticated access vector.

### Remediation
Use Flask-Login or a JWT middleware and protect every sensitive route:

```python
from functools import wraps
from flask import session, abort

def login_required(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        if "user_id" not in session:
            abort(401)
        return f(*args, **kwargs)
    return decorated

@app.route("/invoices", methods=["POST"])
@login_required
def create_invoice():
    ...

@app.route("/invoices", methods=["GET"])
@login_required
def list_invoices():
    ...

@app.route("/pay/<int:invoice_id>", methods=["POST"])
@login_required
def mark_invoice_paid(invoice_id):
    ...
```

## Finding 3: IDOR — No Object-Level Authorization on Pay Endpoint

**Finding ID:** `APPSEC-f1a83e7c24`  
**File:** `main.py`  
**Lines:** 56–63  
**CWE:** CWE-862 — Missing Authorization  
**OWASP Category:** A01:2021 – Broken Access Control  
**Priority:** P2  
**Severity:** HIGH  
**Confidence:** HIGH  

### Vulnerable Code
```python
@app.route("/pay/<int:invoice_id>", methods=["POST"])
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.get_or_404(invoice_id)

    # Imagine some proper payment logic here ...
    invoice.paid = True
    db.session.commit()
    return jsonify({"message": f"Invoice {invoice_id} marked as paid."})
```

### Description
The handler fetches the invoice by its integer ID taken directly from the URL path and marks it paid without verifying that the authenticated caller owns or is authorized to act on that invoice. In a multi-tenant deployment, any authenticated user who can guess or enumerate a sequential integer ID can mark any other tenant's invoice as paid — potentially clearing legitimate outstanding debt or triggering false business-logic completion. Invoice IDs are sequential integers (SQLite auto-increment), making enumeration trivial (`/pay/1`, `/pay/2`, …).

Attacker payload: `POST /pay/42` marks invoice 42 paid regardless of which tenant created it.

### Prioritization
P2 — Depends on authentication existing (Finding 2). Remediate after auth is in place. If authentication is added without this fix, this IDOR becomes immediately exploitable by any authenticated user against any other user's invoice.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must be authenticated (or authentication must be absent, as in the current state). Invoice IDs are auto-increment integers, trivially guessable.
- **Uncertainty Boundary:** If invoices are filtered by user at a layer not visible in scope, impact is reduced — but there is no visible ownership filter in this code.

### Counterfactual Invalidation
Adding an ownership check `if invoice.user_id != current_user.id: abort(403)` after the fetch would invalidate this finding.

### Remediation
After implementing authentication, enforce object-level ownership before acting:

```python
@app.route("/pay/<int:invoice_id>", methods=["POST"])
@login_required
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.filter_by(id=invoice_id, user_id=current_user.id).first_or_404()
    invoice.paid = True
    db.session.commit()
    return jsonify({"message": f"Invoice {invoice_id} marked as paid."})
```

Filtering by both `id` and `user_id` in the query itself prevents any row from being accessed unless it belongs to the caller.

### References
- https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/
- https://cwe.mitre.org/data/definitions/862.html

## Finding 4: Sensitive Data Exposure — All Invoices Returned Without Tenant Scoping

**Finding ID:** `APPSEC-9e6d2b3f78`  
**File:** `main.py`  
**Lines:** 51–54  
**CWE:** CWE-284 — Improper Access Control  
**OWASP Category:** A01:2021 – Broken Access Control  
**Priority:** P2  
**Severity:** MEDIUM  
**Confidence:** HIGH  

### Vulnerable Code
```python
@app.route("/invoices", methods=["GET"])
def list_invoices():
    invoices = Invoice.query.all()
    return jsonify([i.to_dict() for i in invoices])
```

### Description
`Invoice.query.all()` returns every row in the table with no filtering by user, tenant, or any other scope. The `to_dict()` method (lines 20–29) serializes `customer_name`, `billing_address`, and `vat_id` — all PII. Any caller (currently unauthenticated) receives the full invoice ledger for every customer, creating a data breach scenario where one user can harvest the personal and financial details of all other users.

### Prioritization
P2 — Depends on authentication (Finding 2). Once auth exists, this query must be scoped to the current user's records; without scoping it becomes a horizontal privilege escalation at the data layer.

### Exploitability Notes
- **Exploit Preconditions:** Network access to `GET /invoices`. Currently unauthenticated.
- **Uncertainty Boundary:** If an upstream layer pre-filters results or enforces tenant context, impact is reduced. None visible in scope.

### Counterfactual Invalidation
Filtering the query by `user_id=current_user.id` would prevent cross-tenant data access.

### Remediation
```python
@app.route("/invoices", methods=["GET"])
@login_required
def list_invoices():
    invoices = Invoice.query.filter_by(user_id=current_user.id).all()
    return jsonify([i.to_dict() for i in invoices])
```

## Finding 5: CSRF — State-Changing Pay Endpoint Lacks CSRF Protection

**Finding ID:** `APPSEC-4c7a8e1d62`  
**File:** `main.py`  
**Lines:** 56–63  
**CWE:** CWE-352 — Cross-Site Request Forgery  
**OWASP Category:** A01:2021 – Broken Access Control  
**Priority:** P3  
**Severity:** MEDIUM  
**Confidence:** MEDIUM  

### Vulnerable Code
```python
@app.route("/pay/<int:invoice_id>", methods=["POST"])
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.get_or_404(invoice_id)
    invoice.paid = True
```

### Description
`POST /pay/<id>` accepts a body-less POST request and performs a state-changing operation (marking an invoice paid). The `POST /invoices` endpoint requires `Content-Type: application/json`, which browsers treat as a non-simple request requiring a CORS pre-flight — providing implicit CSRF protection. However, the pay endpoint requires no request body or specific content type, meaning a cross-origin HTML form submission (`<form method="POST" action="/pay/42">`) will be sent directly by the browser including session cookies, with no pre-flight. If cookie-based authentication is added, any malicious page visited by a logged-in user can silently mark invoices as paid.

### Prioritization
P3 — Contingent on cookie-based authentication being introduced (Findings 2, 3 take priority). Flag now so CSRF protection is included in any auth implementation.

### Exploitability Notes
- **Exploit Preconditions:** Cookie-based session authentication must be in place; victim must visit attacker-controlled page while logged in; victim must have an invoice with a known ID.
- **Uncertainty Boundary:** If auth is implemented with Bearer tokens (Authorization header) rather than cookies, CSRF is not exploitable via browser-initiated cross-origin requests.

### Counterfactual Invalidation
Adding Flask-WTF CSRF protection or requiring a `Content-Type: application/json` body on this endpoint would prevent form-based CSRF.

### Remediation
Use Flask-WTF's CSRF extension to protect all state-changing endpoints:

```python
from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)
```

Or, restructure the pay endpoint to require a JSON body (forcing a CORS pre-flight for cross-origin requests):

```python
@app.route("/pay/<int:invoice_id>", methods=["POST"])
@login_required
def mark_invoice_paid(invoice_id):
    # Require JSON body; browser cross-origin form POSTs cannot set Content-Type: application/json
    if not request.is_json:
        abort(400)
    ...
```

### References
- https://owasp.org/www-community/attacks/csrf
- https://cwe.mitre.org/data/definitions/352.html

## Finding 6: Security Misconfiguration — `FLASK_ENV=development` in Production Deployment

**Finding ID:** `APPSEC-7b5f3d9a01`  
**File:** `docker-compose.yml`  
**Lines:** 8–9  
**CWE:** CWE-16 — Configuration  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P3  
**Severity:** LOW  
**Confidence:** MEDIUM  

### Vulnerable Code
```yaml
environment:
  - FLASK_ENV=development
```

### Description
The Docker Compose deployment configuration sets `FLASK_ENV=development`. In Flask versions prior to 2.2 this variable automatically enabled the Werkzeug interactive debugger (which provides a PIN-protected but dangerous RCE console on unhandled exceptions). In Flask 2.3.x (used here) `FLASK_ENV` was deprecated in favour of `FLASK_DEBUG`, and `app.run(debug=False)` on line 69 of `main.py` overrides any implicit debug enablement — so the Werkzeug debugger is likely not active. The risk is twofold: (1) future Flask upgrades or environment changes could restore the implicit debug-mode behaviour; (2) the variable creates confusion about the intended deployment environment, potentially leading operators to apply development-grade hardening assumptions to a production container.

### Prioritization
P3 informational; lower impact than Findings 1–5.

### Exploitability Notes
- **Exploit Preconditions:** Behaviour change would require either a Flask downgrade or removal of the `debug=False` argument.
- **Uncertainty Boundary:** Exact Flask 2.3.x handling of `FLASK_ENV` may vary by patch version.

### Remediation
Remove the `FLASK_ENV` variable from the production compose file and replace with an explicit, safe configuration:

```yaml
environment:
  - FLASK_DEBUG=0
```

And ensure `app.run()` in `main.py` does not set `debug=True` in production:
```python
app.run(host="0.0.0.0", port=5000, debug=False)
```

### References
- https://flask.palletsprojects.com/en/2.3.x/config/#DEBUG
- https://owasp.org/Top10/A05_2021-Security_Misconfiguration/
