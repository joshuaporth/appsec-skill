## Finding 1: Missing Authentication and Authorization (IDOR)

**File:** `main.py`
**Lines:** 51–54, 56–63
**CWE:** CWE-862 — Missing Authorization
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route("/invoices", methods=["GET"])
def list_invoices():
    invoices = Invoice.query.all()
    return jsonify([i.to_dict() for i in invoices])

@app.route("/pay/<int:invoice_id>", methods=["POST"])
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.get_or_404(invoice_id)
    invoice.paid = True
    db.session.commit()
    return jsonify({"message": f"Invoice {invoice_id} marked as paid."})
```

### Description
No authentication or authorization check exists on any route. `GET /invoices` returns every invoice in the database — every customer name, billing address, and VAT ID — to any caller. `POST /pay/<invoice_id>` marks any invoice as paid without verifying the caller owns it; sequential enumeration of integer IDs (1, 2, 3…) is trivially sufficient. An unauthenticated attacker can exfiltrate the full customer PII dataset and mark arbitrary invoices paid, directly subverting financial integrity.

### Prioritization
Top remediation priority. All other findings are secondary; some become moot or materially worse once authentication is added. The absence of access control is the dominant threat in this codebase.

### Exploitability Notes
- **Exploit Preconditions:** None — any HTTP client suffices. `curl http://host/invoices` dumps all records; `curl -X POST http://host/pay/1` marks invoice #1 paid.
- **Uncertainty Boundary:** None. Code is unambiguous.
- **Counterfactual invalidation:** Adding `@login_required` plus filtering `Invoice.query.filter_by(user_id=current_user.id)` eliminates both the data-exposure and IDOR paths.

### Remediation
```python
# requirements.txt: add Flask-Login
from flask_login import LoginManager, login_required, current_user

login_manager = LoginManager(app)

# Invoice model: add ownership column
class Invoice(db.Model):
    # ... existing fields ...
    user_id = db.Column(db.Integer, db.ForeignKey("user.id"), nullable=False)

@app.route("/invoices", methods=["GET"])
@login_required
def list_invoices():
    invoices = Invoice.query.filter_by(user_id=current_user.id).all()
    return jsonify([i.to_dict() for i in invoices])

@app.route("/pay/<int:invoice_id>", methods=["POST"])
@login_required
def mark_invoice_paid(invoice_id):
    # filter_by enforces ownership — returns 404 if invoice belongs to another user
    invoice = Invoice.query.filter_by(
        id=invoice_id, user_id=current_user.id
    ).first_or_404()
    invoice.paid = True
    db.session.commit()
    return jsonify({"message": f"Invoice {invoice_id} marked as paid."})
```

## Finding 2: Mass Assignment — `paid` Flag Writable by Client

**File:** `main.py`
**Lines:** 39–49
**CWE:** CWE-915 — Improperly Controlled Modification of Dynamically-Determined Object Attributes
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route("/invoices", methods=["POST"])
def create_invoice():
    data = request.json or {}

    # Amount is server-controlled (e.g., from the authenticated user's plan/contract)
    data["amount"] = get_amount_for_current_user()
    invoice = Invoice(**data)   # all keys in data, including 'paid', bound to model

    db.session.add(invoice)
    db.session.commit()
    return jsonify(invoice.to_dict()), 201
```

### Description
`Invoice(**data)` passes every key from the attacker-controlled JSON body to the SQLAlchemy model constructor. `amount` is explicitly overwritten server-side on the line above, protecting it. `paid` is not overwritten; its model default (`False`) is never enforced when the client supplies a value. An attacker can POST `{"paid": true}` and create an invoice that enters the database already marked as paid — bypassing the payment flow (with its "proper payment logic" comment) entirely. The concrete payload is one line: `{"customer_name": "any", "paid": true}`.

### Prioritization
P1 alongside Finding 1. This is independently exploitable (no auth required) and directly subverts financial integrity. Remediating Finding 1 (auth) does not fix this; both must be patched.

### Exploitability Notes
- **Exploit Preconditions:** The `POST /invoices` endpoint must be reachable. It currently is, with no auth.
- **Concrete attacker input:** `curl -X POST http://host/invoices -H 'Content-Type: application/json' -d '{"customer_name":"acme","paid":true}'` → creates invoice with `paid=True` in DB.
- **Uncertainty Boundary:** None — `paid` is a plain model column, not write-protected anywhere.
- **Counterfactual invalidation:** Filtering `data` to an explicit allowlist that excludes `paid` eliminates the path.

### Remediation
```python
INVOICE_WRITABLE_FIELDS = {"customer_name", "billing_address", "vat_id", "description"}

@app.route("/invoices", methods=["POST"])
def create_invoice():
    raw = request.json or {}

    # Explicit allowlist — client cannot touch 'paid', 'amount', or any future field
    data = {k: v for k, v in raw.items() if k in INVOICE_WRITABLE_FIELDS}

    # Server-controlled fields
    data["amount"] = get_amount_for_current_user()
    # 'paid' intentionally absent — model default (False) applies

    invoice = Invoice(**data)
    db.session.add(invoice)
    db.session.commit()
    return jsonify(invoice.to_dict()), 201
```

## Finding 3: CSRF — `POST /pay/<id>` Accepts Form Submissions

**File:** `main.py`, `templates/index.html`
**Lines:** `main.py` 56–63; `index.html` 33–36
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM (escalates to HIGH once authentication is added)
**Confidence:** HIGH

### Vulnerable Code
```python
# main.py — no CSRF token check
@app.route("/pay/<int:invoice_id>", methods=["POST"])
def mark_invoice_paid(invoice_id):
    invoice = Invoice.query.get_or_404(invoice_id)
    invoice.paid = True
    db.session.commit()
    return jsonify({"message": f"Invoice {invoice_id} marked as paid."})
```
```javascript
// index.html — no CSRF token sent
async function pay(id) {
  await fetch(`/pay/${id}`, { method: "POST" });
  load();
}
```

### Description
`POST /pay/<id>` carries no CSRF token and requires no request body. An attacker can embed a hidden HTML form on any page that auto-submits to `http://target/pay/42` — browsers will attach the victim's session cookie automatically. Because this endpoint takes no body, it is not protected by the browser's pre-flight CORS check (only non-simple content types trigger pre-flight). Once authentication is implemented, any authenticated user who visits a malicious page will silently mark the attacker-chosen invoice as paid. The `POST /invoices` JSON endpoint is less immediately exploitable via classic CSRF (browser blocks cross-origin `application/json` without a permissive CORS policy), but adding CORS later would re-open it.

### Prioritization
P2 — exploitable only after authentication exists, but that remediation is P1 and should happen soon. CSRF protection must be added as part of the same development sprint.

### Exploitability Notes
- **Exploit Preconditions:** Authentication must be in place and victim must visit attacker's page while logged in.
- **Concrete attacker page:** `<form action="http://target/pay/1" method="POST"><script>document.forms[0].submit()</script></form>`
- **Uncertainty Boundary:** Default browser `SameSite=Lax` cookie policy blocks cross-site POST for cookies set without an explicit `SameSite` attribute — but Flask does not set `SameSite` on session cookies by default, so the mitigation is browser-version-dependent and should not be relied upon.
- **Counterfactual invalidation:** Adding Flask-WTF CSRF protection with a valid token requirement eliminates the attack.

### Remediation
```python
# main.py
from flask_wtf.csrf import CSRFProtect, generate_csrf

csrf = CSRFProtect(app)
app.config["SECRET_KEY"] = os.environ["SECRET_KEY"]  # required for CSRF tokens

# Expose token for JS fetch calls
@app.route("/csrf-token")
def csrf_token():
    return jsonify({"token": generate_csrf()})
```
```javascript
// index.html — fetch CSRF token once and attach to state-changing requests
let csrfToken = "";

async function initCsrf() {
  const data = await (await fetch("/csrf-token")).json();
  csrfToken = data.token;
}

async function pay(id) {
  await fetch(`/pay/${id}`, {
    method: "POST",
    headers: { "X-CSRFToken": csrfToken }
  });
  load();
}
```

Also add to `app.config`: `SESSION_COOKIE_SAMESITE = "Lax"` and `SESSION_COOKIE_SECURE = True` (in production) for defense-in-depth.

### References
- https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/352.html

## Finding 4: Container Runs as Root

**File:** `Dockerfile`
**Lines:** 1–10
**CWE:** CWE-250 — Execution with Unnecessary Privileges
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```dockerfile
FROM python:3.11-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "main.py"]
```

### Description
No `USER` directive is present. The Flask process runs as UID 0 (root) inside the container. If any vulnerability in the application yields code execution (e.g., via a future injection flaw), the attacker gains root within the container, significantly lowering the bar for container escape or host-namespace attacks depending on runtime configuration.

### Prioritization
P3 — defense-in-depth measure; requires a prior RCE to matter. Address after the access-control findings.

### Exploitability Notes
- **Exploit Preconditions:** Application must first be compromised via a code-execution vulnerability.
- **Uncertainty Boundary:** Impact depends on container runtime hardening (`seccomp`, `AppArmor`, `--privileged` flags), none of which are visible in scope.
- **Counterfactual invalidation:** Adding a `USER` directive dropping to a non-root UID removes root privileges from the process.

### Remediation
```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd -m -u 1000 appuser && chown -R appuser:appuser /app
USER appuser

CMD ["python", "main.py"]
```

### References
- https://docs.docker.com/develop/security-best-practices/
- https://cwe.mitre.org/data/definitions/250.html

## Finding 5: `FLASK_ENV=development` in Production Compose File

**File:** `docker-compose.yml`
**Lines:** 8–9
**CWE:** CWE-215 — Insertion of Sensitive Information Into Debugging Code
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P4
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```yaml
environment:
  - FLASK_ENV=development
```

### Description
The compose file declares `FLASK_ENV=development` while `main.py:69` explicitly passes `debug=False`. These are inconsistent. `FLASK_ENV=development` enables Flask's reloader and can activate development-mode behaviors in Flask extensions (e.g., verbose error pages if `debug` is ever removed from `app.run()`). A developer who removes the explicit `debug=False` in the future — believing the environment variable controls it — would silently re-enable the interactive debugger, which provides an authenticated Python REPL on `/console`.

### Prioritization
P4 — no current exploitability; risk is future regression. Fix during the same sprint as the other findings.

### Exploitability Notes
- **Exploit Preconditions:** A future code change removes `debug=False` from `app.run()`.
- **Uncertainty Boundary:** Current code is not exploitable; risk is latent.
- **Counterfactual invalidation:** Setting `FLASK_ENV=production` eliminates the inconsistency.

### Remediation
```yaml
# docker-compose.yml
environment:
  - FLASK_ENV=production
  - SECRET_KEY=${SECRET_KEY}   # inject via .env or secrets manager — never hardcode
```

### References
- https://flask.palletsprojects.com/en/2.3.x/config/#environment-and-debug-features
