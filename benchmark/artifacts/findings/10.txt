## Finding 1: JWT Authentication Bypass — Signature Never Verified

**Finding ID:** `APPSEC-c7f3a1b8e2`
**File:** `main.js`
**Lines:** 16–17
**CWE:** CWE-347 — Improper Verification of Cryptographic Signature
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
const decoded = jwt.decode(token, { complete: true });
req.decoded = decoded.payload;
```

### Description
`jwt.decode()` base64-decodes the token payload without ever touching the signature. It is explicitly documented in the `jsonwebtoken` library as "not checking the signature." This means any caller can craft a token with `{"username":"admin"}` in the payload, sign it with a random secret (or use `alg: none`), and the `verifyToken` middleware will accept it unconditionally. The subsequent `username === 'admin'` check at line 24 is then trivially bypassed, granting full admin access to any unauthenticated caller. The `secretKey` loaded from the environment has zero effect on this flow.

### Prioritization
This is the primary finding and must be remediated first. It is a one-HTTP-request exploit requiring no privileges, no account, and no brute-force.

### Exploitability Notes
- **Exploit Preconditions:** None. Any attacker can send a request to `GET /admin` with a self-signed or unsigned JWT containing `{"username":"admin"}`.
  Concrete payload: `Authorization: eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VybmFtZSI6ImFkbWluIn0.`
- **Uncertainty Boundary:** None that changes the outcome — `jwt.decode()` never verifies under any configuration.

### Remediation
Replace `jwt.decode()` with `jwt.verify()`, which validates the signature and all registered claims (including `exp`):

```javascript
// Before (BROKEN — no signature validation)
const decoded = jwt.decode(token, { complete: true });
req.decoded = decoded.payload;

// After — throws JsonWebTokenError on bad signature or expired token
try {
  const decoded = jwt.verify(token, secretKey);
  req.decoded = decoded;
  next();
} catch (err) {
  return res.status(401).json({ message: 'Invalid or expired token' });
}
```

The `try/catch` is required because `jwt.verify()` throws on failure rather than returning `null`.

- https://cwe.mitre.org/data/definitions/347.html
- https://github.com/auth0/node-jsonwebtoken#jwtdecodedtoken-options

## Finding 2: Unhandled Null Dereference on Malformed Token Input

**Finding ID:** `APPSEC-9a4d2f7c03`
**File:** `main.js`
**Lines:** 16–18
**CWE:** CWE-476 — NULL Pointer Dereference / CWE-209 — Information Exposure Through Error Message
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
const decoded = jwt.decode(token, { complete: true });
req.decoded = decoded.payload;

next();
```

### Description
`jwt.decode()` returns `null` when given a value that cannot be parsed as a JWT. Because the code reads `decoded.payload` on the next line without a null guard, a malformed `Authorization` header (e.g., `Authorization: notaJWT`) causes an uncaught `TypeError: Cannot read properties of null (reading 'payload')`. Express will catch this and return an HTTP 500. In development mode (`NODE_ENV=development`) Express includes the full stack trace in the response body, disclosing internal paths and library versions. Even without the stack trace, a 500 instead of a 401 is an exploitable oracle distinguishing "malformed input" from "missing token."

### Prioritization
Secondary to Finding 1. Remediation of Finding 1 (using `jwt.verify()` inside a `try/catch`) eliminates this issue simultaneously, since the `catch` block handles all failure modes.

### Exploitability Notes
- **Exploit Preconditions:** Attacker sends any non-JWT value as the `Authorization` header.
  Concrete input: `Authorization: garbage`
- **Uncertainty Boundary:** Stack trace disclosure depends on `NODE_ENV`; 500 oracle is present regardless.

### Remediation
The `try/catch` shown in Finding 1's remediation handles this entirely — `jwt.verify()` throws a typed error for all failure modes and the `catch` returns a clean 401.

### References
- https://cwe.mitre.org/data/definitions/476.html
- https://cwe.mitre.org/data/definitions/209.html

## Finding 3: JWT Expiration Not Enforced

**Finding ID:** `APPSEC-b1e8d3f265`
**File:** `main.js`
**Lines:** 16
**CWE:** CWE-613 — Insufficient Session Expiration
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
const decoded = jwt.decode(token, { complete: true });
```

### Description
Tokens are generated with `expiresIn: '1h'` at line 34, embedding an `exp` claim. However, `jwt.decode()` decodes the payload without evaluating any claims, so the `exp` field is silently ignored. A token that has been expired for days, months, or years is accepted as valid. Combined with Finding 1, this means a once-leaked or once-valid token becomes an eternal credential with no revocation path.

### Prioritization
Shares the same root cause as Finding 1. `jwt.verify()` enforces `exp` automatically, so both findings are resolved by the same single-line change.

### Exploitability Notes
- **Exploit Preconditions:** Attacker possesses any previously-issued token, regardless of age.
- **Uncertainty Boundary:** None — `exp` enforcement is purely absent at the code level.

### Remediation
`jwt.verify()` (see Finding 1) automatically rejects tokens whose `exp` has passed, throwing `TokenExpiredError`.

### References
- https://cwe.mitre.org/data/definitions/613.html
- https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.4

## Finding 4: `secretKey` Undefined When `JWT_SECRET` Not Set

**Finding ID:** `APPSEC-2c9fe0a174`
**File:** `main.js`
**Lines:** 7, 34
**CWE:** CWE-798 — Use of Hard-coded Credentials (variant: absent/undefined key)
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** HIGH
**Confidence:** MEDIUM

### Vulnerable Code
```javascript
const secretKey = process.env.JWT_SECRET;;

// later...
const token = jwt.sign(payload, secretKey, { expiresIn: '1h' });
```

### Description
If `JWT_SECRET` is not set in the environment, `secretKey` is `undefined`. Depending on the `jsonwebtoken` version, `jwt.sign(payload, undefined, ...)` may throw at startup (failing loudly) or, in some older versions, produce a token signed with an empty/null secret. An empty secret is equivalent to a publicly known secret, meaning any party can forge tokens signed under it. There is no startup guard ensuring the key is present and has sufficient entropy before the server begins accepting requests. The double semicolon `;;` on line 7 is harmless but suggests the line was edited carelessly.

### Prioritization
Lower operational priority since Finding 1 renders the secret irrelevant today. However, once Finding 1 is fixed, a missing or weak `JWT_SECRET` becomes the remaining attack surface.

### Exploitability Notes
- **Exploit Preconditions:** `JWT_SECRET` environment variable is unset or empty at server start.
- **Uncertainty Boundary:** Actual behavior depends on the exact `jsonwebtoken` version installed — newer versions throw, older versions may silently accept.

### Remediation
```javascript
const secretKey = process.env.JWT_SECRET;
if (!secretKey || secretKey.length < 32) {
  console.error('FATAL: JWT_SECRET must be set to at least 32 characters');
  process.exit(1);
}
```

Use a randomly generated secret of at least 256 bits (32 bytes): `node -e "require('crypto').randomBytes(32).toString('hex')|0"` and store it in a secrets manager, not in a `.env` file committed to version control.

### References
- https://cwe.mitre.org/data/definitions/798.html
- https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_for_Java_Cheat_Sheet.html

## Finding 5: Missing Security Headers

**Finding ID:** `APPSEC-d4710e82ab`
**File:** `main.js`
**Lines:** 5–6
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
const app = express();
// no helmet() call
```

### Description
No `helmet` middleware is registered. Express by default sends `X-Powered-By: Express` (fingerprinting) and omits `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy`. While this JSON API has limited XSS/clickjacking surface today, the absence of `X-Powered-By` removal is an immediate and trivially fixed information leak.

### Prioritization
Lowest priority — does not change exploitability of any of the above findings; purely hardening.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can read response headers to fingerprint the stack.
- **Uncertainty Boundary:** Impact depends on whether the API serves HTML or is consumed by browsers.

### Remediation
```javascript
const helmet = require('helmet');
app.use(helmet());
```

### References
- https://helmetjs.github.io/
- https://owasp.org/www-project-secure-headers/
