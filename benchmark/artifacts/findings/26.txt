## Finding 1: Prototype Pollution via Unsafe `merge()` → Admin Privilege Escalation

**Finding ID:** `APPSEC-a3f2c91b4e`
**File:** `main.js`
**Lines:** 14–18, 33
**CWE:** CWE-1321 — Improperly Controlled Modification of Object Prototype Attributes ('Prototype Pollution')
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
function merge(target, source) {
    for (let key in source) {
        target[key] = source[key];
    }
}
// ...
merge(user, req.body);
```

### Description
The `merge()` function iterates all enumerable keys of `source` using `for...in` without filtering the dangerous `__proto__` key. When `body-parser` v1.20.3 parses `{"__proto__": {"isAdmin": true}}`, it creates an object where `"__proto__"` exists as an own enumerable data property (via `[[DefineOwnProperty]]`, bypassing the setter). The loop then executes `target["__proto__"] = source["__proto__"]`, which invokes the `Object.prototype.__proto__` setter and calls `Object.setPrototypeOf(user, {isAdmin: true})`. After this, `user.isAdmin` resolves to `true` via prototype chain traversal, bypassing the admin gate at line 40 (`user && user.isAdmin`). A guest-level authenticated user achieves full admin access in three unauthenticated-to-admin steps.

### Prioritization
Highest priority. Direct, unauthenticated-to-admin exploit with no preconditions beyond obtaining a guest cookie (which requires only one additional POST). All other findings are secondary to this.

### Exploitability Notes
- **Exploit Preconditions:** Attacker first calls `POST /guest-login` to receive the `username=guest` cookie. Then calls `POST /update-profile` with body `{"__proto__": {"isAdmin": true}}`. Then calls `GET /admin`.
- **Uncertainty Boundary:** None relevant — body-parser 1.20.3 (locked) parses `__proto__` as an own data property in V8/Node.js 18; the setter path is unconditional.

**Counterfactual invalidation:** Adding `if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;` inside `merge()` would prevent the prototype write.

### Remediation
```javascript
// Option A — Safe merge with explicit prototype-key guard
function merge(target, source) {
    for (let key of Object.keys(source)) {  // own keys only, no inherited
        if (key === '__proto__' || key === 'constructor' || key === 'prototype') continue;
        target[key] = source[key];
    }
}

// Option B (preferred) — allowlist only the fields the endpoint should accept
app.post("/update-profile", (req, res) => {
    let username = req.cookies.username;
    if (!username || !users[username]) {
        return res.status(401).json({ error: "Unauthorized" });
    }
    const ALLOWED = ['profile'];  // explicit allowlist
    const user = users[username];
    for (const key of ALLOWED) {
        if (Object.prototype.hasOwnProperty.call(req.body, key)) {
            user[key] = req.body[key];
        }
    }
    res.json({ message: "Profile updated", user });
});
```
The allowlist approach is strongly preferred because it eliminates mass assignment simultaneously and makes the security boundary explicit.

## Finding 2: Mass Assignment — All User Fields Writable by Client

**Finding ID:** `APPSEC-7d8e3a2f1c`
**File:** `main.js`
**Lines:** 26–36
**CWE:** CWE-915 — Improperly Controlled Modification of Dynamically-Determined Object Attributes
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post("/update-profile", (req, res) => {
    let username = req.cookies.username;
    if (!username || !users[username]) {
        return res.status(401).json({ error: "Unauthorized" });
    }

    let user = users[username];
    merge(user, req.body);

    res.json({ message: "Profile updated", user });
});
```

### Description
`merge(user, req.body)` copies every key from the attacker-controlled JSON body onto the user object without an allowlist. Beyond the prototype pollution path (Finding 1), this allows an attacker to overwrite security-relevant fields such as `password` directly: `{"password": "attacker_controlled"}`. If `isAdmin` were stored as an own property on a user object rather than inherited via prototype, `{"isAdmin": true}` would also directly elevate privilege without needing prototype pollution. The response also echoes the entire `user` object back, disclosing `password` to the caller on every update.

### Prioritization
P2, secondary to Finding 1. The allowlist fix for Finding 1 resolves this simultaneously, but the field-disclosure-in-response is an independent secondary concern.

### Exploitability Notes
- **Exploit Preconditions:** Valid `username` cookie (obtained via `POST /guest-login`).
- **Uncertainty Boundary:** In this in-memory mock the impact is scoped to the running process; in a persisted store (database, session) it would be permanent.

**Counterfactual invalidation:** Using an explicit field allowlist (`['profile']`) and never passing `req.body` directly to any merge/assign removes this class entirely.

### Remediation
Use the allowlist-only pattern shown in Finding 1, Option B. Additionally, remove `user` from the response or redact sensitive fields:

```javascript
res.json({ message: "Profile updated", profile: user.profile });
```

## Finding 3: Plaintext Password Storage

**Finding ID:** `APPSEC-2c4f1a8b6d`
**File:** `main.js`
**Lines:** 10–12
**CWE:** CWE-256 — Plaintext Storage of a Password
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
let users = {
    guest: { password: "guest", profile: "My cool profile" }
};
```

### Description
The password is stored as a plaintext string. If this pattern were carried forward into a real persistence layer (database, Redis, file), a single read of the store would expose all credentials. Additionally, password comparison is done via identity (`users[username]` lookup by cookie name, not by password check), but the presence of plaintext passwords on the object means mass-assignment exploitation (Finding 2) discloses them in every `/update-profile` response. The code comment "Assume that this is a fully-grown database" implies this pattern is meant to represent real auth logic.

### Prioritization
P2. High severity as a pattern, but practical exploitability is lower in this specific in-memory mock. Must not be replicated in real persistence.

### Exploitability Notes
- **Exploit Preconditions:** Ability to read the `users` data structure (via mass-assignment response disclosure in Finding 2, or direct store access).
- **Uncertainty Boundary:** Impact is process-local in current code; severity rises to critical if applied to a real database.

**Counterfactual invalidation:** Hashing passwords with `bcrypt` at write time and comparing with `bcrypt.compare()` at login eliminates plaintext storage entirely.

### Remediation
```javascript
const bcrypt = require('bcrypt');
const SALT_ROUNDS = 12;

// At registration / seed:
const hashedPassword = await bcrypt.hash("guest", SALT_ROUNDS);
let users = {
    guest: { passwordHash: hashedPassword, profile: "My cool profile" }
};

// At login:
const valid = await bcrypt.compare(suppliedPassword, users[username].passwordHash);
if (!valid) return res.status(401).json({ error: "Invalid credentials" });
```

## Finding 4: Session Cookie Missing `sameSite` and `secure` Attributes

**Finding ID:** `APPSEC-9b5e7d3a2f`
**File:** `main.js`
**Lines:** 22
**CWE:** CWE-1275 — Sensitive Cookie with Improper SameSite Attribute / CWE-614 — Sensitive Cookie in HTTPS Session Without 'Secure' Attribute
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
res.cookie("username", "guest", { httpOnly: true });
```

### Description
The session cookie is set with `httpOnly: true` (correct) but is missing `sameSite` and `secure` attributes. Without `sameSite: "lax"` or `"strict"`, the browser sends this cookie on cross-site navigational requests, enabling CSRF attacks. While `bodyParser.json()` requiring `Content-Type: application/json` raises the bar (cross-origin non-simple requests trigger CORS preflight, which fails on this server), it does not eliminate CSRF — an attacker controlling a same-site origin or using browser quirks can still forge state-changing requests. Without `secure: true`, the cookie is transmitted over plain HTTP connections, exposing it to network interception.

### Prioritization
P3. CSRF exploitability is constrained by the JSON content-type requirement and lack of CORS headers, but the missing `sameSite` and `secure` flags are unambiguous hardening gaps.

### Exploitability Notes
- **Exploit Preconditions:** Network attacker (for `secure` issue) or same-site origin controlled by attacker (for `sameSite` issue).
- **Uncertainty Boundary:** CSRF via cross-origin JSON POST is browser/version-dependent due to content-type preflight behavior.

**Counterfactual invalidation:** Adding `sameSite: "strict"` would prevent cross-site cookie attachment; adding `secure: true` prevents HTTP transmission.

### Remediation
```javascript
res.cookie("username", "guest", {
    httpOnly: true,
    sameSite: "strict",   // prevent cross-site requests carrying this cookie
    secure: true,          // HTTPS only
    // Consider adding: maxAge: 3600000 (1h session expiry)
});
```

### References
- https://owasp.org/www-community/SameSite
- https://cwe.mitre.org/data/definitions/1275.html

## Finding 5: `NODE_ENV=development` in Deployment Configuration

**Finding ID:** `APPSEC-4e1a7c2b8f`
**File:** `docker-compose.yml`
**Lines:** 9
**CWE:** CWE-489 — Active Debug Code
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```yaml
environment:
  - NODE_ENV=development
```

### Description
Setting `NODE_ENV=development` in a containerized deployment activates Express's development behavior: full stack traces are included in error responses sent to clients, verbose error messages are returned, and some framework-level security hardening is not applied. An attacker receiving a 500-level error with a stack trace gains internal path disclosure, version information, and code logic hints that accelerate further exploitation.

### Prioritization
P3. Impact is informational amplification; fix requires a one-line change.

### Exploitability Notes
- **Exploit Preconditions:** Any request that triggers an unhandled exception in the app.
- **Uncertainty Boundary:** Exact stack-trace behavior depends on Express version and error handler configuration, but the safe default is always `NODE_ENV=production`.

**Counterfactual invalidation:** Setting `NODE_ENV=production` causes Express to omit stack traces from error responses.

### Remediation
```yaml
environment:
  - NODE_ENV=production
```

### References
- https://expressjs.com/en/advanced/best-practice-security.html
- https://cwe.mitre.org/data/definitions/489.html

## Finding 6: Missing Security Headers (No `helmet` Middleware)

**Finding ID:** `APPSEC-b2d9f17e3a`
**File:** `main.js`
**Lines:** 1–7
**CWE:** CWE-16 — Configuration
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** INFO
**Confidence:** HIGH

### Vulnerable Code
```javascript
const app = express();
app.use(bodyParser.json());
app.use(cookieParser());
// No helmet() or manual security header configuration
```

### Description
No security headers are set. Absent headers include `Content-Security-Policy` (enables XSS mitigation), `X-Frame-Options` / `frame-ancestors` (prevents clickjacking), `X-Content-Type-Options: nosniff` (prevents MIME sniffing), and `Strict-Transport-Security` (enforces HTTPS). While none of these independently represents a high-severity vulnerability in the current codebase, their absence is a defense-in-depth gap and a baseline hardening failure.

### Prioritization
P3/INFO. Background hardening; does not expose direct exploit paths given current code.

### Exploitability Notes
- **Exploit Preconditions:** Relevant only if additional vulnerabilities (XSS, framing) are introduced.
- **Uncertainty Boundary:** Impact depends on the presence of HTML responses carrying user-influenced content.

### Remediation
```javascript
const helmet = require('helmet');
app.use(helmet());  // sets CSP, X-Frame-Options, HSTS, X-Content-Type-Options, etc.
```

Install: `npm install helmet`

### References
- https://helmetjs.github.io/
- https://owasp.org/www-project-secure-headers/
