## Finding 1: Code Injection — Remote Code Execution via `eval()`

**Finding ID:** `APPSEC-91ab9416712a`
**File:** `main.js`
**Lines:** 26–35
**CWE:** CWE-94 — Improper Control of Generation of Code ('Code Injection')
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post('/process-data', (req, res) => {
    const { data } = req.body;

    try {
        const result = eval(data); 
        res.send({ result });
    } catch (err) {
        res.status(400).send({ error: 'Invalid data' });
    }
});
```

### Description
`req.body.data` is fully attacker-controlled JSON input that flows directly into `eval()` with no validation, sandboxing, or restriction. `eval()` executes the supplied string as JavaScript in the full Node.js runtime context — the same process and privilege as the server. An unauthenticated attacker (see Finding 2) can read arbitrary files, spawn child processes, exfiltrate environment variables, or pivot to internal network resources by sending a crafted `data` field. The `try/catch` only masks runtime errors; it provides no security boundary.

**Concrete exploit payload:**
```json
POST /process-data
{"data": "require('child_process').execSync('id && cat /etc/passwd').toString()"}
```

### Prioritization
Highest-priority finding. Unauthenticated, zero-precondition RCE. All other findings are secondary.

### Exploitability Notes
- **Exploit Preconditions:** The server must be reachable. No authentication, prior knowledge, or account is required (see Finding 2). Express parses the JSON body automatically.
- **Uncertainty Boundary:** None. The data flow is completely unambiguous — `req.body.data` → `eval(data)` with no intermediate transformation.

**Counterfactual invalidation:** Removing the `eval()` call and replacing it with a safe, allowlisted operation would fully eliminate this finding.

### Remediation
Remove `eval()` entirely. Determine the actual intended computation and implement it with a controlled, explicit operation:

```javascript
// If the intent is to evaluate a simple arithmetic expression:
const ALLOWED_EXPR = /^[0-9+\-*/(). ]+$/;

app.post('/process-data', (req, res) => {
    const { data } = req.body;
    if (typeof data !== 'string' || !ALLOWED_EXPR.test(data)) {
        return res.status(400).send({ error: 'Invalid data' });
    }
    // Use a safe math-only evaluator (e.g., mathjs) — not eval()
    const result = mathjs.evaluate(data);
    res.send({ result });
});
```

If arbitrary expression evaluation is genuinely required, use an isolated sandbox (e.g., `vm2`, `isolated-vm`) — never the main Node.js context — and enforce strict resource limits. In practice, avoid `eval()` on untrusted input entirely.

### References
- https://cwe.mitre.org/data/definitions/94.html
- https://owasp.org/www-community/attacks/Code_Injection

## Finding 2: Missing Authentication for Critical Function

**Finding ID:** `APPSEC-a4d0e4acd3a3`
**File:** `main.js`
**Lines:** 26–35
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post('/process-data', (req, res) => {
    const { data } = req.body;
    // No authentication check before reaching eval()
    try {
        const result = eval(data);
```

### Description
The `/process-data` endpoint — which executes arbitrary JavaScript via `eval()` — performs no authentication check before processing the request. Any HTTP client can reach the code-execution sink without credentials. Additionally, the `/login` endpoint issues no session token on success, meaning there is no authentication credential that downstream endpoints could validate; the auth system has no enforcement mechanism at all. This is an architectural gap that leaves every sensitive endpoint effectively public.

### Prioritization
P2 — directly amplifies the P1 RCE (Finding 1). Would be independently HIGH even if `eval()` were removed, because future sensitive operations added to this endpoint would also be unauthenticated.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 3000. No account required.
- **Uncertainty Boundary:** If a reverse proxy upstream enforces auth, impact would be reduced — but no evidence of one exists in scope.

**Counterfactual invalidation:** Adding a session/token check at the route level and issuing a signed token on login would eliminate this finding.

### Remediation
Issue a signed JWT or opaque session token on successful login and verify it on every sensitive route:

```javascript
const jwt = require('jsonwebtoken');
const JWT_SECRET = process.env.JWT_SECRET; // never hardcode

app.post('/login', (req, res) => {
    const { username, password } = req.body;
    const user = mockDb.users.find(u => u.username === username);
    if (!user || !bcrypt.compareSync(password, user.passwordHash)) {
        return res.status(401).send({ error: 'Invalid credentials' });
    }
    const token = jwt.sign({ username }, JWT_SECRET, { expiresIn: '1h' });
    res.send({ token });
});

function requireAuth(req, res, next) {
    try {
        const token = req.headers.authorization?.split(' ')[1];
        req.user = jwt.verify(token, JWT_SECRET);
        next();
    } catch {
        res.status(401).send({ error: 'Unauthorized' });
    }
}

app.post('/process-data', requireAuth, (req, res) => { ... });
```

### References
- https://cwe.mitre.org/data/definitions/306.html
- https://owasp.org/Top10/A01_2021-Broken_Access_Control/

## Finding 3: Hardcoded Credentials and Plaintext Password Storage

**Finding ID:** `APPSEC-13865c0c9cde`
**File:** `main.js`
**Lines:** 5–10
**CWE:** CWE-798 — Use of Hard-coded Credentials; CWE-256 — Plaintext Storage of a Password
**OWASP Category:** A02:2021 – Cryptographic Failures; A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
const mockDb = {
    users: [
        { username: 'admin', password: 'admin123' },
        { username: 'user1', password: 'password1' },
    ],
};
```

### Description
Passwords are stored in plaintext in source code, creating two compounding weaknesses. First, anyone with repository read access (`git clone`, a leaked diff, or a CI log) immediately has all credentials — no cracking required (CWE-798). Second, because the passwords are stored as cleartext rather than a slow hash, any future data exposure (memory dump, log leak, DB snapshot) exposes all user passwords directly. An attacker obtaining `admin123` can authenticate as `admin` and, given the identical password pattern, likely reuse it across other services.

### Prioritization
P2. Independently HIGH; lower exploitability than the unauthenticated RCE (Finding 1) only because it requires source access rather than a bare HTTP request.

### Exploitability Notes
- **Exploit Preconditions:** Access to the source code repository, or any leak of the in-memory state.
- **Uncertainty Boundary:** The comment "imagine this to be a fully-grown database" implies a real DB would replace this; plaintext storage in that DB would be equally critical.

**Counterfactual invalidation:** Replacing plaintext values with bcrypt hashes and loading credentials from environment variables or a secrets manager would eliminate this finding.

### Remediation
Store only password hashes and load credentials from the environment:

```javascript
const bcrypt = require('bcrypt');

// At provisioning time (not in source):
// const hash = await bcrypt.hash('admin123', 12);

const mockDb = {
    users: [
        { username: 'admin', passwordHash: process.env.ADMIN_PASSWORD_HASH },
        { username: 'user1', passwordHash: process.env.USER1_PASSWORD_HASH },
    ],
};

// In /login:
const user = mockDb.users.find(u => u.username === username);
if (!user || !(await bcrypt.compare(password, user.passwordHash))) {
    return res.status(401).send({ error: 'Invalid credentials' });
}
```

## Finding 4: Observable Timing Discrepancy in Password Comparison

**Finding ID:** `APPSEC-add2e53bc3a9`
**File:** `main.js`
**Lines:** 17
**CWE:** CWE-208 — Observable Timing Discrepancy
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```javascript
const user = mockDb.users.find(u => u.username === username && u.password === password);
```

### Description
JavaScript's `===` operator short-circuits on the first mismatching character, making comparison time proportional to the length of the common prefix. An attacker sending repeated requests can statistically distinguish a "correct username, wrong password" response from a "wrong username" response by measuring response latency. With enough samples, this leaks which usernames are valid and — against short or low-entropy passwords — can narrow the password search space character by character. The per-character timing delta is small over a local network but measurable over many samples with statistical analysis.

### Prioritization
P3. Medium severity; practically harder to exploit over a real network than Findings 1–3, but becomes more relevant if the critical findings are fixed and authentication is tightened.

### Exploitability Notes
- **Exploit Preconditions:** Ability to send many requests and measure response timing (e.g., from a low-latency network position). No account required.
- **Uncertainty Boundary:** Network jitter on real deployments can make byte-level timing attacks impractical, reducing this to username enumeration rather than password brute-force.

**Counterfactual invalidation:** Using a constant-time comparison function (`crypto.timingSafeEqual`) would eliminate this finding.

### Remediation
Always look up the user by username first, then compare using a constant-time function (and a slow hash, per Finding 3):

```javascript
const crypto = require('crypto');

app.post('/login', async (req, res) => {
    const { username, password } = req.body;
    const user = mockDb.users.find(u => u.username === username);

    // Always run the comparison even if user not found (dummy hash prevents timing oracle on username)
    const passwordHash = user?.passwordHash ?? '$2b$12$invalidhashfortimingsafety000000000000000000000';
    const match = user && await bcrypt.compare(password, passwordHash);

    if (match) {
        res.send({ message: 'Login successful!' });
    } else {
        res.status(401).send({ error: 'Invalid credentials' });
    }
});
```

### References
- https://cwe.mitre.org/data/definitions/208.html
- https://codahale.com/a-lesson-in-timing-attacks/
