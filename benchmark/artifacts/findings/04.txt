## Finding 1: Hardcoded Credentials

**Finding ID:** `APPSEC-c3f1a8d204`
**File:** `main.py`
**Lines:** 5–6
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```python
USERNAME = "admin"
PASSWORD = "mypassword"
```

### Description
The application's authentication credentials are stored as plaintext constants in the source file. Any party who reads the source code — through a repository leak, accidental commit to a public host, or insider access — immediately obtains valid login credentials. The value `mypassword` is also trivially guessable and appears in common wordlists. There is no mechanism to rotate these credentials without a code change and redeployment.

### Prioritization
Highest priority finding. Direct credential disclosure with no preconditions beyond source code access; trivially exploitable and eliminates all security value of the login system.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must read the source file (repository leak, internal access, or LFI on a co-located service).
- **Uncertainty Boundary:** If the deployment never exposes source code, the *secret* properties of this credential are weakened but still present; `mypassword` is likely in breach databases regardless.

### Remediation
Load credentials from environment variables and use a proper password-hashing function. Never store cleartext passwords in code:

```python
import os
import bcrypt

# Store the bcrypt hash in an env var (generate once with bcrypt.hashpw)
# export PASSWORD_HASH=$(python -c "import bcrypt; print(bcrypt.hashpw(b'...yourpassword...', bcrypt.gensalt(12)).decode())")
USERNAME = os.environ["APP_USERNAME"]
PASSWORD_HASH = os.environ["APP_PASSWORD_HASH"].encode()  # bcrypt hash

@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '').encode()
    if username == USERNAME and bcrypt.checkpw(password, PASSWORD_HASH):
        ...
```

## Finding 2: Missing Session State After Authentication

**Finding ID:** `APPSEC-7b2e9f3a01`
**File:** `main.py`
**Lines:** 12–20
**CWE:** CWE-287 — Improper Authentication
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username')
    password = request.form.get('password')

    if username == USERNAME and password == PASSWORD:
        return "Login successful!"
    else:
        return "Invalid credentials!"
```

### Description
The login endpoint verifies credentials but never establishes an authenticated session — no `flask.session` write, no token issuance, no cookie. The `"Login successful!"` response carries no credential the client can present on subsequent requests. Any protected routes added to this application will be reachable without authentication because the login gate produces no durable proof of identity. The authentication step is functionally inert: a correct password and an incorrect password produce identically unauthenticated HTTP clients afterward.

### Prioritization
Tied for highest priority with Finding 1. The hardcoded-credential issue makes authentication trivially bypassable from the credential side; this finding makes authentication irrelevant from the session side — both must be fixed for the login system to provide any security.

### Exploitability Notes
- **Exploit Preconditions:** Any protected route must exist or be added for this to manifest as access-control bypass; the current route set has no protected resources.
- **Uncertainty Boundary:** Impact is theoretical until protected routes are implemented, but the flaw is structurally present and will silently affect any new routes added.

### Remediation
Use Flask's signed-cookie session to set an authenticated flag, and protect subsequent routes with an auth check:

```python
from flask import Flask, request, session, redirect, url_for
import os

app = Flask(__name__)
app.secret_key = os.environ["FLASK_SECRET_KEY"]  # strong random bytes, not hardcoded

@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '').encode()
    if username == USERNAME and bcrypt.checkpw(password, PASSWORD_HASH):
        session.clear()               # prevent session fixation
        session['authenticated'] = True
        session['username'] = username
        return redirect(url_for('home'))
    return "Invalid credentials!", 401

def login_required(f):
    from functools import wraps
    @wraps(f)
    def decorated(*args, **kwargs):
        if not session.get('authenticated'):
            return redirect(url_for('login_page'))
        return f(*args, **kwargs)
    return decorated
```

### References
- https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/
- https://cwe.mitre.org/data/definitions/287.html

## Finding 3: Timing Side-Channel on Credential Comparison

**Finding ID:** `APPSEC-d9c4b1e702`
**File:** `main.py`
**Lines:** 17
**CWE:** CWE-208 — Observable Timing Discrepancy
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```python
if username == USERNAME and password == PASSWORD:
```

### Description
Python's `==` operator on strings short-circuits at the first mismatched byte, meaning the comparison takes measurably less time the earlier a mismatch occurs. An attacker who can issue many login requests and measure response times can enumerate the correct password one character at a time, reducing a brute-force search from `O(charset^length)` to `O(charset × length)`. This is a textbook timing oracle (CWE-208). The `and` short-circuit also leaks whether the username was correct — a wrong username causes both comparisons to be skipped entirely.

### Prioritization
P2, lower than Findings 1–2. The hardcoded credential (Finding 1) already exposes the password in cleartext; timing-based recovery is a redundant attack path while Finding 1 is unresolved. Remediate after fixing P1 findings, and apply constant-time comparison to both fields.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must be able to make many login requests with measurable response-time differences; network jitter can raise the noise floor but does not eliminate the channel in controlled conditions.
- **Uncertainty Boundary:** Python's GIL and CPython string internment may reduce practical timing precision; however, `hmac.compare_digest` is the correct fix regardless of noise level.

### Remediation
Use `hmac.compare_digest()` for both comparisons. The function always runs in constant time regardless of where bytes diverge:

```python
import hmac

@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '')
    # Both comparisons must be constant-time; short-circuiting `and` leaks username validity
    username_ok = hmac.compare_digest(username, USERNAME)
    password_ok = hmac.compare_digest(password, PASSWORD)
    if username_ok and password_ok:
        ...
```

### References
- https://cwe.mitre.org/data/definitions/208.html
- https://docs.python.org/3/library/hmac.html#hmac.compare_digest

## Finding 4: No CSRF Protection on Login Endpoint

**Finding ID:** `APPSEC-a1f5c8b203`
**File:** `main.py`
**Lines:** 12–13
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/login', methods=['POST'])
def login():
```

### Description
The login endpoint accepts `POST` requests with no CSRF token verification. Flask does not enable CSRF protection by default. This permits a *login CSRF* attack: a malicious page can silently submit a `<form>` to `/login` with attacker-chosen credentials, causing the victim's browser to authenticate as the attacker's account. If the application later stores user-specific data (documents, payment methods, history), the attacker can then log into the same account and read the victim's actions. This attack class is distinct from classical CSRF because the *attacker* controls the credentials, not the victim's cookie.

### Prioritization
P2. Login CSRF is most damaging in applications with persistent user state. In the current single-endpoint implementation the impact is limited, but the fix is low-cost and should be applied before the application grows.

### Exploitability Notes
- **Exploit Preconditions:** Victim must visit a page controlled by the attacker while their browser has no same-site cookie policy blocking the cross-origin POST; attacker must know an account credential to plant.
- **Uncertainty Boundary:** SameSite=Strict or Lax cookies on the session cookie would mitigate this, but no cookie is currently issued (see Finding 2).

### Remediation
Add `Flask-WTF` and enable the CSRF extension globally, or generate and validate a token per-form:

```python
from flask_wtf.csrf import CSRFProtect

csrf = CSRFProtect(app)
app.config['SECRET_KEY'] = os.environ["FLASK_SECRET_KEY"]

# In the login HTML template:
# <input type="hidden" name="csrf_token" value="{{ csrf_token() }}">
```

### References
- https://owasp.org/www-community/attacks/csrf
- https://flask-wtf.readthedocs.io/en/stable/csrf.html

## Finding 5: Missing HTTP Security Headers

**Finding ID:** `APPSEC-e6d2a4f108`
**File:** `main.py`
**Lines:** 1–23
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```python
app = Flask(__name__)
# No after_request hook or Flask-Talisman configuration
```

### Description
The application sets no browser security headers: no `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, or `Strict-Transport-Security`. Flask does not add these by default. Without `X-Frame-Options: DENY` or a CSP `frame-ancestors` directive the login page can be framed for clickjacking. Without `X-Content-Type-Options: nosniff` browsers may MIME-sniff responses. The absence of CSP removes a layer of XSS defence for any future HTML content.

### Prioritization
P3. No direct exploit path in the current single-route, plaintext-response application, but headers should be set before any HTML is returned to clients.

### Exploitability Notes
- **Exploit Preconditions:** Depends on content type returned and browser behavior; current responses are `text/html` plain strings.
- **Uncertainty Boundary:** Impact grows with any HTML template addition.

### Remediation
Use `Flask-Talisman` to apply a secure header baseline in one line:

```python
from flask_talisman import Talisman

Talisman(app, content_security_policy={
    'default-src': "'self'"
})
```

Or set headers manually via `after_request`:

```python
@app.after_request
def set_security_headers(response):
    response.headers['X-Frame-Options'] = 'DENY'
    response.headers['X-Content-Type-Options'] = 'nosniff'
    response.headers['Referrer-Policy'] = 'strict-origin-when-cross-origin'
    return response
```

### References
- https://owasp.org/www-project-secure-headers/
- https://cwe.mitre.org/data/definitions/693.html

## Finding 6: No Brute-Force / Rate-Limit Protection on Login

**Finding ID:** `APPSEC-3b8c5d9e17`
**File:** `main.py`
**Lines:** 12–20
**CWE:** CWE-307 — Improper Restriction of Excessive Authentication Attempts
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username')
    password = request.form.get('password')
    if username == USERNAME and password == PASSWORD:
```

### Description
The `/login` endpoint imposes no limit on failed authentication attempts. An attacker can submit unlimited credential guesses at network speed with no lockout, delay, or CAPTCHA. Even if the hardcoded credential is replaced with a stronger one, the endpoint remains a target for online password spraying. The absence of rate limiting also amplifies the timing oracle in Finding 3.

### Prioritization
P3. Finding 1 (hardcoded credential) already exposes the password directly; brute-force protection is moot while that issue exists. Fix after P1/P2 findings are resolved.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the `/login` endpoint.
- **Uncertainty Boundary:** A reverse proxy or WAF upstream may enforce rate limits not visible in this source file.

### Remediation
Apply per-IP rate limiting with `Flask-Limiter`:

```python
from flask_limiter import Limiter
from flask_limiter.util import get_remote_address

limiter = Limiter(get_remote_address, app=app, default_limits=["200 per day"])

@app.route('/login', methods=['POST'])
@limiter.limit("10 per minute")
def login():
    ...
```

- https://cwe.mitre.org/data/definitions/307.html
- https://owasp.org/www-community/controls/Blocking_Brute_Force_Attacks
