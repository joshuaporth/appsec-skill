## Finding 1: Hardcoded Credentials

**File:** `main.py`  
**Lines:** 5–6  
**CWE:** CWE-798 — Use of Hard-coded Credentials  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```python
USERNAME = "admin"
PASSWORD = "mypassword"
```

### Description
The application's login credentials are baked directly into source code. Any developer, code reviewer, CI system, or attacker who obtains the source (via a repository breach, leaked artifact, or insider access) immediately has valid credentials. This also means credential rotation requires a code change and redeployment — making rotation effectively infeasible in practice. The credentials are then used verbatim in the authentication comparison at line 17.

### Prioritization
Highest-priority finding in this file. No preconditions beyond source access, which is a realistic attacker scenario (leaked repo, disgruntled employee, public commit history).

### Exploitability Notes
- **Exploit Preconditions:** Attacker obtains source code (or built artifact containing string literals).
- **Uncertainty Boundary:** If this is a local dev stub and credentials are overridden at deploy time, real-world impact is lower — but the code as written does not indicate any such mechanism.

### Remediation
```python
import os

USERNAME = os.environ["APP_USERNAME"]
PASSWORD_HASH = os.environ["APP_PASSWORD_HASH"]  # store a bcrypt hash, not plaintext
```
Load credentials from environment variables or a secrets manager (AWS Secrets Manager, HashiCorp Vault). Never commit credentials to source control. Combine with Finding 2's fix to store a hash, not the raw password.

### References
- https://cwe.mitre.org/data/definitions/798.html
- https://owasp.org/www-community/vulnerabilities/Use_of_hard-coded_password

## Finding 2: Plaintext Password Storage and Comparison

**File:** `main.py`  
**Lines:** 6, 17  
**CWE:** CWE-256 — Plaintext Storage of a Password / CWE-916 — Use of Password Hash With Insufficient Computational Effort  
**OWASP Category:** A02:2021 – Cryptographic Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```python
PASSWORD = "mypassword"
...
if username == USERNAME and password == PASSWORD:
```

### Description
The password is stored as a raw plaintext string and compared directly against user input. There is no hashing, no salt, and no use of a purpose-built password hashing function. If the credential store is ever migrated to a database or external config and that store is breached, all passwords are immediately revealed without requiring any cracking. Password hashing (bcrypt, Argon2id) exists precisely to ensure that even with a full credential-store dump, passwords are not trivially recovered.

### Prioritization
Co-equal P1 with Finding 1. Both must be fixed together: move the credential to env/config AND store it as a bcrypt hash.

### Exploitability Notes
- **Exploit Preconditions:** Access to source code or wherever the credential string is stored.
- **Uncertainty Boundary:** In the current single-file form, exposure is tied to source access. If credentials move to a DB later without hashing, a SQL injection or DB dump would yield plaintext passwords instantly.

### Remediation
```python
import bcrypt
import os

# At setup time, generate and store:
#   bcrypt.hashpw(b"mypassword", bcrypt.gensalt(rounds=12))
# Store that hash in env or secrets manager, not the raw password.

PASSWORD_HASH = os.environ["APP_PASSWORD_HASH"].encode()

@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '').encode()

    if username == os.environ["APP_USERNAME"] and bcrypt.checkpw(password, PASSWORD_HASH):
        return "Login successful!"
    return "Invalid credentials!", 401
```
`bcrypt.checkpw` is constant-time within the bcrypt domain and uses an adaptive cost factor — this fix also addresses Finding 4.

### References
- https://cwe.mitre.org/data/definitions/256.html
- https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html

## Finding 3: No Authentication State Issued After Login

**File:** `main.py`  
**Lines:** 12–19  
**CWE:** CWE-306 — Missing Authentication for Critical Function  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username')
    password = request.form.get('password')

    if username == USERNAME and password == PASSWORD:
        return "Login successful!"
    else:
        return "Invalid credentials!"
```

### Description
The login endpoint verifies credentials but issues no session cookie, token, or any other persistent auth artifact. A "successful" login produces only the string `"Login successful!"` — the client is left with no proof of authentication. Because Flask's session system is also unconfigured (no `app.secret_key` is set), any routes added to this application in the future would have no mechanism to verify that a user previously authenticated. Authentication is effectively non-functional: it checks but never grants.

### Prioritization
P1 alongside credential findings. If protected routes are added without this being addressed first, those routes will have no auth gate. This represents a structural failure of the authentication subsystem.

### Exploitability Notes
- **Exploit Preconditions:** Any future route that assumes session-based auth would be accessible to unauthenticated users.
- **Uncertainty Boundary:** In the current two-route form, there are no protected routes to bypass. Impact is latent but guaranteed to materialize on any realistic extension of this codebase.

### Remediation
```python
from flask import Flask, request, session
import os, bcrypt

app = Flask(__name__)
app.secret_key = os.environ["FLASK_SECRET_KEY"]  # 32+ random bytes, set in env

@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username', '')
    password = request.form.get('password', '').encode()
    stored_hash = os.environ["APP_PASSWORD_HASH"].encode()

    if username == os.environ["APP_USERNAME"] and bcrypt.checkpw(password, stored_hash):
        session.clear()                    # prevent session fixation
        session['user'] = username
        session.permanent = True
        return "Login successful!"
    return "Invalid credentials!", 401

@app.route('/protected')
def protected():
    if 'user' not in session:
        return "Unauthorized", 401
    return f"Hello, {session['user']}"
```
`app.secret_key` must be a cryptographically random value (e.g., `secrets.token_hex(32)`) loaded from environment — never hardcoded. `session.clear()` before setting the new session prevents session fixation.

### References
- https://owasp.org/www-community/attacks/Session_fixation
- https://flask.palletsprojects.com/en/stable/quickstart/#sessions

## Finding 4: Timing Attack on Credential Comparison

**File:** `main.py`  
**Line:** 17  
**CWE:** CWE-208 — Observable Timing Discrepancy  
**OWASP Category:** A02:2021 – Cryptographic Failures  
**Priority:** P2  
**Severity:** MEDIUM  
**Confidence:** HIGH

### Vulnerable Code
```python
if username == USERNAME and password == PASSWORD:
```

### Description
Python's `==` operator on strings uses short-circuit evaluation: it returns `False` on the first mismatched character. This means an attacker who can make many login attempts and measure response times can iteratively determine the correct password one character at a time, even without any error message leaking which character was wrong. While network jitter makes this harder to exploit remotely than locally, it is a real class of attack (Timing Oracle / CWE-208) and particularly dangerous for password and token comparisons.

### Prioritization
P2 — lower than P1 findings because it requires many observable requests and some precision in timing measurement. Remediating Findings 1–3 first is correct, and the bcrypt fix in Finding 2 inherently uses a constant-time comparison, making this finding moot if that remediation is applied.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can send repeated login attempts and measure response latency with sufficient precision.
- **Uncertainty Boundary:** Remote network jitter reduces practical exploitability. Local or low-latency environments are higher risk.

### Remediation
```python
import hmac

# Using hmac.compare_digest for constant-time comparison:
if username == USERNAME and hmac.compare_digest(password, PASSWORD):
    ...
```
Note: the complete fix from Finding 2 (using `bcrypt.checkpw`) already provides constant-time comparison within the bcrypt domain and is the preferred solution. This fix is only relevant if plaintext comparison is retained for other reasons (it should not be).

### References
- https://cwe.mitre.org/data/definitions/208.html
- https://docs.python.org/3/library/hmac.html#hmac.compare_digest

## Finding 5: Missing CSRF Protection on Login Endpoint

**File:** `main.py`  
**Lines:** 12–19  
**CWE:** CWE-352 — Cross-Site Request Forgery  
**OWASP Category:** A01:2021 – Broken Access Control  
**Priority:** P2  
**Severity:** MEDIUM  
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/login', methods=['POST'])
def login():
    username = request.form.get('username')
    password = request.form.get('password')
```

### Description
The login endpoint accepts POST requests without any CSRF token validation. Flask does not enable CSRF protection by default. An attacker can embed a forged form on an attacker-controlled page that silently POSTs to `/login` with the attacker's own credentials when a victim visits that page. This enables a **login CSRF** attack: the victim is logged in as the attacker, and any actions the victim takes (browsing, entering personal data) are performed under the attacker's account, giving the attacker visibility into those actions. The impact is amplified if the app later stores user data.

### Prioritization
P2 — login CSRF is less immediately impactful than credential or session flaws (Findings 1–3), and without session management (Finding 3), session fixation via login CSRF is currently not exploitable. However, it must be addressed before session management is added, or the combination becomes a session fixation primitive.

### Exploitability Notes
- **Exploit Preconditions:** Victim must visit an attacker-controlled page while the browser has no SameSite cookie restrictions in force. Modern browsers default `SameSite=Lax`, which blocks cross-site form POSTs, partially mitigating this — but not all browsers/versions behave identically.
- **Uncertainty Boundary:** Browser SameSite policy version and whether the app's session cookie will be set with `SameSite` attribute will determine practical exploitability.

### Remediation
```python
# Install Flask-WTF: pip install flask-wtf
from flask_wtf import FlaskForm
from wtforms import StringField, PasswordField
from flask_wtf.csrf import CSRFProtect

csrf = CSRFProtect(app)

# In the login form template, include: {{ form.hidden_tag() }}
# Flask-WTF validates the token automatically on POST.
```
Alternatively, set session cookies with `SameSite=Strict` as a defense-in-depth measure:
```python
app.config['SESSION_COOKIE_SAMESITE'] = 'Strict'
app.config['SESSION_COOKIE_SECURE'] = True   # require HTTPS
app.config['SESSION_COOKIE_HTTPONLY'] = True
```

### References
- https://owasp.org/www-community/attacks/csrf
- https://flask-wtf.readthedocs.io/en/stable/csrf/
