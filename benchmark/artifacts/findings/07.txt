## Finding 1: Hardcoded Static Password Reset Token

**Finding ID:** `APPSEC-fd73b8705d94`
**File:** `main.js`
**Lines:** 25–25
**CWE:** CWE-330 — Use of Insufficiently Random Values
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```javascript
const resetLink = `http://${req.headers.host}/reset-password?token=generatedToken123`;
```

### Description
The password reset token is a hardcoded string literal `generatedToken123` rather than a cryptographically random value generated at request time. Every password reset request for every user uses the exact same predictable token. An attacker who knows (or guesses) the token value can initiate a legitimate reset request for a victim's email, then immediately navigate to `/reset-password?token=generatedToken123` without intercepting any email — achieving a full account takeover with zero authentication. Even without knowing the token in advance, any attacker who has ever legitimately used the reset flow now possesses the universal token for all users indefinitely.

### Prioritization
Highest-priority finding in this codebase. The token is fully predictable from source code inspection alone, there are no preconditions beyond knowing a target's email address, and the impact is complete account compromise. All other findings rank below this one.

### Exploitability Notes
- **Exploit Preconditions:** Attacker knows a target user's email address. Attacker has read access to this source code (or can test the token empirically).
- **Uncertainty Boundary:** Impact depends on whether the password reset handler (not shown in this file) actually validates the token before applying the change. If it does not validate at all, exploitation is trivial. If there is separate validation, this finding still represents a universally shared, non-expiring, non-rotating secret.

### Remediation
Generate a cryptographically random, per-request, time-limited token using Node's `crypto` module. Store it server-side with the associated email address and an expiry timestamp.

```javascript
const crypto = require('crypto');

app.post('/reset-password', (req, res) => {
    const token = crypto.randomBytes(32).toString('hex'); // 256-bit CSPRNG token
    const expiry = Date.now() + 60 * 60 * 1000; // 1-hour expiry

    // Persist: db.saveResetToken(req.body.email, token, expiry)

    const resetLink = `https://yourdomain.example.com/reset-password?token=${token}`;
    transporter.sendMail({
        from: 'support@example.com',
        to: req.body.email,
        subject: 'Password Reset',
        text: `Click here to reset your password: ${resetLink}`
    });

    res.send('Password reset link has been sent to your email.');
});
```

**Why:** `crypto.randomBytes(32)` draws from the OS CSPRNG, producing a 256-bit token that cannot be guessed or brute-forced. Binding the token to the email address server-side and enforcing expiry ensures each token is single-use and short-lived.

### References
- [OWASP: Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)
- [CWE-330: Use of Insufficiently Random Values](https://cwe.mitre.org/data/definitions/330.html)

## Finding 2: Host Header Injection — Password Reset Link Poisoning

**Finding ID:** `APPSEC-f3025f5709f6`
**File:** `main.js`
**Lines:** 25–25
**CWE:** CWE-640 — Weak Password Recovery Mechanism for Forgotten Password
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
const resetLink = `http://${req.headers.host}/reset-password?token=generatedToken123`;
```

### Description
The `Host` header is an attacker-controlled HTTP request header, yet it is interpolated directly into the password reset URL that is emailed to the victim. An attacker who initiates a reset for `victim@example.com` and sends `Host: attacker.com` receives a valid email in the victim's inbox reading: `http://attacker.com/reset-password?token=generatedToken123`. When the victim clicks the link they land on the attacker's server, which logs the token. This is the well-documented "password reset poisoning" attack class. Impact is account takeover of any user whose email address is known.

### Prioritization
Co-ranked P1 with Finding 1. While it requires the victim to click a link (phishing precondition), this is a realistic social engineering step; combined with Finding 1's static token, exploitation becomes trivially reliable.

### Exploitability Notes
- **Exploit Preconditions:** Attacker knows victim's email address. Victim must click the emailed link. No existing session or authentication required.
- **Uncertainty Boundary:** Some reverse proxies normalize or override the `Host` header before it reaches the application. If such a proxy is deployed in front of this service, the attack surface narrows. No proxy config is in scope here, so the application must be treated as directly Internet-exposed.

### Remediation
Never derive the application's origin from the incoming `Host` header for security-sensitive operations. Use a server-side configured base URL:

```javascript
// In environment config or app startup
const BASE_URL = process.env.APP_BASE_URL || 'https://yourdomain.example.com';

app.post('/reset-password', (req, res) => {
    const token = crypto.randomBytes(32).toString('hex');
    const resetLink = `${BASE_URL}/reset-password?token=${token}`;
    // ...
});
```

**Why:** The base URL is operator-controlled, not request-derived. An attacker manipulating the `Host` header cannot influence the constructed link.

### References
- [PortSwigger: Host Header Injection](https://portswigger.net/web-security/host-header)
- [CWE-640: Weak Password Recovery Mechanism for Forgotten Password](https://cwe.mitre.org/data/definitions/640.html)

## Finding 3: Email Header Injection via Unvalidated `to` Address

**Finding ID:** `APPSEC-176c108ffdbe`
**File:** `main.js`
**Lines:** 26–32
**CWE:** CWE-93 — Improper Neutralization of CRLF Sequences ('CRLF Injection')
**OWASP Category:** A03:2021 – Injection
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```javascript
transporter.sendMail({
    from: 'support@example.com',
    to: req.body.email,
    subject: 'Password Reset',
    text: `Click here to reset your password: ${resetLink}`
});
```

### Description
`req.body.email` is passed directly to the `to` field of the mail options without any format validation or sanitization. Many SMTP client libraries (including nodemailer) allow multiple recipients via comma-separation, and some are vulnerable to CRLF injection in header fields. An attacker can supply a value such as `victim@example.com\r\nBcc: attacker@attacker.com` or `victim@example.com, attacker@attacker.com`, causing the reset email to be copied to an attacker-controlled address. Depending on the actual mail transport used in production, this can be exploited to intercept reset tokens sent to any user.

### Prioritization
P2; exploitability depends on the email library used at runtime (here replaced by a mock). With Finding 1 fixed (random tokens), the token interception path becomes meaningful. With Finding 2 fixed (fixed base URL), this remains the primary token-capture vector.

### Exploitability Notes
- **Exploit Preconditions:** The production mail transporter (not in scope) must not strip CRLF sequences or additional recipients from the `to` field. The attacker must supply a crafted email value in the request body.
- **Uncertainty Boundary:** Nodemailer's actual header injection behavior depends on its version and transport configuration. The current mock transporter cannot be exploited. Rating is MEDIUM confidence accordingly.

### Remediation
Validate the email address format before use, and confirm the real transporter sanitizes header values:

```javascript
const validator = require('validator'); // npm install validator

app.post('/reset-password', (req, res) => {
    const email = req.body.email;
    if (!email || !validator.isEmail(email)) {
        return res.status(400).send('Invalid email address.');
    }
    // proceed with validated email
});
```

**Why:** Strict RFC 5321 email validation rejects CRLF sequences and multiple recipients before they can reach the SMTP layer. The `validator` library's `isEmail()` enforces this format.

### References
- [OWASP: Email Header Injection](https://owasp.org/www-community/attacks/Email_Header_Injection)
- [CWE-93: CRLF Injection](https://cwe.mitre.org/data/definitions/93.html)

## Finding 4: Missing CSRF Protection on State-Changing Endpoints

**Finding ID:** `APPSEC-1264a0e684eb`
**File:** `main.js`
**Lines:** 19–33
**CWE:** CWE-352 — Cross-Site Request Forgery (CSRF)
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```javascript
app.post('/register', (req, res) => { ... });
app.post('/reset-password', (req, res) => { ... });
```

### Description
Both POST endpoints perform state-changing operations (user registration and password reset initiation) without any CSRF token verification. Neither endpoint checks for a synchronizer token pattern, double-submit cookie, or `SameSite` cookie attribute enforcement. A malicious page can silently trigger `/reset-password` for an authenticated user's account via a cross-origin fetch. Although `Content-Type: application/json` limits classical form-based CSRF, the endpoints accept `application/x-www-form-urlencoded` as well (body-parser is in use), making them reachable from a traditional HTML form on an attacker-controlled origin.

### Prioritization
P2. Impact is meaningful but requires the victim to visit an attacker-controlled page. Express's `body-parser` + no `SameSite` cookies is the relevant attack path. Lower priority than Findings 1–2.

### Exploitability Notes
- **Exploit Preconditions:** Victim must have an active session (if session auth is later added). Attacker must host a page the victim visits. Request body must be deliverable without a custom Content-Type.
- **Uncertainty Boundary:** Exploitability is higher if session cookies are later added without `SameSite=Strict/Lax`. Currently, no session management is visible in scope.

### Remediation
Add the `csurf` middleware (or its modern equivalent) and enforce `SameSite=Strict` on all session cookies:

```javascript
const csrf = require('csurf');
const csrfProtection = csrf({ cookie: { sameSite: 'strict', secure: true } });

app.post('/reset-password', csrfProtection, (req, res) => { ... });
app.post('/register', csrfProtection, (req, res) => { ... });
```

**Why:** A CSRF token tied to the user's session cannot be read by a cross-origin page, breaking the forgery prerequisite.

### References
- [OWASP: CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- [CWE-352: Cross-Site Request Forgery](https://cwe.mitre.org/data/definitions/352.html)

## Finding 5: PII and Reset Token Logged to Console

**Finding ID:** `APPSEC-a94c7862a840`
**File:** `main.js`
**Lines:** 10–12
**CWE:** CWE-532 — Insertion of Sensitive Information into Log File
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
const transporter = { 
    sendMail: (mailOptions) => {
        console.log('[MOCK] Sending email with options:', mailOptions);
    }
};
```

### Description
The mock transporter logs the entire `mailOptions` object, which includes the recipient's email address (`to`), the reset link with its token (`text`), and the subject. If the real production transporter retains any logging that captures these fields, both PII (email addresses) and active security credentials (reset tokens) will appear in application logs. An attacker with log access can harvest reset tokens and bypass the entire reset flow.

### Prioritization
P3. This is a mock implementation and the direct risk is minimal in the current codebase. However, the pattern of logging `mailOptions` verbatim should not be carried into any production transporter.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must gain access to application log storage (e.g., compromised logging infrastructure, exposed log files).
- **Uncertainty Boundary:** The real transporter's logging behavior is not in scope.

### Remediation
Never log objects that may contain PII or security tokens. Restrict logging to non-sensitive metadata:

```javascript
const transporter = {
    sendMail: (mailOptions) => {
        console.log('[MOCK] Email queued for:', mailOptions.to.replace(/(?<=.{3}).(?=.*@)/g, '*'));
    }
};
```

In production, use a structured logger (e.g., `pino`) that can redact sensitive fields by key:

```javascript
const logger = pino({ redact: ['email', 'text', 'html', 'token'] });
```

**Why:** Redacting sensitive fields at the logger level ensures tokens and PII never reach log storage regardless of call-site mistakes.

### References
- [CWE-532: Insertion of Sensitive Information into Log File](https://cwe.mitre.org/data/definitions/532.html)
- [OWASP: Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)
