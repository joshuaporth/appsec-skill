## Finding 1: XSLT Code Injection → Local File Inclusion + SSRF

**File:** `app.py`
**Lines:** 19–33
**CWE:** CWE-94 — Improper Control of Generation of Code ('Code Injection') / OWASP-adjacent: SSRF (CWE-918), LFI (CWE-22)
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```python
with PySaxonProcessor(license=False) as proc:
    xsltproc = proc.new_xslt30_processor()
    xsltproc.set_cwd('.')
    transformer = xsltproc.compile_stylesheet(stylesheet_text=xslt_content.decode())

    with open('./resources/some.xml', 'rb') as xml_file:
        xml_content = xml_file.read()

    document = proc.parse_xml(xml_text=xml_content.decode('utf-8'))
    output = transformer.transform_to_string(xdm_node=document)
```

### Description
The `/parse-xslt` endpoint accepts a user-uploaded file, reads it as text, and passes it directly as the XSLT stylesheet source to Saxon's XSLT 3.0 processor with no validation, sandboxing, or URI-resolver restrictions. XSLT 3.0 is a Turing-complete language with built-in standard functions `unparsed-text()` and `doc()` that perform filesystem reads and outbound HTTP fetches. Since the attacker controls the full stylesheet source — not merely a template variable — this is template-source injection: the attacker defines the program that runs with the web server's privileges. An attacker can read arbitrary local files (`/etc/passwd`, `/proc/self/environ`, application secrets) and probe internal network services (cloud metadata endpoints, internal APIs) simply by uploading a crafted XSLT file.

**LFI payload:**
```xml
<?xml version="1.0" encoding="UTF-8"?>
<xsl:stylesheet version="3.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
  <xsl:template match="/">
    <xsl:value-of select="unparsed-text('file:///etc/passwd')"/>
  </xsl:template>
</xsl:stylesheet>
```
`unparsed-text()` is a standard XPath 3.0 function — no Saxon extension license required — and returns the file as a string, which becomes the transformation output returned verbatim to the attacker's browser.

**SSRF payload:**
```xml
<xsl:value-of select="unparsed-text('http://169.254.169.254/latest/meta-data/iam/security-credentials/')"/>
```
This reaches the AWS EC2 instance metadata service from the container and returns IAM credential material.

**Additional vector — relative paths:** `set_cwd('.')` (line 21) resolves relative URIs against the container working directory `/app`. An attacker can traverse upward: `unparsed-text('../../../etc/shadow')` if permissions allow.

**Potential file write:** `xsl:result-document href="file:///tmp/evil"` may write secondary output documents to the filesystem depending on Saxon's output resolver behavior in this API call path (classified MEDIUM confidence — depends on saxonche runtime defaults).

### Prioritization
This is the **highest-priority finding** in the codebase. The attack surface is unauthenticated (see Finding 2), requires no preconditions beyond HTTP access, and exploitation is trivially demonstrated with a single uploaded file. The result is immediate, unauthenticated read of any file accessible to the process, and outbound requests to any reachable network endpoint.

### Exploitability Notes
- **Exploit Preconditions:** HTTP access to the `/parse-xslt` endpoint (no authentication required); ability to upload a file via multipart/form-data POST.
- **Uncertainty Boundary:** File write via `xsl:result-document` depends on whether saxonche's `transform_to_string` silently discards secondary result documents or materializes them to disk; this does not affect the confirmed LFI/SSRF paths. Saxon HE (enforced by `license=False`) lacks Java extension functions, so `saxon:exec()` RCE via extension is not available — however, the LFI + SSRF surface is severe on its own.

### Remediation
The root cause is accepting arbitrary code as input. The correct fix is to remove user-supplied XSLT entirely and use a fixed, server-owned stylesheet. If accepting user XSLTs is a product requirement, a URI resolver that blocks all `file://` and `http://` URIs must be installed before execution:

```python
# PREFERRED: eliminate user-supplied XSLT entirely
# Compile the stylesheet once at startup from a trusted source
XSLT_PATH = os.path.join(os.path.dirname(__file__), 'resources', 'transform.xslt')

with PySaxonProcessor(license=False) as proc:
    xsltproc = proc.new_xslt30_processor()
    # do NOT call set_cwd with attacker-influenced paths
    transformer = xsltproc.compile_stylesheet(stylesheet_file=XSLT_PATH)
    ...
```

If user-supplied XSLT is unavoidable, install a custom `PyURIResolver` that rejects all `file://` and non-allowlisted `http://` URIs, and strictly validate the XSLT source against a schema or AST allowlist before compilation. Note: URI filtering alone does not address all XSLT 3.0 attack surface (e.g., dynamic evaluation via `xsl:evaluate`).

**Counterfactual invalidation:** Replacing `stylesheet_text=xslt_content.decode()` with `stylesheet_file=TRUSTED_STATIC_PATH` entirely eliminates the injection surface because attacker input no longer reaches the XSLT compiler.

## Finding 2: Missing Authentication on XSLT Processing Endpoint

**File:** `app.py`
**Lines:** 11–36
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
    try:
        if 'xslt_file' not in request.files:
            return 'No file part', 400
        
        xslt_file = request.files['xslt_file']
        xslt_content = xslt_file.read()
        ...
```

### Description
The `/parse-xslt` endpoint performs server-side XSLT execution but requires no authentication. Any HTTP client that can reach port 5000 — including unauthenticated internet users if the host is exposed, or any container on the `app-network` bridge — can invoke the full XSLT processing pipeline. This directly amplifies Finding 1: the critical XSLT injection is reachable with zero preconditions.

### Prioritization
Second priority after Finding 1. Does not independently produce a new vulnerability class, but removing the zero-precondition access path for Finding 1 would reduce its effective severity. Ranked above Finding 3 (info disclosure) because it controls access to the highest-impact operation.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the service.
- **Uncertainty Boundary:** If deployed behind a network boundary that restricts access to trusted clients only, the practical impact of missing auth is reduced — but defense-in-depth requires authentication at the application layer.

### Remediation
Add an authentication gate before processing. At minimum, require an API key from an environment variable checked against the request:

```python
import hmac, os

API_KEY = os.environ.get('XSLT_API_KEY', '')

@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
    provided_key = request.headers.get('X-API-Key', '')
    if not API_KEY or not hmac.compare_digest(provided_key, API_KEY):
        return 'Unauthorized', 401
    ...
```

For multi-user applications, use a proper session-based or token-based auth framework (e.g., Flask-Login, JWT).

## Finding 3: Exception Detail Disclosure to Client

**File:** `app.py`
**Lines:** 34–36
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```python
    except Exception as e:
        print(f"Error processing XSLT: {str(e)}")
        return str(e), 500
```

### Description
On any exception during XSLT processing, the full exception message is returned directly to the client. For a Saxon XSLT processor, exception messages can include internal file paths (e.g., the stylesheet compile path, resolved URI strings), partial file content when a `doc()` or `unparsed-text()` call partially succeeds, and Java/C stack frame text. In the context of Finding 1, this accelerates attacker reconnaissance: a malformed XSLT payload that partially reads a file may surface file path information in the error response even when the transformation fails.

### Prioritization
Third priority. The information disclosure is a secondary enabler for Finding 1 rather than an independently exploitable issue. Ranked lower than the auth finding because exploiting it requires triggering an error condition, which an attacker with Finding 1 already has.

### Exploitability Notes
- **Exploit Preconditions:** Ability to submit a request that causes an exception.
- **Uncertainty Boundary:** Saxon exception message verbosity depends on the error type; some errors return only a code, others include file paths or content fragments.

### Remediation
Log the full exception server-side and return a generic error message to the client:

```python
import logging
logger = logging.getLogger(__name__)

    except Exception as e:
        logger.exception("Error processing XSLT")
        return 'Internal server error', 500
```

## Finding 4: No CSRF Protection on State-Changing Endpoint

**File:** `app.py`
**Lines:** 11–36
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P4
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```python
@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
```

### Description
The application accepts `multipart/form-data` POST requests with no CSRF token verification. Flask does not enable CSRF protection by default. An attacker who can convince a victim's browser to send a cross-origin POST (via a malicious page with a crafted form) triggers server-side XSLT execution on behalf of the victim. Because the application has no sessions, the CSRF impact is not credential theft but rather using the victim as a proxy to initiate Finding 1's SSRF from within the victim's network context — particularly meaningful if the service is on an internal network and the victim is an authenticated internal user.

### Prioritization
Lower priority than Findings 1–3. Without session cookies to steal, the standalone CSRF impact is limited to exploiting the victim as an unwitting SSRF relay. Exploitation requires a victim with browser access to a page under attacker control who also has network access to the Flask service.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can serve a page to a user who has network access to the Flask endpoint; browser must allow cross-origin `multipart/form-data` POST (no pre-flight required for simple forms, but file field may trigger preflight depending on content).
- **Uncertainty Boundary:** Actual exploitability depends on whether the browser's CORS policy blocks the cross-origin response read; for pure SSRF-triggering (fire-and-forget), response reading is not required.

### Remediation
Install `flask-wtf` and enable CSRF protection globally, or check `Origin`/`Referer` headers for AJAX endpoints:

```python
from flask_wtf.csrf import CSRFProtect
csrf = CSRFProtect(app)
app.config['SECRET_KEY'] = os.environ['FLASK_SECRET_KEY']
```

Or for API-style endpoints, validate the `Origin` header against an allowlist:
```python
ALLOWED_ORIGINS = {'http://localhost:5000'}
if request.headers.get('Origin') not in ALLOWED_ORIGINS:
    return 'Forbidden', 403
```
