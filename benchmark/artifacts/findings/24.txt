## Finding 1: XSLT Injection / Server-Side Request Forgery via Arbitrary XSLT Upload

**Finding ID:** `APPSEC-xslt-cwe611-39ab2c`
**File:** `app.py`
**Lines:** 10–36
**CWE:** CWE-611 — XML External Entity Reference; CWE-94 — Code Injection
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```python
@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
    ...
    xslt_file = request.files['xslt_file']
    xslt_content = xslt_file.read()

    with PySaxonProcessor(license=False) as proc:
        xsltproc = proc.new_xslt30_processor()
        xsltproc.set_cwd('.')
        transformer = xsltproc.compile_stylesheet(stylesheet_text=xslt_content.decode())
        ...
        output = transformer.transform_to_string(xdm_node=document)
        return output
```

### Description

The endpoint accepts arbitrary XSLT stylesheets uploaded by unauthenticated users and compiles them directly into a Saxon XSLT 3.0 processor with no security constraints. Saxon XSLT 3.0 supports several dangerous functions by default:

- `unparsed-text('/etc/passwd')` — reads arbitrary local files
- `doc('file:///etc/shadow')` — fetches arbitrary URIs (LFI/SSRF)
- `environment-variable('SECRET_KEY')` — reads environment variables

An attacker uploads this stylesheet and gets the file contents back in the HTTP response:

```xml
<xsl:stylesheet version="3.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform">
  <xsl:template match="/">
    <xsl:value-of select="unparsed-text('/etc/passwd')"/>
  </xsl:template>
</xsl:stylesheet>
```

This gives unauthenticated arbitrary file read with no preconditions beyond HTTP access.

### Prioritization

Highest priority. Direct file exfiltration and SSRF with no authentication, no rate limiting, and no filtering in the code path.

### Exploitability Notes
- **Exploit Preconditions:** HTTP POST access to `/parse-xslt`. No authentication required.
- **Uncertainty Boundary:** Exact impact depends on whether a Java SecurityManager is active in the container (not configured in the Dockerfile). Saxon's default is to allow all file/network access.
- **Counterfactual invalidation:** Adding a Saxon `UnfilteredUriResolver` that allowlists zero URIs would eliminate file read / SSRF. Switching to a static server-side XSLT template would eliminate the class entirely.

### Remediation

The safest fix is to never accept user-supplied XSLT — use a server-side template allowlist instead:

```python
TRUSTED_STYLESHEETS = {
    'transform1': open('./xslt/transform1.xsl').read(),
}

@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
    name = request.form.get('template')
    if name not in TRUSTED_STYLESHEETS:
        return 'Unknown template', 400
    stylesheet_text = TRUSTED_STYLESHEETS[name]
    # compile and execute as before
```

If user-supplied XSLT is a hard requirement, set a Saxon `SecurityManager` that denies all external resource access and reject stylesheets containing `doc(`, `unparsed-text(`, `environment-variable(`, `collection(`, `uri-collection(`, and `transform(` before compilation.

- [OWASP XXE Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/XML_External_Entity_Prevention_Cheat_Sheet.html)

## Finding 2: Sensitive Error Information Disclosed to Client

**Finding ID:** `APPSEC-app-cwe209-7f4e1b`
**File:** `app.py`
**Lines:** 34–36
**CWE:** CWE-209 — Information Exposure Through an Error Message
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```python
    except Exception as e:
        print(f"Error processing XSLT: {str(e)}")
        return str(e), 500
```

### Description

The full exception string is returned directly to the HTTP client. In the context of the XSLT injection above, this leaks internal file paths, Saxon version strings, Java class names, and — critically — it reflects file contents when the XSLT reads a file that causes a parse error, aiding attacker reconnaissance even when the happy path is blocked.

### Prioritization

Secondary to Finding 1. Fix alongside it.

### Remediation

```python
import logging
logger = logging.getLogger(__name__)

except Exception as e:
    logger.exception("Error processing XSLT")
    return "An error occurred processing your request.", 500
```

## Finding 3: No File Size or Content-Type Validation on Upload

**Finding ID:** `APPSEC-app-cwe434-6d2e3c`
**File:** `app.py`
**Lines:** 13–17
**CWE:** CWE-434 — Unrestricted Upload of File with Dangerous Type
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```python
xslt_file = request.files['xslt_file']
xslt_content = xslt_file.read()
```

### Description

No file size limit, extension check, or content-type check is performed before reading the upload into memory and passing it to the Saxon compiler. An attacker can submit an arbitrarily large file to exhaust server memory, or submit a non-XSLT binary that triggers parsing exceptions revealing internal details (see Finding 2).

### Remediation

```python
MAX_UPLOAD_BYTES = 512 * 1024  # 512 KB
ALLOWED_EXTENSIONS = {'xsl', 'xslt'}

xslt_file = request.files['xslt_file']
fname = xslt_file.filename or ''
ext = fname.rsplit('.', 1)[-1].lower() if '.' in fname else ''
if ext not in ALLOWED_EXTENSIONS:
    return 'Invalid file type', 400

xslt_content = xslt_file.read(MAX_UPLOAD_BYTES + 1)
if len(xslt_content) > MAX_UPLOAD_BYTES:
    return 'File too large', 400
```

## Finding 4: No CSRF Protection on State-Triggering POST Endpoint

**Finding ID:** `APPSEC-app-cwe352-91a8f7`
**File:** `app.py` / `templates/index.html`
**Lines:** 10, form element
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P3
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```python
@app.route('/parse-xslt', methods=['POST'])
def parse_xslt():
    # no CSRF token checked
```

### Description

The POST endpoint triggers Saxon XSLT execution without a CSRF token. An attacker page can submit a form cross-origin to trigger XSLT processing against the server. Because the endpoint has no authentication, the practical impact is attacker-controlled XSLT being processed — intersecting directly with Finding 1.

### Exploitability Notes
- **Exploit Preconditions:** Victim visits attacker page while the target app is accessible. File uploads via cross-origin forms are CORS-constrained but not fully blocked in all browser configurations.
- **Uncertainty Boundary:** CORS policy (`*` or none set) on the Flask app affects cross-origin read of the response, but the server-side execution still happens.

### Remediation

Use Flask-WTF CSRF tokens or verify `Origin`/`Referer` headers. See [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
