## Finding 1: Signed Integer Overflow — Negative Total Price

**File:** `main.c`
**Lines:** 27–32
**CWE:** CWE-681 — Incorrect Conversion Between Numeric Types / CWE-190 — Integer Overflow or Wraparound
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```c
unsigned int total_u = quantity * (unsigned int) FIXED_PRICE;
int total_s = (int) total_u;   // line 28

printf("Total price: %d euros\n", total_s);   // line 32
```

### Description
Any `quantity` value between `INT_MAX + 1` (2 147 483 648) and `UINT_MAX` (4 294 967 295) fits cleanly in `unsigned int`, passes the `quantity == 0` guard, and results in `total_u` holding a value that, when cast to `int`, wraps to a **negative number**. In C, converting an `unsigned int` value that exceeds `INT_MAX` to `int` is **implementation-defined behaviour** (C11 §6.3.1.3p3) — on virtually every real platform it sign-wraps, producing a negative total. For example, entering `"2147483648"` yields `Total price: -2147483648 euros`. In any system that propagates this total to a payment processor or account ledger, a negative value means a **credit or refund** rather than a charge.

### Prioritization
This is the highest-priority finding. It is directly reachable via a single user-supplied string, requires zero authentication or prerequisites, and produces exploitable incorrect financial output. The negative-price bypass is a classic integer-conversion class bug (CWE-190/681) with well-documented real-world financial impact.

**Counterfactual invalidation:** Replacing `int total_s = (int) total_u` with `unsigned int total_u` throughout — and printing with `%u` — eliminates the vulnerability entirely.

### Exploitability Notes
- **Exploit Preconditions:** Enter any decimal string whose numeric value is in the range [2 147 483 648, 4 294 967 295] (e.g., `"2147483648"`, `"3000000000"`, `"4294967295"`). The `-` guard on line 16 is irrelevant; these are positive decimal strings.
- **Concrete attacker input:** `echo "2147483648" | ./a.out` → `Total price: -2147483648 euros`
- **Uncertainty Boundary:** The C standard calls this implementation-defined, not undefined behaviour for the cast; on all major compilers/platforms (GCC, Clang, MSVC) it wraps as expected, making exploitation reliable.

### Remediation
Remove the signed type entirely. The total is conceptually non-negative, so keep it unsigned throughout:

```c
// Before (vulnerable)
unsigned int total_u = quantity * (unsigned int) FIXED_PRICE;
int total_s = (int) total_u;
printf("Total price: %d euros\n", total_s);

// After — no signed conversion, no overflow risk
unsigned int total_u = quantity * (unsigned int) FIXED_PRICE;
printf("Total price: %u euros\n", total_u);
```

If a signed output type is required, **range-check before casting**:

```c
if (total_u > (unsigned int)INT_MAX) {
    puts("Error: Total exceeds maximum displayable value.");
    return 1;
}
int total_s = (int) total_u;
printf("Total price: %d euros\n", total_s);
```

## Finding 2: Integer Truncation — strtoul Result Silently Narrowed to `unsigned int`

**File:** `main.c`
**Lines:** 21
**CWE:** CWE-197 — Numeric Truncation Error
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```c
unsigned int quantity = (unsigned int) strtoul(input, NULL, 10);
```

### Description
`strtoul` returns `unsigned long`, which on 64-bit Linux is 64 bits wide. Casting to `unsigned int` (32 bits) silently discards the upper 32 bits when the parsed value exceeds `UINT_MAX`. Two exploitable sub-cases exist:

1. **Undercharge via modular wrap:** Input `"4294967297"` (UINT_MAX + 2) → `strtoul` = 4 294 967 297 → `quantity` = 1 → `Total price: 1 euros`, even though the user claimed 4+ billion items. In a system where quantity controls inventory or access counts, an attacker gets credit for a massive quantity while paying for one.

2. **Undetected strtoul range overflow:** Inputs like `"999999999999999999999"` cause `strtoul` to return `ULONG_MAX` and set `errno = ERANGE` — but the code never checks `errno`. On 64-bit, `(unsigned int)ULONG_MAX = UINT_MAX = 4 294 967 295`, which then feeds directly into Finding 1's negative-total path.

### Prioritization
Lower than Finding 1 because the truncation itself requires a larger input to manifest, but it compounds Finding 1 by creating a second path to extreme `quantity` values. Fix both together.

### Exploitability Notes
- **Exploit Preconditions:** Enter a decimal string whose value exceeds `UINT_MAX` (e.g., `"4294967297"`, `"8589934594"`).
- **Concrete attacker input:** `echo "4294967297" | ./a.out` → `Your entered quantity: 1` / `Total price: 1 euros` (quantity 4,294,967,297 billed as 1).
- **Uncertainty Boundary:** On a 32-bit platform `unsigned long == unsigned int`, so the truncation path disappears; the strtoul ERANGE path still applies.

### Remediation
Validate the `unsigned long` value against `UINT_MAX` **before** truncating, and check `errno` for strtoul range errors:

```c
#include <errno.h>
#include <limits.h>

errno = 0;
char *endptr;
unsigned long raw = strtoul(input, &endptr, 10);

if (endptr == input || (*endptr != '\n' && *endptr != '\0')) {
    puts("Error: Invalid input – expected a positive integer.");
    return 1;
}
if (errno == ERANGE || raw > UINT_MAX) {
    puts("Error: Quantity is too large.");
    return 1;
}
unsigned int quantity = (unsigned int) raw;
```

- [CERT C INT35-C: Use correct integer precisions](https://wiki.sei.cmu.edu/confluence/display/c/INT35-C.+Use+correct+integer+precisions)

## Finding 3: Incomplete Input Validation — NULL `endptr` in `strtoul`

**File:** `main.c`
**Lines:** 21
**CWE:** CWE-20 — Improper Input Validation
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```c
unsigned int quantity = (unsigned int) strtoul(input, NULL, 10);
```

### Description
Passing `NULL` as `strtoul`'s `endptr` discards all parse error information. The input `"123abc"` silently parses as `123`; `"abc"` returns 0 (caught by the zero guard, but silently — no message distinguishing "you typed zero" from "you typed garbage"). This masks user errors and could silently accept malformed values in more complex downstream logic.

### Prioritization
Lowest priority — no direct exploitable security impact in the current code, but it is the root cause pattern that allows the strtoul misuse in Finding 2 to go undetected. The remediation for Finding 2 already fixes this.

### Exploitability Notes
- **Exploit Preconditions:** Enter a string starting with digits followed by non-digits (e.g., `"5abc"`).
- **Concrete attacker input:** `echo "5abc" | ./a.out` → accepted and priced as 5 items with no warning.
- **Uncertainty Boundary:** No direct security impact in isolation; risk is elevated if surrounding code is extended.

### Remediation
Use `endptr` and validate that the full input was consumed (covered by the corrected snippet in Finding 2).

### References
- [CWE-20: Improper Input Validation](https://cwe.mitre.org/data/definitions/20.html)
