## Finding 1: Unsigned-to-Signed Integer Conversion Yields Negative Price

**Finding ID:** `APPSEC-c4f3a82d9e`
**File:** `main.c`
**Lines:** 27–32
**CWE:** CWE-196 — Unsigned to Signed Conversion Error
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```c
unsigned int total_u = quantity * (unsigned int) FIXED_PRICE;
int total_s = (int) total_u; 

printf("Your entered quantity: %u\n", quantity);
printf("Fixed price per item is: %d euro\n", FIXED_PRICE);
printf("Total price: %d euros\n", total_s);
```

### Description
`total_u` is an `unsigned int` that can hold values up to 4,294,967,295 (`UINT_MAX`). Casting it to `int total_s` without an upper-bound guard is implementation-defined when `total_u > INT_MAX` (2,147,483,647). On every major two's-complement platform this produces a **negative value**. Because the code then prints `total_s` as the final price, an attacker who enters "2147483648" causes the program to report "Total price: -2147483648 euros." In any real commerce integration where this output feeds a billing system, a negative total would mean the customer is owed money rather than charged — a classic integer-conversion price-inversion attack.

### Prioritization
This is the top-priority finding. The source-to-sink path is direct and requires no preconditions beyond entering a number ≥ 2^31.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can provide stdin input ≥ 2,147,483,648. No authentication or special access required.
- **Uncertainty Boundary:** Impact depends on whether the caller or downstream system consumes the printed string or the process exit code. If the printed total is parsed by a billing service, financial fraud is possible. If the program is purely informational with no downstream consumer, the impact is limited to display corruption.

### Counterfactual
Adding `if (total_u > (unsigned int)INT_MAX)` before the cast and rejecting the input would eliminate this finding.

### Remediation
Eliminate the unsigned→signed cast entirely. Keep arithmetic in `unsigned int` and use the `%u` format specifier, or add an explicit upper-bound check before casting:

```c
/* Option A — remove the cast; print unsigned directly */
unsigned int total = quantity * (unsigned int) FIXED_PRICE;
printf("Your entered quantity: %u\n", quantity);
printf("Fixed price per item is: %d euro\n", FIXED_PRICE);
printf("Total price: %u euros\n", total);   /* %u, not %d */

/* Option B — guard before cast if signed output is required downstream */
unsigned int total_u = quantity * (unsigned int) FIXED_PRICE;
if (total_u > (unsigned int)INT_MAX) {
    puts("Error: Quantity exceeds maximum allowed value.");
    return 1;
}
int total_s = (int) total_u;
```

Option A is preferred: it removes the type mismatch entirely and requires no magic constants.

## Finding 2: `strtoul` Overflow and Truncation Not Detected

**Finding ID:** `APPSEC-7b2e5f3a1c`
**File:** `main.c`
**Lines:** 21
**CWE:** CWE-252 — Unchecked Return Value (secondary: CWE-197 — Numeric Truncation Error)
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```c
unsigned int quantity = (unsigned int) strtoul(input, NULL, 10);
```

### Description
`strtoul` returns `unsigned long` (64 bits on LP64 Linux). Two problems compound here. First, when the input exceeds `ULONG_MAX`, `strtoul` saturates to `ULONG_MAX` and sets `errno = ERANGE` — but `errno` is never checked. Second, the `unsigned long` result is silently truncated to `unsigned int` by the cast; on a 64-bit system, any value above `UINT_MAX` loses its upper 32 bits. Concretely, entering "99999999999999999999999" yields `strtoul` → `ULONG_MAX` → cast → `UINT_MAX` (4,294,967,295) → quantity passes the `!= 0` guard → cast to `int` in Finding 1 produces -1. This is a second, distinct path to a negative price output that also bypasses the intent of the overflow guard in Finding 1. The `NULL` endptr also means trailing non-numeric characters (e.g., "12abc") are silently accepted as 12 with no error, which makes the validation surface ill-defined.

### Prioritization
P2 — lower than Finding 1 because it is a contributing path to the same negative-price impact and requires a very long numeric string rather than a precise 32-bit boundary value. Fixing Finding 1 (adding the `total_u > INT_MAX` guard) mitigates this path, but the root cause should also be fixed here.

### Exploitability Notes
- **Exploit Preconditions:** Attacker provides a numeric string exceeding 64 digits (overflows `unsigned long`) or a large-but-valid value such that the `unsigned int` truncation discards upper bits.
- **Uncertainty Boundary:** On LP32 platforms where `long` and `int` are both 32 bits, `strtoul` cannot return values beyond `UINT_MAX`, removing the truncation concern — but the `errno` gap remains.

### Counterfactual
Using `endptr` validation and an `ERANGE` check would make this finding invalid.

### Remediation
```c
#include <errno.h>

char *endptr;
errno = 0;
unsigned long raw = strtoul(input, &endptr, 10);

/* reject non-numeric input, trailing garbage, and overflow */
if (endptr == input || (*endptr != '\n' && *endptr != '\0')
        || errno == ERANGE || raw == 0 || raw > UINT_MAX) {
    puts("Error: Invalid or out-of-range quantity.");
    return 1;
}

unsigned int quantity = (unsigned int) raw;
```

This validates that the entire input was consumed, that no overflow occurred in `strtoul`, and that the value fits within `unsigned int` before the narrowing cast.
