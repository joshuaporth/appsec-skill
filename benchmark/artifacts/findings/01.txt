## Finding 1: Broken Authentication — Stub Always Returns `None`

**File:** `main.py`
**Lines:** 8–10
**CWE:** CWE-287 — Improper Authentication
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```python
def is_authenticated_user():
    # This function checks if the user is authenticated and is omitted for brevity
   pass
```

### Description
`is_authenticated_user()` contains only `pass`, which causes Python to return `None` implicitly. At line 14, `if not is_authenticated_user()` evaluates to `if not None` → `True` on every single request, unconditionally redirecting all traffic to the login page. No authenticated code path is ever reachable. Because the comment states "omitted for brevity," this is a placeholder stub, but any deployment of this code as-is means the home page and the redirect feature are completely inaccessible and the intended access-control model does not exist.

### Prioritization
Highest priority. Broken auth is a foundational issue that makes the rest of the authenticated flow (including Finding 2) unreachable. Must be fixed first. Counterfactual: replacing the stub body with a real session/token check that returns a truthy value on valid auth would invalidate this finding.

### Exploitability Notes
- **Exploit Preconditions:** None — the flaw is in the code path itself; every request triggers it
- **Uncertainty Boundary:** The comment "omitted for brevity" signals intentional placeholder, but any deployment without replacing it leaves authentication entirely broken

### Remediation
Replace the stub with real session verification:

```python
from flask import session

def is_authenticated_user():
    return bool(session.get('user_id'))

@app.route('/login', methods=['GET', 'POST'])
def login():
    if request.method == 'POST':
        username = request.form.get('username')
        password = request.form.get('password')
        if validate_credentials(username, password):   # bcrypt check against DB
            session['user_id'] = username
            return redirect(url_for('home'))
        return 'Invalid credentials', 401
    return 'Login Page'
```

Set a strong secret key so sessions cannot be forged:

```python
import secrets
app.secret_key = secrets.token_hex(32)   # load from env var in production
```

**Why:** `session.get('user_id')` returns a truthy value only when the login endpoint explicitly set it, and Flask signs the session cookie with `secret_key`, preventing forgery.

## Finding 2: Open Redirect (with Potential HTTP Header Injection)

**File:** `main.py`
**Lines:** 18–21
**CWE:** CWE-601 — URL Redirection to Untrusted Site / CWE-113 — HTTP Response Splitting
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** MEDIUM

### Vulnerable Code
```python
redirect_url = request.args.get('redirect_url')
if redirect_url:
    logging.info(f'Redirecting to: {redirect_url}')
    return redirect(redirect_url)
```

### Description
`redirect_url` is sourced directly from the query string and passed unvalidated to Flask's `redirect()`, which sets it verbatim as the `Location` response header. An attacker can supply any absolute URL (e.g., `/?redirect_url=https://evil.com`) to send authenticated users to a phishing or malware site. Additionally, Werkzeug versions prior to 2.1 do not strip `\r\n` from redirect targets; an attacker supplying `%0d%0a` sequences could inject arbitrary response headers or split the HTTP response (CWE-113). Confidence is MEDIUM because this code path is currently unreachable (blocked by the always-failing auth stub in Finding 1), but the vulnerability will be live once auth is corrected.

### Prioritization
Co-equal P1 with Finding 1 — must be fixed together when auth is implemented. Counterfactual: replacing `redirect(redirect_url)` with a strict-allowlist check or a relative-only redirect would invalidate this finding.

### Exploitability Notes
- **Exploit Preconditions:** User must be authenticated (requires Finding 1 to be fixed first); attacker crafts link with `redirect_url=https://evil.com` and sends it to the victim
- **Uncertainty Boundary:** CRLF injection exploitability depends on Werkzeug version; no `requirements.txt` in scope to confirm exact version

### Remediation
Restrict redirects to same-origin relative paths only, or enforce a strict allowlist:

```python
from urllib.parse import urlparse

ALLOWED_HOSTS = {'app.example.com'}   # extend as needed

def safe_redirect(url: str):
    parsed = urlparse(url)
    # Allow only relative paths (no scheme, no netloc)
    if not parsed.scheme and not parsed.netloc:
        return redirect(url)
    # Or allow an explicit allowlist of hosts
    if parsed.netloc in ALLOWED_HOSTS:
        return redirect(url)
    return redirect(url_for('home'))   # fallback: ignore untrusted destination

@app.route('/')
def home():
    if not is_authenticated_user():
        return redirect(url_for('login'))

    redirect_url = request.args.get('redirect_url')
    if redirect_url:
        return safe_redirect(redirect_url)

    return 'Welcome to the home page!'
```

**Why:** Checking `parsed.netloc` rejects absolute URLs pointing to foreign origins; the allowlist handles legitimate cross-origin redirects without accepting arbitrary attacker-controlled destinations.

## Finding 3: Sensitive User Input Written to Logs

**File:** `main.py`
**Lines:** 20
**CWE:** CWE-532 — Insertion of Sensitive Information into Log File
**OWASP Category:** A09:2021 – Security Logging and Monitoring Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** MEDIUM

### Vulnerable Code
```python
logging.info(f'Redirecting to: {redirect_url}')
```

### Description
The raw attacker-controlled `redirect_url` value is written to the application log without any sanitization. If logs are stored in a SIEM, shipped to a log aggregator, or accessible to developers, this exposes attacker payloads (including any embedded credentials in the URL such as `https://user:pass@host/`) and pollutes audit trails. This is currently a dead code path (see Finding 1), but will become active once auth is implemented.

### Prioritization
Lowest priority of the three findings; exploitability depends on log access, which is out of scope. Fix alongside Findings 1 and 2.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must gain read access to log storage; more relevant if logs are exposed via a misconfigured dashboard or stored in a shared location
- **Uncertainty Boundary:** Impact depends on log retention, access controls, and whether the application handles credential-bearing URLs

### Remediation
Log only the parsed hostname (not the full URL) and never log credentials embedded in URLs:

```python
from urllib.parse import urlparse

if redirect_url:
    destination = urlparse(redirect_url).hostname or '(relative)'
    logging.info('Redirecting authenticated user to host: %s', destination)
    return safe_redirect(redirect_url)
```

**Why:** Extracting only the hostname removes credentials, paths, and attacker-controlled query strings from the log entry while preserving enough context for auditing.

- https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/532.html
