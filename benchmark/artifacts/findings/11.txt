## Finding 1: Direct Port Exposure Bypasses Nginx Admin Block — Missing App-Layer Authorization

**Finding ID:** `APPSEC-3f2a91b6c4`
**File:** `docker-compose.yml` line 9 + `main.py` lines 5–7 + `nginx.conf` lines 11–13
**Lines:** docker-compose.yml:9 / main.py:5–7
**CWE:** CWE-284 — Improper Access Control / CWE-862 — Missing Authorization
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code

```yaml
# docker-compose.yml:9
ports:
  - "5000:5000"
```

```python
# main.py:5-7
@app.route('/admin')
def admin():
    return "Admin area accessed!"
```

```nginx
# nginx.conf:11-13
location = /admin {
    deny all;
}
```

### Description

The entire `/admin` access control architecture depends on a single Nginx `deny all` rule. Flask is simultaneously bound to `0.0.0.0:5000` and that port is published to the host via `"5000:5000"` in docker-compose.yml. Any client with network access to the host on port 5000 can issue `GET http://<host>:5000/admin` and receive the admin response directly, with Nginx never in the request path. The `/admin` route itself has no authentication, session check, or role verification of any kind — the Nginx layer is the sole (and entirely bypassable) control.

A second architectural mistake amplifies this: Nginx is configured to `proxy_pass http://host.docker.internal:5000`, meaning it routes back through the host rather than over the internal Docker bridge. This design forces port 5000 to be published on the host to be reachable by Nginx at all, directly causing the exposure. If Nginx proxied to the Flask service by its compose service name (`http://flask-app:5000`), port 5000 would not need to be published and the bypass route would not exist.

### Prioritization

Highest-priority finding in this review. No preconditions beyond network reachability to port 5000. Exploitable with a single HTTP request. All other findings are secondary to this one.

### Exploitability Notes

- **Exploit Preconditions:** Attacker must be able to reach port 5000 on the host. In a cloud deployment with a default-open security group or in any environment where port 5000 is internet-accessible, this is a zero-click bypass.
- **Concrete attacker input:** `curl http://<host>:5000/admin` — returns `"Admin area accessed!"` immediately.
- **Uncertainty Boundary:** Impact depends on what the `/admin` handler actually does in a production version of this app. If it is a stub, practical impact is limited now but the bypass is fully confirmed.

### Remediation

**Step 1** — Remove the published port from docker-compose.yml so Flask is only reachable on the internal Docker network:

```yaml
# docker-compose.yml — REMOVE the ports stanza for flask-app
services:
  flask-app:
    build: .
    # Remove: ports: ["5000:5000"]
    networks:
      - app-network
```

**Step 2** — Fix the nginx `proxy_pass` to use the internal Docker service name instead of routing through the host:

```nginx
# nginx.conf
location / {
    proxy_pass http://flask-app:5000;   # internal Docker DNS, not host.docker.internal
}
```

**Step 3** — Add app-layer authentication on the `/admin` route regardless of proxy configuration (defense in depth). Proxy rules are operational configuration, not application security:

```python
from flask import Flask, abort, request
from functools import wraps

app = Flask(__name__)

ADMIN_TOKEN = os.environ.get("ADMIN_TOKEN")  # set via Docker secret or env var

def require_admin(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        token = request.headers.get("X-Admin-Token", "")
        if not ADMIN_TOKEN or not hmac.compare_digest(token, ADMIN_TOKEN):
            abort(403)
        return f(*args, **kwargs)
    return decorated

@app.route('/admin')
@require_admin
def admin():
    return "Admin area accessed!"
```

**Counterfactual invalidation:** removing `"5000:5000"` from docker-compose.yml and pointing nginx to `http://flask-app:5000` eliminates the network-level bypass. Adding `@require_admin` eliminates the auth gap independently.

## Finding 2: Nginx Admin Block Uses Exact-Match Only — Trailing-Slash Path Not Protected

**Finding ID:** `APPSEC-7d4e82a15f`
**File:** `nginx.conf`
**Lines:** 11–13
**CWE:** CWE-284 — Improper Access Control
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code

```nginx
location = /admin {
    deny all;
}
```

### Description

The Nginx `location = /admin` directive uses an exact-match operator (`=`), which matches only the literal string `/admin`. A request for `/admin/` (trailing slash) does **not** match this block and instead falls through to the `location /` proxy rule, forwarding the request to Flask. Flask's default `strict_slashes=True` behavior causes it to respond with a 308 redirect to `/admin`, which Nginx then blocks when the client follows the redirect — so the current code does not produce a direct content leak through the proxy. However, this is a fragile, single-path dependency: any change to Flask routing (e.g., adding a second route at `/admin/`, setting `strict_slashes=False`, or adding a distinct route under `/admin/<anything>`) would silently break the protection without changing the Nginx config. The edge-only control with no app-layer fallback means the security posture is one route annotation away from full bypass.

### Prioritization

P2, secondary to Finding 1 (direct port bypass). By itself the trailing slash does not currently expose admin content through the proxy due to Flask's redirect behavior, but the architectural brittleness warrants fixing before any admin functionality is expanded.

### Exploitability Notes

- **Exploit Preconditions (current state):** The trailing-slash bypass through Nginx currently results in a redirect back to `/admin`, which Nginx blocks. Direct bypass requires port 5000 access (see Finding 1).
- **Exploit Preconditions (future risk):** If Flask routing changes, `/admin/` becomes directly accessible through port 80 with no code change to Nginx.
- **Concrete attacker input:** `GET /admin/ HTTP/1.1` → proxied to Flask → Flask 308 → client follows → Nginx `deny all` (currently safe, but brittle).
- **Uncertainty Boundary:** Exact Nginx behavior with more complex path variations (e.g., `/admin%2F`, `/admin/.`) depends on Nginx version and `merge_slashes` settings.

### Remediation

Replace the exact-match block with a prefix-match that also covers sub-paths and trailing slashes:

```nginx
# Before — exact match only, /admin/ falls through
location = /admin {
    deny all;
}

# After — prefix block covers /admin, /admin/, and /admin/*
location ^~ /admin {
    deny all;
}
```

Simultaneously, enforce authorization in Flask (see Finding 1 remediation Step 3) so that even if a path variant evades the Nginx rule, the app still checks credentials.

### References
- [Nginx location matching order](https://nginx.org/en/docs/http/ngx_http_core_module.html#location)
- [OWASP: Access Control Design Principles](https://cheatsheetseries.owasp.org/cheatsheets/Access_Control_Cheat_Sheet.html)

## Finding 3: Flask Built-In Development Server Used in Production

**Finding ID:** `APPSEC-a1c3f9d827`
**File:** `main.py` / `Dockerfile`
**Lines:** main.py:13–14 / Dockerfile:14
**CWE:** CWE-16 — Configuration
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code

```python
# main.py:13-14
if __name__ == "__main__":
    app.run(host='0.0.0.0', port=5000)
```

```dockerfile
# Dockerfile:14
CMD ["python", "main.py"]
```

### Description

The container runs Flask's built-in Werkzeug development server (`python main.py`). The Werkzeug server is single-threaded, not designed for concurrent production traffic, and emits more verbose error output than a production WSGI server. While `debug=False` is the default (and is not set to `True` here, so the interactive debugger is not exposed), the dev server lacks production-grade hardening. If debug mode were accidentally enabled in a future change, the Werkzeug PIN-protected debugger allows arbitrary code execution on the server.

### Prioritization

P3, lowest priority. No immediate exploit path; informational risk for production deployments.

### Exploitability Notes

- **Exploit Preconditions:** `debug=True` would need to be set for the Werkzeug debugger to activate; not currently set.
- **Uncertainty Boundary:** Whether this is a production or development environment changes the risk weight.

### Remediation

Replace the dev server with a production WSGI server in the Dockerfile:

```dockerfile
# Install gunicorn alongside app dependencies
RUN pipenv install --deploy --system gunicorn

# Replace dev server invocation
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "--workers", "4", "main:app"]
```

Remove the `app.run()` block from `main.py` (it is only needed for local dev invocation, not for production containers):

```python
# main.py — remove the __main__ block for production
# Keep it only if needed for local debugging behind a feature flag
```

## Finding 4: Missing HTTP Security Response Headers

**Finding ID:** `APPSEC-b8e42d7c91`
**File:** `main.py` / `nginx.conf`
**Lines:** main.py (global), nginx.conf (server block)
**CWE:** CWE-16 — Configuration
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** INFO
**Confidence:** HIGH

### Vulnerable Code

```python
# main.py — no security headers configured
app = Flask(__name__)
```

```nginx
# nginx.conf — no add_header directives in server block
server {
    listen 80;
    server_name example.com;
    ...
}
```

### Description

Neither Flask nor Nginx adds standard HTTP security response headers. Missing headers of note: `X-Content-Type-Options: nosniff` (MIME sniffing protection), `X-Frame-Options: DENY` (clickjacking protection), `Content-Security-Policy` (XSS/injection mitigation), and `Strict-Transport-Security` (HTTPS enforcement). The application also serves over HTTP with no TLS, meaning any token or session data sent in future would be transmitted in cleartext. While the current app has no sensitive responses or forms, these headers are baseline hygiene and should be in place before admin or authenticated functionality is added.

### Prioritization

Lowest priority (INFO). No current user-facing content to exploit. Becomes higher priority when the admin area serves real functionality.

### Exploitability Notes

- **Exploit Preconditions:** Requires a separate XSS or MIME-sniffing vector; none exist in current code.
- **Uncertainty Boundary:** Impact is entirely dependent on future feature additions.

### Remediation

Add security headers at the Nginx layer (preferred for centralized control):

```nginx
server {
    listen 80;
    server_name example.com;

    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;
    add_header Referrer-Policy "no-referrer" always;
    add_header Content-Security-Policy "default-src 'none'" always;

    location = /admin {
        deny all;
    }
    location / {
        proxy_pass http://flask-app:5000;
    }
}
```

Or use Flask-Talisman for app-layer header management:

```python
from flask_talisman import Talisman
Talisman(app, force_https=False, content_security_policy={'default-src': "'none'"})
```

### References
- [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/)
- [MDN HTTP Security Headers](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers#security)
