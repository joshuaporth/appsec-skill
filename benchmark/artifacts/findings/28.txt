## Finding 1: Web Cache Deception — Unauthenticated API Key Exfiltration

**Finding ID:** `APPSEC-f3a82c1d09`
**File:** `nginx.conf` (lines 17–25) + `main.js` (line 52)
**Lines:** `nginx.conf:17–25`, `main.js:52–61`
**CWE:** CWE-525 — Use of Web Browser Cache Containing Sensitive Information / CWE-284 — Improper Access Control
**OWASP Category:** A05:2021 – Security Misconfiguration / A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```nginx
# nginx.conf:17–25
location ~* \.(css|js|jpg|png|gif)$ {
    proxy_pass http://express-app:5000;
    expires 30d;
    proxy_cache STATIC;  
    proxy_cache_valid 200 1h;
    proxy_cache_valid any 5m;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    add_header X-Cached $upstream_cache_status;
}
```
```javascript
// main.js:52–61
app.get("/profile*", (req, res) => {
    if (!req.session.user) {
        return res.redirect("/login");
    }

    const user = req.session.user;
    const api_key = users_db[user].api_key;

    res.send(`${user} - API Key: ${api_key}`);
});
```

### Description
The nginx `proxy_cache` location block caches any response whose URL path ends in `.css`, `.js`, `.jpg`, `.png`, or `.gif`. The default `proxy_cache_key` is `$scheme$proxy_host$request_uri`, which **does not include the `Cookie` header**. Express's wildcard route `/profile*` matches any path beginning with `/profile` — including `/profile.css`, `/profile.jpg`, etc. An attacker who tricks an authenticated victim into requesting `http://example.com/profile.css` will cause nginx to cache the victim's authenticated API key response (keyed only by URL, not by session). Any subsequent unauthenticated request to `/profile.css` receives the cached response containing the victim's API key. The response is cached for one hour per `proxy_cache_valid 200 1h`. The Express app sets no `Cache-Control: no-store` header on the `/profile*` handler and no `proxy_no_cache`/`proxy_cache_bypass` directive exists in the nginx config.

### Prioritization
This is the highest-priority finding. It allows full unauthenticated exfiltration of a logged-in user's API key with no prior access required beyond tricking the victim into clicking a link. No brute force, no injection, no session required.

### Exploitability Notes
- **Exploit Preconditions:** (1) A victim must be authenticated and navigate to a crafted URL like `http://example.com/profile.css` (via phishing, `<img src="...">`, clickjacking, etc.). (2) nginx must not have been explicitly configured with `proxy_cache_key` including `$cookie_*`. Both are true as written.
- **Uncertainty Boundary:** If nginx is fronted by a CDN that normalizes extensions, the cache key behavior at that outer layer might differ. Within this config as written, exploitation is deterministic.
- **Counterfactual invalidation:** Adding `Cache-Control: no-store, no-cache` in the Express `/profile*` handler (or `proxy_no_cache $cookie_session_id;` in nginx) would prevent caching of authenticated responses and eliminate this vulnerability.
- **Concrete attacker input:** `GET /profile.css HTTP/1.1` (no `Cookie` header) — after the victim has primed the cache.

### Remediation
Fix on both layers — defense in depth:

```javascript
// main.js — Express: prevent any caching of authenticated responses
app.get("/profile*", (req, res) => {
    if (!req.session.user) {
        return res.redirect("/login");
    }
    // Prevent reverse proxies from caching this authenticated response
    res.setHeader("Cache-Control", "no-store, no-cache, must-revalidate, private");
    res.setHeader("Pragma", "no-cache");

    const user = req.session.user;
    const api_key = users_db[user].api_key;
    res.send(`${user} - API Key: ${api_key}`);
});
```

```nginx
# nginx.conf — bypass and disable cache for any request carrying a session cookie
location ~* \.(css|js|jpg|png|gif)$ {
    proxy_pass http://express-app:5000;
    proxy_cache STATIC;
    proxy_cache_key "$scheme$proxy_host$request_uri";
    proxy_no_cache     $cookie_connect_sid;   # express-session default cookie name
    proxy_cache_bypass $cookie_connect_sid;
    proxy_cache_valid 200 1h;
    proxy_cache_valid any 5m;
    add_header X-Cached $upstream_cache_status;
}
```

Also, replace the wildcard Express route with an exact match to eliminate the surface entirely:
```javascript
// Change:
app.get("/profile*", (req, res) => { ... });
// To:
app.get("/profile", (req, res) => { ... });
```

- [PortSwigger: Web Cache Deception](https://portswigger.net/web-security/web-cache-deception)
- [CWE-525: Information Exposure Through Browser Caching](https://cwe.mitre.org/data/definitions/525.html)

## Finding 2: Hardcoded Credentials and Secrets

**Finding ID:** `APPSEC-c7b912a4f5`
**File:** `main.js`
**Lines:** 7–10, 15
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A07:2021 – Identification and Authentication Failures / A02:2021 – Cryptographic Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```javascript
const users_db = {
    "admin": {
        "password": "password",
        "api_key": "API-KEY-1234567890-SECRET",
    }
};

app.use(session({ secret: 'supersecretkey'}));
```

### Description
Three secrets are hardcoded in source: a trivial cleartext password (`"password"`), an API key (`"API-KEY-1234567890-SECRET"`), and an `express-session` signing secret (`'supersecretkey'`). The session secret is used to HMAC-sign session cookies; with it known, an attacker can forge session cookies for any username. The cleartext password storage means any code reviewer, contractor, or Git history reader can authenticate as admin without attacking the running system. The API key is directly exposed in source to the same audience.

### Prioritization
P1, ranked second after the web cache deception finding. A compromised session secret enables direct admin impersonation without network access; a leaked API key is equivalent to full account takeover.

### Exploitability Notes
- **Exploit Preconditions:** Read access to source code (including Git history).
- **Uncertainty Boundary:** If this is truly a stand-in for an external secret store (as the comments suggest), actual deployment may use environment variables. However, as committed, these are real values.
- **Counterfactual invalidation:** Replacing the values with `process.env.SESSION_SECRET`, `process.env.ADMIN_PASSWORD`, and `process.env.ADMIN_API_KEY` and rotating the current values would eliminate this finding.

### Remediation
```javascript
// Load secrets from environment variables — never from source
const SESSION_SECRET = process.env.SESSION_SECRET;
if (!SESSION_SECRET) throw new Error("SESSION_SECRET env var is required");

app.use(session({
    secret: SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: { secure: true, httpOnly: true, sameSite: 'strict' }
}));
```

For passwords: store only a bcrypt hash in the database, not plaintext:
```javascript
const bcrypt = require('bcrypt');
// At user creation:
const hash = await bcrypt.hash(plaintextPassword, 12);
// At login:
const match = await bcrypt.compare(req.body.password, stored_hash);
```

## Finding 3: Authentication Bypass via JavaScript Prototype Pollution

**Finding ID:** `APPSEC-8d4e231bc7`
**File:** `main.js`
**Lines:** 30–34
**CWE:** CWE-284 — Improper Access Control / CWE-1321 — Improperly Controlled Modification of Object Prototype Attributes
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.post("/login", (req, res) => {
    const { username, password } = req.body;

    if (users_db[username] && users_db[username].password === password) {
        req.session.user = username;
        return res.redirect('/dashboard');
    }
```

### Description
`users_db` is a plain JavaScript object, so `users_db[username]` resolves inherited prototype properties when `username` is `"toString"`, `"valueOf"`, `"hasOwnProperty"`, `"constructor"`, `"__proto__"`, etc. These prototype properties are truthy (they are functions). The second condition `users_db[username].password` accesses `.password` on the function object, which is `undefined`. If the POST body omits the `password` field entirely, `req.body.password` is also `undefined`, so `undefined === undefined` evaluates to `true`. The attacker receives a valid authenticated session under the username `"toString"` (or any other prototype property name) with no password required. A crafted `POST /login` body of `username=toString` (with no `password` field) produces an authenticated session, granting full access to all authenticated routes.

### Prioritization
P2. Exploitable auth bypass, but in the current hardcoded setup the attacker's session maps to `"toString"` — not `"admin"` — so `users_db["toString"].api_key` returns `undefined`, limiting data exposure. Impact increases significantly if the app ever stores real user data or if the attacker combines this with other vulnerabilities.

### Exploitability Notes
- **Exploit Preconditions:** Send a POST to `/login` with `Content-Type: application/x-www-form-urlencoded`, body `username=toString`, and **no `password` field**.
- **Uncertainty Boundary:** If a future developer adds real user data to `users_db`, the bypass yields a valid session for a ghost account; the exposed data is still limited to the prototype-name account's fields. Impact is bounded by the data model.
- **Counterfactual invalidation:** Using `Object.create(null)` for `users_db` removes the prototype chain; alternatively, `Object.hasOwn(users_db, username)` as a guard eliminates the prototype property lookup.

### Remediation
```javascript
// Option A: use a null-prototype object to eliminate inherited properties
const users_db = Object.create(null);
users_db["admin"] = { password: "...", api_key: "..." };

// Option B: guard every lookup with Object.hasOwn
app.post("/login", (req, res) => {
    const { username, password } = req.body;
    if (Object.hasOwn(users_db, username) && users_db[username].password === password) {
        req.session.user = username;
        return res.redirect('/dashboard');
    }
    return res.send("Invalid credentials! <a href='/login'>Try again</a>");
});
```

- [CWE-1321: Prototype Pollution](https://cwe.mitre.org/data/definitions/1321.html)
- [OWASP: Prototype Pollution Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Prototype_Pollution_Prevention_Cheat_Sheet.html)

## Finding 4: Missing CSRF Protection on Login Endpoint

**Finding ID:** `APPSEC-2e91f5d73a`
**File:** `main.js`
**Lines:** 17–36
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.get("/login", (req, res) => {
    res.send(`<h1>Login</h1>
        <form method='POST'>
            ...
        </form>
    `);
});

app.post("/login", (req, res) => {
    const { username, password } = req.body;
    if (users_db[username] && users_db[username].password === password) {
        req.session.user = username;
        return res.redirect('/dashboard');
    }
```

### Description
The `POST /login` endpoint performs no CSRF token validation. This enables a Login CSRF attack: an attacker hosts a page with a hidden auto-submitting form pointing to `/login` with the attacker's own credentials. When a victim (who may already be authenticated elsewhere on the domain, or whose session state the attacker wants to control) visits that page, they are silently logged into the attacker's account. In applications where post-login actions are tied to the account (e.g., stored payment methods, linked OAuth sessions), this allows the attacker to observe the victim's actions under the attacker's account.

### Prioritization
P2. Lower practical impact in this specific app (no post-login sensitive state tied to account), but Login CSRF is a well-documented real-world attack class and trivial to prevent.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must have valid credentials for the application. Victim must visit attacker-controlled page.
- **Uncertainty Boundary:** Impact depends on what authenticated users do after login; in this app it's limited to dashboard/profile views.
- **Counterfactual invalidation:** Adding CSRF token validation (`csurf` middleware or equivalent) to `POST /login` eliminates this class.

### Remediation
```javascript
const csrf = require('csurf');
const csrfProtection = csrf({ cookie: false }); // use session-bound token

app.get("/login", csrfProtection, (req, res) => {
    res.send(`<h1>Login</h1>
        <form method='POST'>
            <input type='hidden' name='_csrf' value='${req.csrfToken()}'>
            <label>Username:</label> <input type='text' name='username'><br>
            <label>Password:</label> <input type='password' name='password'><br>
            <button type='submit'>Login</button>
        </form>
    `);
});

app.post("/login", csrfProtection, (req, res) => { ... });
```

## Finding 5: Insecure Session Cookie Configuration

**Finding ID:** `APPSEC-9c6a47e82b`
**File:** `main.js`
**Lines:** 15
**CWE:** CWE-614 — Sensitive Cookie in HTTPS Session Without 'Secure' Attribute / CWE-1004 — Sensitive Cookie Without 'HttpOnly' Flag
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```javascript
app.use(session({ secret: 'supersecretkey'}));
```

### Description
The `express-session` call specifies only the `secret` field. Three critical cookie attributes are unset: `secure` (defaults to `false`) allows session cookies to be transmitted over plain HTTP, enabling network interception; `sameSite` is unset, allowing the cookie to be included in cross-origin requests (aiding CSRF); `resave` and `saveUninitialized` default to `true` in older versions, potentially creating sessions for unauthenticated requests and touching the store on every response. Additionally, no `maxAge` is set — sessions have no server-side expiry and persist for the process lifetime on the default MemoryStore. There is also no `/logout` route that calls `req.session.destroy()`, leaving users unable to invalidate their session.

### Prioritization
P2. Combined with the cleartext HTTP setup (no TLS enforced at nginx layer), the missing `secure` flag is immediately exploitable over the network.

### Exploitability Notes
- **Exploit Preconditions:** Network position to observe HTTP traffic (LAN, rogue WiFi, MitM).
- **Uncertainty Boundary:** If TLS termination happens upstream of nginx and the service is only reachable over HTTPS in practice, `secure` omission is lower risk — but defense-in-depth still requires it.
- **Counterfactual invalidation:** Setting `cookie: { secure: true, sameSite: 'strict', httpOnly: true, maxAge: 3600000 }` eliminates cookie interception and CSRF re-use via cookie inclusion.

### Remediation
```javascript
app.use(session({
    secret: process.env.SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: {
        secure: true,         // HTTPS only
        httpOnly: true,       // no JS access
        sameSite: 'strict',   // CSRF mitigation
        maxAge: 60 * 60 * 1000 // 1-hour expiry
    }
}));

// Add a logout handler
app.get("/logout", (req, res) => {
    req.session.destroy(err => {
        res.clearCookie('connect.sid');
        res.redirect('/login');
    });
});
```

### References
- [CWE-614](https://cwe.mitre.org/data/definitions/614.html)
- [OWASP: Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## Finding 6: Timing Attack on Password Comparison

**Finding ID:** `APPSEC-1f7d4a8e3c`
**File:** `main.js`
**Lines:** 30
**CWE:** CWE-208 — Observable Timing Discrepancy
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```javascript
if (users_db[username] && users_db[username].password === password) {
```

### Description
JavaScript's `===` operator short-circuits on the first mismatched byte, leaking timing information. An attacker making many login requests with differing passwords can statistically measure response time differences to determine how many leading characters of their guess are correct, enabling a byte-by-byte password oracle. The impact is limited by network jitter and the fact that passwords are stored in plaintext (removing the timing oracle advantage once you can hash-compare), but the pattern is textbook CWE-208.

### Prioritization
P3. Practically difficult to exploit over a real network due to jitter. Highest-priority remediation is switching to bcrypt (Finding 2), which makes this moot.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must make a high volume of login requests and collect sufficient statistical samples to overcome network noise.
- **Uncertainty Boundary:** Over LAN or loopback, signal-to-noise ratio increases and practical exploitation becomes more feasible.
- **Counterfactual invalidation:** Switching password storage to bcrypt and comparing with `bcrypt.compare()` removes the timing oracle entirely.

### Remediation
```javascript
const crypto = require('crypto');

// Temporary fix (until bcrypt is implemented):
if (users_db[username] && crypto.timingSafeEqual(
    Buffer.from(users_db[username].password),
    Buffer.from(password)
)) {
    req.session.user = username;
    return res.redirect('/dashboard');
}
```

Long-term: store bcrypt hashes and use `bcrypt.compare()` — which is inherently timing-safe.

- [CWE-208](https://cwe.mitre.org/data/definitions/208.html)
- [Timing Attacks on HMAC – sockpuppet.org](http://sockpuppet.org/blog/2014/02/25/safely-generate-random-numbers/)

## Finding 7: Unescaped User-Controlled Data in HTML Response

**Finding ID:** `APPSEC-3b2c9f6d7e`
**File:** `main.js`

**OWASP Category:** A03:2021 – Injection
**Priority:** P3
**Severity:** INFO
**Confidence:** LOW

### Vulnerable Code
```javascript
res.send(`${user} - API Key: ${api_key}`);
```

### Description
`user` originates from `req.session.user`, which was set from `req.body.username` at login. Neither value is HTML-escaped before insertion into the response. In the current hardcoded `users_db`, `user` can only be `"admin"`, making this unexploitable today. P3 / INFO. Not exploitable in the current code. Remediating Finding 1 (Web Cache Deception) and 2 (Hardcoded Data) are far higher priority.

```javascript
const escapeHtml = s => s
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');

res.send(`${escapeHtml(user)} - API Key: ${escapeHtml(api_key)}`);
// Or use a template engine with auto-escaping (e.g., EJS, Handlebars)
```
