## Finding 1: Web Cache Deception — Authenticated Response Caching

**File:** `nginx.conf` + `main.js`  
**Lines:** `nginx.conf:17–24` (cache rule) × `main.js:52–61` (profile route)  
**CWE:** CWE-524 — Use of Cache Containing Sensitive Information  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P1  
**Severity:** CRITICAL  
**Confidence:** HIGH

### Vulnerable Code

```nginx
# nginx.conf:17–24
location ~* \.(css|js|jpg|png|gif)$ {
    proxy_pass http://express-app:5000;
    expires 30d;
    proxy_cache STATIC;  
    proxy_cache_valid 200 1h;
    proxy_cache_valid any 5m;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
    add_header X-Cached $upstream_cache_status;
}
```

```javascript
// main.js:52–61
app.get("/profile*", (req, res) => {
    if (!req.session.user) {
        return res.redirect("/login");
    }

    const user = req.session.user;
    const api_key = users_db[user].api_key;

    res.send(`${user} - API Key: ${api_key}`);
});
```

### Description

Nginx's cache rule matches any URL whose **path ends** in `.css`, `.js`, `.jpg`, `.png`, or `.gif` — including paths like `/profile/steal.jpg`. Express's `/profile*` wildcard route matches the same URL and returns the authenticated user's API key. When an authenticated victim visits `http://example.com/profile/steal.jpg` (e.g., tricked via a phishing link or an `<img src>` tag), Nginx caches the response keyed on that URL. Any subsequent unauthenticated request to `http://example.com/profile/steal.jpg` receives the cached, victim-authenticated response — including the API key — without any session cookie.

**Attack sequence:**
1. Attacker crafts `http://example.com/profile/steal.jpg`
2. Victim (authenticated admin) visits it — intentionally or via embedded link/image
3. Nginx caches the `200 OK` response with `admin - API Key: API-KEY-1234567890-SECRET` for 1 hour
4. Attacker fetches `http://example.com/profile/steal.jpg` unauthenticated → receives the victim's API key from cache

### Prioritization

Highest-priority finding. Directly leaks the admin API key with no authentication required post-cache-population, exploitable by any network-accessible attacker. The only precondition is tricking the authenticated user into visiting a single URL — trivially achievable via social engineering or an embedded image tag.

### Exploitability Notes

- **Exploit Preconditions:** (a) Attacker can trick an authenticated user into visiting the crafted URL; (b) the URL had not been cached previously with a non-200 status
- **Uncertainty Boundary:** Default Nginx `proxy_cache_key` is `$scheme$proxy_host$request_uri` — this is confirmed as sufficient to share the cache entry across users. Behavior unchanged regardless of Nginx version within any reasonably modern release

**Counterfactual:** If the Express route were `/profile` (no wildcard) instead of `/profile*`, URLs ending in `.jpg` would not match it and would not return authenticated content — the caching rule would become harmless.

### Remediation

Three complementary fixes — apply all three for defense-in-depth:

**1. Remove the wildcard from the Express route (root cause fix):**
```javascript
// Before
app.get("/profile*", (req, res) => { ... });
// After — exact match only
app.get("/profile", (req, res) => { ... });
```

**2. Set `Cache-Control: no-store` on all authenticated responses:**
```javascript
app.get("/profile", (req, res) => {
    if (!req.session.user) return res.redirect("/login");
    res.set("Cache-Control", "no-store, no-cache, must-revalidate");
    const user = req.session.user;
    const api_key = users_db[user].api_key;
    res.send(`${user} - API Key: ${api_key}`);
});
```

**3. Scope the Nginx cache rule to never match application routes (defense-in-depth):**
```nginx
# Restrict cache to the explicit /static/ path only, not arbitrary URL endings
location /static/ {
    root /var/www/html/;
    expires 30d;
    proxy_cache STATIC;
    proxy_cache_valid 200 1h;
}
# Remove the extension-based regex cache rule entirely
```

- [OWASP Web Security Testing Guide — Testing for Web Cache Deception (WSTG-SESS-09)](https://owasp.org/www-project-web-security-testing-guide/)

## Finding 2: Hardcoded Credentials and Plaintext Password Storage

**File:** `main.js`  
**Lines:** 6–11  
**CWE:** CWE-798 — Use of Hard-coded Credentials; CWE-256 — Plaintext Storage of a Password  
**OWASP Category:** A02:2021 – Cryptographic Failures; A07:2021 – Identification and Authentication Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code

```javascript
const users_db = {
    "admin": {
        "password": "password",
        "api_key": "API-KEY-1234567890-SECRET",
    }
};
```

### Description

The admin password is stored as a plaintext string literal (`"password"`) in source code — no hashing, no salt. The admin API key is also hardcoded alongside it. Any developer with read access to this repository obtains both credentials immediately; no cracking is required. If this code is committed to version control, both secrets are permanently embedded in git history even if later removed. A proper password store would hold a slow hash (bcrypt/Argon2id); a proper secret store would hold environment-variable-injected values, not literals.

### Prioritization

P1 alongside Finding 1. Hardcoded plaintext credentials are unconditionally exploitable by any insider with repo access and require no runtime interaction.

### Exploitability Notes

- **Exploit Preconditions:** Read access to source code or git history
- **Uncertainty Boundary:** None — plaintext storage is unconditionally exploitable given repo access

### Remediation

**Passwords:** use bcrypt (cost ≥ 12) at registration time; compare with `bcrypt.compare()` at login:
```javascript
const bcrypt = require('bcrypt');

// At user creation:
const hash = await bcrypt.hash(plaintextPassword, 12);

// At login:
if (users_db[username] && await bcrypt.compare(password, users_db[username].password)) {
    req.session.user = username;
    return res.redirect('/dashboard');
}
```

**API keys and secrets:** load from environment variables, never hardcode:
```javascript
// In real code — load from process.env or a vault client
const api_key = process.env.ADMIN_API_KEY;
```

- [CWE-798: Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html)
- [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

## Finding 3: Hardcoded Session Secret

**File:** `main.js`  
**Lines:** 15  
**CWE:** CWE-798 — Use of Hard-coded Credentials  
**OWASP Category:** A02:2021 – Cryptographic Failures  
**Priority:** P1  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code

```javascript
app.use(session({ secret: 'supersecretkey'}));
```

### Description

`express-session` uses `secret` to sign session cookies with HMAC-SHA256. With a known, hardcoded value, an attacker who reads the source code can craft valid signed session cookies for arbitrary user IDs, bypassing authentication entirely — no password required. The comment `// Imagine this to be a secret loaded from a secure secret store` acknowledges the intent but does not change the actual behavior of the code.

### Prioritization

P1. Combined with Finding 2 (hardcoded credentials), a source-code reader gets both password and session-forgery capability. Remediate alongside Finding 2.

### Exploitability Notes

- **Exploit Preconditions:** Knowledge of the hardcoded secret string (read access to source or git history)
- **Uncertainty Boundary:** None — `express-session` cookie signing is deterministic given the secret

### Remediation

```javascript
// Load from environment; fail fast if not set
const SESSION_SECRET = process.env.SESSION_SECRET;
if (!SESSION_SECRET) throw new Error('SESSION_SECRET env var is required');

app.use(session({
    secret: SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: {
        httpOnly: true,
        secure: process.env.NODE_ENV === 'production', // require HTTPS in prod
        sameSite: 'lax',
    }
}));
```

Generate the secret at deploy time: `node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"` and store it in your secret manager (AWS Secrets Manager, Vault, etc.).

- [express-session security best practices](https://expressjs.com/en/resources/middleware/session.html)

## Finding 4: Session Fixation — No Session Regeneration After Login

**File:** `main.js`  
**Lines:** 27–35  
**CWE:** CWE-384 — Session Fixation  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P2  
**Severity:** MEDIUM  
**Confidence:** HIGH

### Vulnerable Code

```javascript
app.post("/login", (req, res) => {
    const { username, password } = req.body;

    if (users_db[username] && users_db[username].password === password) {
        req.session.user = username;
        return res.redirect('/dashboard');
    }
    ...
```

### Description

When login succeeds, the code writes to the existing session (`req.session.user = username`) without regenerating the session ID first. An attacker who can set a known session cookie in the victim's browser (e.g., via a subdomain XSS or network interception on HTTP) can plant a pre-known session ID, wait for the victim to authenticate, and then use that ID to access the victim's authenticated session. The `express-session` library provides `req.session.regenerate()` precisely for this purpose.

### Prioritization

P2. Real-world exploitation requires the attacker to plant a session ID in the victim's browser before login, raising the bar relative to Findings 1–3.

### Exploitability Notes

- **Exploit Preconditions:** Attacker must be able to set a session cookie in the victim's browser (requires same-site subdomain or prior MITM on HTTP)
- **Uncertainty Boundary:** Since the app runs on HTTP (no TLS), cookie interception on the network is realistic, raising this to a meaningful risk

### Remediation

```javascript
app.post("/login", (req, res) => {
    const { username, password } = req.body;

    if (users_db[username] && users_db[username].password === password) {
        req.session.regenerate((err) => {   // Issue new session ID before writing auth state
            if (err) return res.status(500).send("Session error");
            req.session.user = username;
            return res.redirect('/dashboard');
        });
        return;
    }

    return res.send("Invalid credentials! <a href='/login'>Try again</a>");
});
```

## Finding 5: Missing Security Headers

**File:** `main.js`  
**Lines:** 1–16 (app setup)  
**CWE:** CWE-693 — Protection Mechanism Failure  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P3  
**Severity:** LOW  
**Confidence:** HIGH

### Vulnerable Code

```javascript
const express = require('express');
const session = require('express-session');
const app = express();

app.use(express.urlencoded({ extended: true }));
app.use(session({ secret: 'supersecretkey'}));
// No helmet or security header middleware
```

### Description

The application omits all standard HTTP security headers. Without `helmet` (or equivalent manual header setting), responses lack: `X-Content-Type-Options` (MIME-type sniffing protection), `X-Frame-Options`/`frame-ancestors` (clickjacking protection), `Content-Security-Policy` (XSS execution restriction), and `Strict-Transport-Security` (HSTS). The profile page at `main.js:60` also performs string interpolation of the username directly into an HTML response without output encoding — if username values ever come from user-controlled registration (not the case in this hardcoded DB, but relevant at scale), this would be a stored XSS vector.

### Prioritization

P3. Defense-in-depth finding; no direct exploit path given current application behavior, but straightforward to fix.

### Exploitability Notes

- **Exploit Preconditions:** Varies by header; clickjacking requires an attacker-controlled page embedding the app in an iframe
- **Uncertainty Boundary:** Currently hardcoded usernames prevent XSS; dynamic usernames would elevate this

### Remediation

```javascript
const helmet = require('helmet'); // npm install helmet

app.use(helmet()); // Sets X-Content-Type-Options, X-Frame-Options, CSP, HSTS, etc.
```

Add `res.set("Cache-Control", "no-store")` to every authenticated route (see Finding 1 remediation).

### References

- [helmet.js](https://helmetjs.github.io/)
- [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/)
