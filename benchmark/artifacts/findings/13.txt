## Finding 1: SQL Injection via ORDER BY String Concatenation

**Finding ID:** `APPSEC-c3a7f82d91`
**File:** `main.java`
**Lines:** 25–26
**CWE:** CWE-89 — Improper Neutralization of Special Elements used in an SQL Command
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
String query = "SELECT * FROM users ORDER BY " + orderBy;
return jdbcTemplate.queryForList(query);
```

### Description
The `orderBy` request parameter is appended directly to the SQL string via string concatenation before being executed with `JdbcTemplate.queryForList()`. Column names cannot be bound with standard JDBC placeholders, so developers sometimes reach for concatenation here — but the value is never validated against an allowlist of permitted columns. An attacker controls the entire SQL fragment after `ORDER BY`, enabling error-based, time-based blind, and UNION-based extraction techniques against any table the DB user can read. On most databases this is also a vector for stacked-query injection depending on the driver and DB config.

### Prioritization
This is the highest-priority finding. The source-to-sink path is direct and unambiguous (`@RequestParam` → string concat → `queryForList`), requires zero authentication, and is reachable from the public internet on the `GET /users` endpoint.

### Exploitability Notes
- **Exploit Preconditions:** Attacker can send an HTTP GET request to `/users`. No authentication is visible in scope. Even if auth were added, the bug would remain.
- **Uncertainty Boundary:** The specific DB engine determines which exploitation techniques work (e.g., `SLEEP()` on MySQL vs `pg_sleep()` on PostgreSQL vs `WAITFOR DELAY` on MSSQL), but SQLi is valid regardless of backend.

**Concrete attacker input examples:**
```
GET /users?orderBy=1 UNION SELECT null,username,password,null FROM users--
GET /users?orderBy=(SELECT CASE WHEN (1=1) THEN 1 ELSE 2 END)
GET /users?orderBy=1;DROP TABLE users--
```

**Counterfactual invalidation:** If `orderBy` were validated against a strict allowlist of known column names before query construction (e.g., `Set.of("id","username","email")`), this finding would be invalid.

### Remediation
Column names cannot be bound as JDBC parameters, so the correct fix is an explicit allowlist before query construction:

```java
private static final Set<String> ALLOWED_ORDER_COLUMNS = Set.of("id", "username", "email", "created_at");

@GetMapping("/users")
public List<Map<String, Object>> getUsers(@RequestParam String orderBy) {
    if (!ALLOWED_ORDER_COLUMNS.contains(orderBy)) {
        throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "Invalid sort column");
    }
    // orderBy is now a validated, safe identifier — concatenation is acceptable
    String query = "SELECT * FROM users ORDER BY " + orderBy;
    return jdbcTemplate.queryForList(query);
}
```

If the column names are dynamic and an allowlist is impractical, map client-supplied sort keys to server-side column names:

```java
private static final Map<String, String> SORT_COLUMN_MAP = Map.of(
    "name", "username",
    "date", "created_at"
);

String col = SORT_COLUMN_MAP.get(orderBy);
if (col == null) throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "Invalid sort column");
String query = "SELECT * FROM users ORDER BY " + col;
```

## Finding 2: No Authentication or Authorization on Database Endpoints

**Finding ID:** `APPSEC-7b2e4a91c0`
**File:** `main.java`
**Lines:** 23–34
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** HIGH
**Confidence:** MEDIUM

### Vulnerable Code
```java
@GetMapping("/users")
public List<Map<String, Object>> getUsers(@RequestParam String orderBy) {
    ...
}

@PostMapping("/users")
public String addUser(@RequestParam String username) {
    ...
}
```

### Description
Neither endpoint carries any authentication or authorization guard. `GET /users` returns the full `users` table to any caller. `POST /users` permits any unauthenticated caller to insert arbitrary usernames. No Spring Security configuration, JWT validation, or session check is visible in the analyzed scope. In the absence of a broader security config, any internet-reachable deployment of this service exposes all user records and allows unrestricted account creation.

### Prioritization
P2 — ranks below the confirmed SQLi (P1) because the impact here depends on what the `users` table contains and whether Spring Security is configured elsewhere. The SQLi has a certain, direct exploit path regardless of auth state.

### Exploitability Notes
- **Exploit Preconditions:** Service is deployed without an external auth gateway or a Spring Security configuration bean that is not visible in this file.
- **Uncertainty Boundary:** A `SecurityFilterChain` bean in another class or a gateway-level auth policy not in scope could mitigate this. Confidence is MEDIUM for that reason.

### Remediation
Add Spring Security and require authentication for both endpoints. Minimal example:

```java
// SecurityConfig.java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/users").authenticated()
                .anyRequest().denyAll()
            )
            .httpBasic(Customizer.withDefaults()); // or JWT/OAuth2
        return http.build();
    }
}
```

For the `POST /users` endpoint, also verify that only privileged roles (e.g., `ROLE_ADMIN`) may create users:

```java
.requestMatchers(HttpMethod.POST, "/users").hasRole("ADMIN")
.requestMatchers(HttpMethod.GET,  "/users").authenticated()
```
