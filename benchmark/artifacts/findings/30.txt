## Finding 1: SSRF and Local File Inclusion via Unsanitized HTML Injected into wkhtmltopdf

**File:** `main.go`  
**Lines:** 24–32  
**CWE:** CWE-918 — Server-Side Request Forgery / CWE-22 — Path Traversal (LFI)  
**OWASP Category:** A10:2021 – SSRF  
**Priority:** P1  
**Severity:** CRITICAL  
**Confidence:** HIGH

### Vulnerable Code
```go
html := fmt.Sprintf(`
<html><body>
  <h1>Company Report</h1><hr/>
  %s
  <hr/><footer>Generated by Challenge 30 - PDF API</footer>
</body></html>`, req.Content)

pdfg, _ := wkhtmltopdf.NewPDFGenerator()
pdfg.AddPage(wkhtmltopdf.NewPageReader(bytes.NewReader([]byte(html))))
```

### Description
`req.Content` is an attacker-controlled string inserted verbatim into an HTML document via `fmt.Sprintf` with no encoding or sanitization. This HTML is handed directly to `wkhtmltopdf`, which is a full headless WebKit browser — not a PDF typesetter. WebKit follows `file://` URIs to read local files, issues real HTTP requests for `http://` resources, and executes JavaScript during rendering. All three vectors are exploitable here.

**Attack path 1 — Local file read:** Inject `<iframe src="file:///etc/passwd">` or `<iframe src="file:///proc/self/environ">`. The file contents appear in the rendered PDF returned to the attacker.

**Attack path 2 — Cloud metadata SSRF:** Inject `<iframe src="http://169.254.169.254/latest/meta-data/iam/security-credentials/">` to steal AWS instance credentials (or the Azure/GCP equivalents).

**Attack path 3 — JavaScript exfiltration:** Inject a `<script>` block that reads `file:///etc/passwd` via `XMLHttpRequest` and `document.write`s the content into the page, or posts it to an attacker-controlled server:
```html
<script>
  var x = new XMLHttpRequest();
  x.open('GET', 'file:///etc/shadow', false);
  x.send();
  document.write('<pre>' + x.responseText + '</pre>');
</script>
```

This is a complete, no-precondition SSRF/LFI with direct data exfiltration in the PDF response.

### Prioritization
Highest-priority finding. Direct, unauthenticated data exfiltration from filesystem and internal network with no exploit preconditions beyond sending a POST request. All other findings are secondary.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 5000. No credentials required (see Finding 2). The request body must be valid JSON with a `content` key.
- **Uncertainty Boundary:** Impact depth depends on the container's filesystem layout and network reachability of cloud metadata endpoints. Running as root (see Finding 3) maximizes accessible files.

### Counterfactual
If `wkhtmltopdf` were invoked with `--disable-local-file-access --disable-javascript` and restricted from making outbound HTTP requests (or if user content were HTML-encoded before insertion), this finding would be invalid.

### Remediation

**Option A — Encode user content as data, not markup** (simplest safe approach):

```go
import "html"

// In renderHandler:
safeContent := html.EscapeString(req.Content)
htmlDoc := fmt.Sprintf(`
<html><body>
  <h1>Company Report</h1><hr/>
  <p>%s</p>
  <hr/><footer>Generated by Challenge 30 - PDF API</footer>
</body></html>`, safeContent)
```

**Option B — Harden wkhtmltopdf at invocation** (if HTML input is intentional, add defence-in-depth):

```go
pdfg.NoBackground.Set(true)
// Pass these via wkhtmltopdf global settings:
pdfg.GlobalSettings.DisableLocalFileAccess = true   // block file:// reads
// Also pass CLI args through PageOptions if the library supports it:
page := wkhtmltopdf.NewPageReader(bytes.NewReader([]byte(htmlDoc)))
// Equivalent wkhtmltopdf flags: --disable-local-file-access --disable-javascript
// --no-background --disable-external-links
```

Both options should be applied together. HTML-encoding input is mandatory; wkhtmltopdf hardening is defence-in-depth.

### References
- https://owasp.org/Top10/A10_2021-Server-Side_Request_Forgery_%28SSRF%29/
- https://portswigger.net/web-security/ssrf
- https://github.com/wkhtmltopdf/wkhtmltopdf/issues/4536 (known SSRF/LFI class)

## Finding 2: Missing Authentication on the `/render` Endpoint

**File:** `main.go`  
**Lines:** 17, 43  
**CWE:** CWE-306 — Missing Authentication for Critical Function  
**OWASP Category:** A07:2021 – Identification and Authentication Failures  
**Priority:** P2  
**Severity:** HIGH  
**Confidence:** HIGH

### Vulnerable Code
```go
func renderHandler(w http.ResponseWriter, r *http.Request) {
    var req Req
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        // ...
    }
    // No auth check — proceeds directly to PDF generation
```
```go
http.HandleFunc("/render", renderHandler)
```

### Description
The `/render` endpoint requires no token, session, or other credential. Any unauthenticated client with network access to port 5000 can invoke the PDF renderer. Combined with Finding 1 (SSRF/LFI), unauthenticated access means the SSRF requires zero preconditions. Even without Finding 1, unmetered PDF generation is a resource-exhaustion vector: an attacker can flood the endpoint with rendering requests to exhaust CPU and memory.

### Prioritization
P2 after the SSRF/LFI. It dramatically amplifies Finding 1 by removing the only remaining precondition (a valid account). Must be fixed alongside Finding 1.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 5000. The `docker-compose.yml` maps port 5000 directly to the host, so any attacker on the same network or on the public internet (if the host is exposed) can reach it.
- **Uncertainty Boundary:** None — no auth gate exists in the code.

### Remediation

Add a static bearer token check (replace with a proper auth middleware in production):

```go
const apiToken = "" // load from environment: os.Getenv("API_TOKEN")

func authMiddleware(next http.HandlerFunc) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        token := r.Header.Get("Authorization")
        expectedToken := "Bearer " + os.Getenv("API_TOKEN")
        if !hmac.Equal([]byte(token), []byte(expectedToken)) {
            http.Error(w, "Unauthorized", http.StatusUnauthorized)
            return
        }
        next(w, r)
    }
}

// In main():
http.HandleFunc("/render", authMiddleware(renderHandler))
```

Set `API_TOKEN` as a secret in your container environment, not in `docker-compose.yml`.

## Finding 3: Container Runs as Root (No `USER` Directive)

**File:** `Dockerfile`  
**Lines:** 1–21 (no `USER` directive present)  
**CWE:** CWE-250 — Execution with Unnecessary Privileges  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P3  
**Severity:** MEDIUM  
**Confidence:** HIGH

### Vulnerable Code
```dockerfile
FROM debian:bullseye

RUN apt-get update && apt-get install -y \
    wkhtmltopdf \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app
COPY --from=builder /app/app .

EXPOSE 5000
CMD ["./app"]   # runs as root — no USER directive
```

### Description
The final image stage has no `USER` directive, so the application process runs as `root` (UID 0) inside the container. This directly amplifies Finding 1: a `file://` read via wkhtmltopdf can access `/etc/shadow`, `/root/.ssh/id_rsa`, container-mounted secrets at `/run/secrets/*`, and any file on the filesystem rather than only files owned by a restricted service account. It also increases the blast radius of any container escape vulnerability.

### Prioritization
P3. Standalone it is a misconfiguration; in combination with Finding 1 it elevates the practical impact of LFI to full-filesystem read.

### Exploitability Notes
- **Exploit Preconditions:** Exploitability of this finding depends on Finding 1 being exploited first.
- **Uncertainty Boundary:** Container breakout risk depends on kernel version and Docker daemon configuration (e.g., whether `--privileged` or dangerous capabilities are set).

### Remediation

Add a non-root user in the Dockerfile:

```dockerfile
FROM debian:bullseye

RUN apt-get update && apt-get install -y \
    wkhtmltopdf \
    && rm -rf /var/lib/apt/lists/* \
    && groupadd --gid 10001 appuser \
    && useradd --uid 10001 --gid 10001 --no-create-home appuser

WORKDIR /app
COPY --from=builder /app/app .

USER appuser
EXPOSE 5000
CMD ["./app"]
```

### References
- https://docs.docker.com/develop/develop-images/dockerfile_best-practices/#user
- https://cheatsheetseries.owasp.org/cheatsheets/Docker_Security_Cheat_Sheet.html

## Finding 4: Unchecked Error from `wkhtmltopdf.NewPDFGenerator()` Causes Nil-Pointer Panic

**File:** `main.go`  
**Line:** 31  
**CWE:** CWE-390 — Detection of Error Condition Without Action  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P4  
**Severity:** LOW  
**Confidence:** HIGH

### Vulnerable Code
```go
pdfg, _ := wkhtmltopdf.NewPDFGenerator()
pdfg.AddPage(wkhtmltopdf.NewPageReader(bytes.NewReader([]byte(html))))
```

### Description
The error return from `NewPDFGenerator()` is silently discarded with `_`. If the `wkhtmltopdf` binary is missing, inaccessible, or fails to initialize, `pdfg` will be `nil` and the next line will panic with a nil-pointer dereference. Go's default HTTP server catches panics in handlers and returns a 500, but the application logs an uncontrolled stack trace. An attacker can reliably trigger this panic to observe internal path information if error logging reaches the client.

### Remediation

```go
pdfg, err := wkhtmltopdf.NewPDFGenerator()
if err != nil {
    log.Printf("wkhtmltopdf init error: %v", err)
    http.Error(w, "PDF generation unavailable", http.StatusInternalServerError)
    return
}
```

## Finding 5: No Request Body Size Limit — Uncontrolled Resource Consumption

**File:** `main.go`  
**Line:** 19  
**CWE:** CWE-400 — Uncontrolled Resource Consumption  
**OWASP Category:** A05:2021 – Security Misconfiguration  
**Priority:** P5  
**Severity:** LOW  
**Confidence:** HIGH

### Vulnerable Code
```go
if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
```

### Description
`r.Body` is read without a size cap. An attacker can stream a multi-gigabyte JSON body to exhaust server memory during decoding. Because the decoded `Content` string is subsequently fed to `wkhtmltopdf`, a large payload can also trigger resource-intensive rendering (e.g., deeply nested HTML, many embedded resources), compounding the denial-of-service potential.

### Remediation

```go
import "net/http"

// At the start of renderHandler:
r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MB cap
if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
    http.Error(w, "Request too large or invalid JSON", http.StatusBadRequest)
    return
}
```
