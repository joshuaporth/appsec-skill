## Finding 1: XML External Entity (XXE) Injection

**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 36–38
**CWE:** CWE-611 — Improper Restriction of XML External Entity Reference
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
DocumentBuilder builder = dbf.newDocumentBuilder();
Document doc = builder.parse(new InputSource(new StringReader(inputXml)));
```

### Description
`DocumentBuilderFactory.newInstance()` returns a factory with external entity and DTD processing **enabled by default** in Java 17. No feature flags are set before calling `builder.parse()`, and the raw `inputXml` string comes directly from the HTTP POST body (`@RequestMapping(method=RequestMethod.POST, value="/process")`). An unauthenticated attacker can submit a crafted XML document containing a `DOCTYPE` declaration with an external entity pointing to local files (LFI) or internal network services (SSRF). Because the container runs as root (see Finding 3), file reads are unrestricted.

### Prioritization
Highest priority. No preconditions beyond network access to the endpoint. Directly exploitable for arbitrary local file read and SSRF. The container running as root multiplies the impact.

### Exploitability Notes
- **Exploit Preconditions:** Network access to `POST /process`. No authentication is required (see Finding 4). Attacker supplies XML in the `inputXml` request parameter.
- **Uncertainty Boundary:** Java 17 does not have JEP 185 (which hardened defaults, only landed in JDK 23+). `FEATURE_SECURE_PROCESSING` is not set, so the JDK's built-in Xerces parser will resolve external entities. Confirmation of exact JVM flavor (eclipse-temurin 17) is consistent with vulnerability.

**Concrete attacker-controlled input:**
```
POST /process HTTP/1.1
Content-Type: application/x-www-form-urlencoded

inputXml=%3C%3Fxml+version%3D%221.0%22+encoding%3D%22ISO-8859-1%22%3F%3E%0A%3C%21DOCTYPE+foo+%5B%0A++%3C%21ENTITY+xxe+SYSTEM+%22file%3A%2F%2F%2Fetc%2Fpasswd%22+%3E%5D%3E%0A%3Cfoo%3E%26xxe%3B%3C%2Ffoo%3E
```
i.e., the decoded XML payload:
```xml
<?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd" >]>
<foo>&xxe;</foo>
```
The `/etc/passwd` contents will be embedded in the parsed document and returned to the caller via `xmlToString(doc)`.

**Counterfactual invalidation:** Adding `dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` before `newDocumentBuilder()` would prevent all DOCTYPE declarations, fully eliminating this attack class.

### Remediation
Disable DTD processing entirely on the factory before building the parser. Harden the `TransformerFactory` as well (line 50) per defense-in-depth:

```java
@RequestMapping(method=RequestMethod.POST, value="/process")
public String process(String inputXml) {
    if (inputXml == null) {
        return "Provide an inputXml variable";
    }
    try {
        DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
        // Completely disallow DOCTYPE declarations — prevents all XXE/DTD attacks
        dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
        // Belt-and-suspenders: explicitly disable external entities
        dbf.setFeature("http://xml.org/sax/features/external-general-entities", false);
        dbf.setFeature("http://xml.org/sax/features/external-parameter-entities", false);
        dbf.setExpandEntityReferences(false);

        DocumentBuilder builder = dbf.newDocumentBuilder();
        Document doc = builder.parse(new InputSource(new StringReader(inputXml)));
        return xmlToString(doc);
    } catch (Exception e) {
        // Return a generic error message — do not echo e.getMessage()
        return "XML processing failed";
    }
}

public static String xmlToString(Document doc) {
    try {
        StringWriter sw = new StringWriter();
        TransformerFactory tf = TransformerFactory.newInstance();
        // Harden transformer factory as well
        tf.setFeature(javax.xml.XMLConstants.FEATURE_SECURE_PROCESSING, true);
        tf.setAttribute(javax.xml.XMLConstants.ACCESS_EXTERNAL_DTD, "");
        tf.setAttribute(javax.xml.XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "");
        Transformer transformer = tf.newTransformer();
        transformer.transform(new DOMSource(doc), new StreamResult(sw));
        return sw.toString();
    } catch (Exception ex) {
        throw new RuntimeException("Error converting to String", ex);
    }
}
```

## Finding 2: Sensitive Information Exposure via Exception Messages

**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 41–44
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```java
} catch (Exception e) {
    e.printStackTrace();
    return e.getMessage();
}
```

### Description
Any exception thrown during XML processing — including `SAXParseException`, `IOException`, and `TransformerException` — has its message returned verbatim to the HTTP client. In the context of the XXE finding above, certain parser error messages may include portions of the fetched file content or internal file paths. Even absent XXE, exception messages can disclose stack trace fragments, internal class names, or filesystem layout. `e.printStackTrace()` writes stack traces to stdout/stderr which may be captured in container logs accessible to attackers with container-level access.

### Prioritization
P3. Lower priority than Finding 1. Independently a LOW finding, but it amplifies the XXE vulnerability by making it easier to exfiltrate data through error channels.

### Exploitability Notes
- **Exploit Preconditions:** Any malformed XML input triggers this path. Combined with XXE, it may directly exfiltrate file content in the error response.
- **Uncertainty Boundary:** Whether exact file content appears in `e.getMessage()` depends on the JDK's SAX parser error formatting at runtime.

### Remediation
Return a fixed, generic error string and log structured errors server-side using a logging framework instead of `printStackTrace()`:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

private static final Logger log = LoggerFactory.getLogger(main.class);

// In process():
} catch (Exception e) {
    log.error("XML processing error", e);  // structured log, not to stdout
    return "XML processing failed";        // generic message to caller
}
```

## Finding 3: Container Running as Root

**File:** `Dockerfile`
**Lines:** 1–9
**CWE:** CWE-250 — Execution with Unnecessary Privileges
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```dockerfile
FROM eclipse-temurin:17-jdk

WORKDIR /app

COPY . .

RUN apt-get update && apt-get install -y maven && mvn clean package -DskipTests

CMD ["java", "-jar", "target/demo-0.0.1-SNAPSHOT.jar"]
```

### Description
No `USER` directive is specified, so the application process runs as `root` (UID 0) inside the container. This directly amplifies the XXE finding (Finding 1): file reads via external entities are executed with root privileges, granting access to files with restricted permissions (e.g., `/etc/shadow`, private keys, application secrets mounted as volumes). In the event of full RCE, container escape is also more achievable from a root context.

### Prioritization
P3. Secondary to the XXE finding. However, switching to a non-root user is a trivial one-line change that significantly limits blast radius.

### Exploitability Notes
- **Exploit Preconditions:** Exploitation of this finding is realized through the XXE vulnerability (Finding 1). Standalone, it requires another RCE primitive.
- **Uncertainty Boundary:** Container isolation (seccomp, AppArmor, capabilities) may limit some root-level impact, but those are runtime-dependent mitigations outside this codebase.

### Remediation
Add a non-root user and drop privileges before the `CMD`:

```dockerfile
FROM eclipse-temurin:17-jdk

WORKDIR /app

COPY . .

RUN apt-get update && apt-get install -y maven && mvn clean package -DskipTests \
    && useradd -r -s /bin/false appuser \
    && chown -R appuser /app

USER appuser

CMD ["java", "-jar", "target/demo-0.0.1-SNAPSHOT.jar"]
```

### References
- [Docker security best practices — non-root users](https://docs.docker.com/develop/security-best-practices/)
- [CWE-250](https://cwe.mitre.org/data/definitions/250.html)

## Finding 4: Missing Authentication on XML Processing Endpoint

**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 29–44
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P3
**Severity:** INFO
**Confidence:** HIGH

### Vulnerable Code
```java
@RequestMapping(method=RequestMethod.POST, value="/process")
public String process(String inputXml) {
```

### Description
The `/process` endpoint performs XML parsing and exposes the resulting document with no authentication or authorization check. Any party with network access to port 8081 (exposed via `docker-compose.yml`) can invoke it. While the endpoint's function (XML echo) may be intentionally public in a demo context, its combination with XXE processing creates a trivially exploitable unauthenticated CRITICAL attack surface in any deployment.

### Prioritization
P3 on its own. Elevates the effective exploitability of Finding 1 to zero-precondition.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the exposed port.
- **Uncertainty Boundary:** A reverse proxy or network-level control not in scope could restrict access; no such controls are present in the reviewed configurations.

### Remediation
If this endpoint is not intended to be public, add Spring Security with at minimum HTTP Basic or token-based authentication:

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

```java
// SecurityConfig.java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/process").authenticated()
                .anyRequest().permitAll())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}
```
