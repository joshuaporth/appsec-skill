## Finding 1: Path Traversal via Nginx Alias Off-by-Slash

**Finding ID:** `APPSEC-c8f2a19e3b`
**File:** `nginx.conf`
**Lines:** 9–11
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```nginx
location /html {
    alias /usr/share/nginx/html/;
}
```

### Description
The `location` directive uses the path `/html` (no trailing slash) while the `alias` directive ends with a trailing slash `/usr/share/nginx/html/`. When nginx resolves a request, it strips the matched location prefix and concatenates the remainder onto the alias path literally. Because `/html` has no trailing slash, a request URI of `/html../` is valid: nginx strips `/html`, prepends `/usr/share/nginx/html/`, yielding `/usr/share/nginx/html/../` — which resolves one directory above the intended root. With sufficient `../` repetitions an attacker can escape to arbitrary filesystem paths and read any file the nginx worker process has permission to access (e.g., `/etc/passwd`, application config files, private keys).

Concrete exploit input: `GET /html../../../../../etc/passwd HTTP/1.1` — nginx alias substitution produces `/usr/share/nginx/html/../../../../../etc/passwd`, which resolves to `/etc/passwd`.

### Prioritization
Highest-priority finding. Unauthenticated, no preconditions beyond network access; directly leaks filesystem contents. All other findings are secondary.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 80; nginx worker process must have read permission on the target file.
- **Uncertainty Boundary:** Some nginx builds/versions apply additional path normalization that may reduce traversal depth, but the misconfiguration pattern is reliably exploitable across modern nginx releases. The exact filesystem layout determines which sensitive files are reachable.

### Remediation
Add a trailing slash to the `location` path so it matches the alias exactly. With matching trailing slashes, nginx cannot form a `../` escape because the prefix boundary is unambiguous:

```nginx
# Before (vulnerable)
location /html {
    alias /usr/share/nginx/html/;
}

# After (safe)
location /html/ {
    alias /usr/share/nginx/html/;
}
```

Why: when both the location and alias end with `/`, the concatenation is always `alias_root + sub_path` where `sub_path` never starts with `../`, because a leading `../` would mean the URI was `/html/../` — which nginx normalizes by collapsing `/html/../` to `/` before location matching, causing it to miss `location /html/` entirely.

**Counterfactual invalidation:** Adding the trailing slash to `location /html/` makes this finding invalid.

### References
- [Acunetix: Path Traversal via Misconfigured Nginx Alias](https://www.acunetix.com/vulnerabilities/web/path-traversal-via-misconfigured-nginx-alias/)
- [CWE-22: Path Traversal](https://cwe.mitre.org/data/definitions/22.html)

## Finding 2: Proxy Location Off-by-Slash Routing Ambiguity

**Finding ID:** `APPSEC-7d3e50a812`
**File:** `nginx.conf`
**Lines:** 5–7
**CWE:** CWE-284 — Improper Access Control
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```nginx
location /backend { 
    proxy_pass http://backend/;
}
```

### Description
`location /backend` (no trailing slash) is a prefix match that also matches URIs such as `/backendadmin`, `/backendapi`, `/backend-internal`. When nginx substitutes the proxy_pass URI, it replaces only the literal matched prefix `/backend`, so a request to `/backendadmin` is proxied to `http://backend/admin`. If there are backend routes that callers should not reach directly (e.g., `/admin`, `/internal`, `/health`), an attacker can bypass any external access controls by prefixing those paths with the word `backend` in the request URI. The impact depends entirely on what the backend exposes — confidence is MEDIUM because the backend's route surface is not in scope.

Concrete example: `GET /backendadmin/users HTTP/1.1` → proxied to `http://backend/admin/users`, potentially an admin-only endpoint.

### Prioritization
P2 — lower exploitability than Finding 1 because impact is backend-dependent, but still a direct access control concern if the backend has sensitive routes.

### Exploitability Notes
- **Exploit Preconditions:** The backend must expose routes under `/admin`, `/internal`, or similar paths that the nginx config was meant to restrict. Network access to port 80 required.
- **Uncertainty Boundary:** If the backend has its own authentication middleware on sensitive routes, impact is reduced. Without backend source this cannot be confirmed.

### Remediation
Add a trailing slash to both `location` and `proxy_pass` so the prefix boundary is unambiguous, and optionally restrict what sub-paths are proxied:

```nginx
# Before (ambiguous)
location /backend { 
    proxy_pass http://backend/;
}

# After (precise boundary)
location /backend/ {
    proxy_pass http://backend/;
}
```

Why: `location /backend/` only matches URIs starting with `/backend/`, preventing the `/backendXXX` conflation.

**Counterfactual invalidation:** Adding a trailing slash to `location /backend/` closes the routing ambiguity.

### References
- [Nginx Docs: proxy_pass with URI](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass)
- [CWE-284: Improper Access Control](https://cwe.mitre.org/data/definitions/284.html)

## Finding 3: Cleartext HTTP — No TLS

**Finding ID:** `APPSEC-f901b64c77`
**File:** `nginx.conf`
**Lines:** 2
**CWE:** CWE-319 — Cleartext Transmission of Sensitive Information
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```nginx
listen 80;
```

### Description
The server only listens on port 80 (HTTP). All traffic between clients and this server — including session tokens, credentials, and any proxied responses — is transmitted in cleartext. An attacker with a network position between the client and server (on-path, café Wi-Fi, ISP-level interception) can read and modify all traffic. There is no HTTPS listener and no HTTP→HTTPS redirect, so there is no downgrade protection.

### Prioritization
P2 alongside Finding 2. Lower practical risk than Finding 1 but broadly affects all users. Remediation is non-intrusive (certificate provisioning + redirect rule).

### Exploitability Notes
- **Exploit Preconditions:** Attacker must have a network-level position between client and server (on-path attacker).
- **Uncertainty Boundary:** If this server is purely internal (RFC1918, never client-facing), TLS risk is reduced. `server_name another-awesome-challenge.com` suggests it is internet-facing.

### Remediation
```nginx
# Redirect HTTP to HTTPS
server {
    listen 80;
    server_name another-awesome-challenge.com;
    return 301 https://$host$request_uri;
}

# HTTPS server
server {
    listen 443 ssl;
    server_name another-awesome-challenge.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    location /backend/ {
        proxy_pass http://backend/;
    }

    location /html/ {
        alias /usr/share/nginx/html/;
    }
}
```

Why: TLS encrypts the transport layer, preventing passive eavesdropping and active injection. HSTS pins clients to HTTPS after first visit.

### References
- [CWE-319](https://cwe.mitre.org/data/definitions/319.html)
- [OWASP Transport Layer Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transport_Layer_Security_Cheat_Sheet.html)

## Finding 4: Missing Security Response Headers

**Finding ID:** `APPSEC-22d7f3b901`
**File:** `nginx.conf`
**Lines:** 1–12
**CWE:** CWE-693 — Protection Mechanism Failure
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```nginx
server {
    listen 80;
    server_name another-awesome-challenge.com;
    # no add_header directives present
    ...
}
```

### Description
No security-relevant response headers are set. The absence of `X-Content-Type-Options`, `X-Frame-Options`, and `Content-Security-Policy` leaves browsers without defence-in-depth protections against MIME sniffing, clickjacking, and content injection. Combined with the XSS and injection surface of the proxied backend (not in scope here), these missing headers amplify client-side risk.

### Prioritization
P3 — lower exploitability than findings above; typically requires a separate vulnerability to exploit. Remediation is low-effort and should be included in any hardening pass.

### Exploitability Notes
- **Exploit Preconditions:** Requires a separate content-injection or XSS vulnerability in the proxied application to exploit meaningfully.
- **Uncertainty Boundary:** Some headers may be set by the backend application itself; however, nginx-layer headers ensure they are always present regardless of backend behavior.

### Remediation
```nginx
# Add inside the server block
add_header X-Content-Type-Options    "nosniff"          always;
add_header X-Frame-Options           "DENY"             always;
add_header Referrer-Policy           "no-referrer"      always;
add_header Content-Security-Policy   "default-src 'self'" always;
# add_header Strict-Transport-Security once TLS is in place
server_tokens off;
```

Why: `always` ensures headers are sent even on error responses. `server_tokens off` prevents nginx version disclosure in `Server:` headers and error pages.

### References
- [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/)
- [CWE-693](https://cwe.mitre.org/data/definitions/693.html)
