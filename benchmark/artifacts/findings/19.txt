## Finding 1: Server-Side Template Injection → Local File Inclusion

**Finding ID:** `APPSEC-c3d9f2a71b4e`
**File:** `main.go`
**Lines:** 22–36
**CWE:** CWE-94 — Improper Control of Generation of Code ('Code Injection')
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```go
tmpl := r.URL.Query().Get("tmpl")

funcs := template.FuncMap{
    "ReadUserFile": func(filename string) string {
        return user.ReadUserFile(filename)
    },
}

t, err := template.New("page").Funcs(funcs).Parse(tmpl)
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

if err = t.Execute(w, user); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
}
```

### Description
The query parameter `tmpl` is parsed verbatim as a `html/template` template source and then executed with the `user` struct as data. An attacker controls the entire template program: they can access any exported field on the data object (including `{{.Password}}`) and invoke any registered FuncMap function (including `ReadUserFile`). `html/template` provides contextual HTML output escaping but places no restrictions on template logic, field access, or function invocation — it does not sandbox execution. Because `ReadUserFile` wraps `os.ReadFile` with no path validation, the attacker gains read access to any file the process can open: `?tmpl={{ReadUserFile "/etc/passwd"}}`, `?tmpl={{ReadUserFile "/proc/self/environ"}}`, or the application binary itself.

### Prioritization
Highest priority. This is a zero-precondition, unauthenticated, remotely exploitable critical finding combining template injection with unrestricted local file read. All other findings are secondary to this.

### Exploitability Notes
- **Exploit Preconditions:** None — any HTTP GET request to `/` with a crafted `tmpl` parameter is sufficient. No authentication, no special network position required.
- **Uncertainty Boundary:** In a distroless container (as in the Dockerfile), filesystem access is limited to what is in the image. However, `/proc/self/environ`, `/proc/self/maps`, the Go binary at `/app/main`, and any mounted secrets are still readable.

### Remediation
Never use user-controlled input as a template source. Use a server-side template file identified by an allowlisted name, or eliminate the dynamic template entirely:

```go
// Option A: allowlisted template name → server-side file
func handler(w http.ResponseWriter, r *http.Request) {
    name := r.URL.Query().Get("page")
    allowed := map[string]bool{"home": true, "about": true}
    if !allowed[name] {
        http.Error(w, "not found", http.StatusNotFound)
        return
    }
    t, err := template.ParseFiles("templates/" + name + ".html")
    if err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
        return
    }
    // Do not expose sensitive data in template context
    if err = t.Execute(w, nil); err != nil {
        http.Error(w, "internal error", http.StatusInternalServerError)
    }
}

// Option B: if dynamic rendering is genuinely required, pre-parse templates
// at startup and select by allowlisted key — never parse attacker-supplied strings.
```

Additionally, remove `ReadUserFile` from the FuncMap entirely. If file reading is needed, implement it server-side with strict canonicalization and base-path enforcement, never exposing it to template callers.

### References
- [CWE-94: Improper Control of Generation of Code](https://cwe.mitre.org/data/definitions/94.html)
- [OWASP Server-Side Template Injection](https://owasp.org/www-project-web-security-testing-guide/v42/4-Web_Application_Security_Testing/07-Input_Validation_Testing/18-Testing_for_Server-Side_Template_Injection)

## Finding 2: Hardcoded Password in Source Code

**Finding ID:** `APPSEC-8f1e4b29c7a3`
**File:** `main.go`
**Lines:** 21
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
user := &User{Email: "test@example.com", Password: "Password123!"}
```

### Description
A plaintext password is hardcoded directly in the handler and bound into the template data context as `.Password`. Combined with Finding 1, any attacker can retrieve it with `?tmpl={{.Password}}` — no source access needed. Even absent the SSTI, hardcoded credentials appear in version control history forever, are visible to anyone with repository read access, and cannot be rotated without a code change. This credential represents an authentication factor with no rotation mechanism.

### Prioritization
P1, second only to Finding 1. The SSTI makes this trivially exploitable over HTTP with a single request. Even if Finding 1 were fixed, hardcoded credentials in source remain a standalone HIGH.

### Exploitability Notes
- **Exploit Preconditions:** Exploitable directly via Finding 1 with zero preconditions. Independently, exploitable by anyone with source or git history access.
- **Uncertainty Boundary:** It is unclear whether this credential is reused elsewhere in a real deployment. If it is, the blast radius extends beyond this service.

### Remediation
Remove credentials from source entirely. Load them at runtime from environment variables or a secrets manager, and never place them in the template data context:

```go
func handler(w http.ResponseWriter, r *http.Request) {
    // Do not put credentials in the template data context at all.
    // If user data is needed, expose only what the template requires.
    data := struct{ Email string }{Email: os.Getenv("APP_USER_EMAIL")}

    t, err := template.ParseFiles("templates/page.html") // static template
    if err != nil { ... }
    t.Execute(w, data)
}
```

If the password is needed for authentication logic, use `os.Getenv("APP_PASSWORD")` at startup and store only the **hash** (bcrypt cost ≥ 12), never the plaintext.

### References
- [CWE-798: Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html)
- [OWASP: Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## Finding 3: Unrestricted File Read via Exported Template Function

**Finding ID:** `APPSEC-d4b7e9120f56`
**File:** `main.go`
**Lines:** 15–18, 24–28
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
func (u *User) ReadUserFile(filename string) string {
    data, _ := os.ReadFile(filename)
    return string(data)
}

funcs := template.FuncMap{
    "ReadUserFile": func(filename string) string {
        return user.ReadUserFile(filename)
    },
}
```

### Description
`ReadUserFile` accepts an arbitrary `filename` string and calls `os.ReadFile` directly with no canonicalization, no base-directory check, and no allowlist. It is registered as a FuncMap function and thus callable from any template the server executes. Via Finding 1, the attacker supplies both the template source and the filename argument: `?tmpl={{ReadUserFile "/etc/passwd"}}`. In a container context, readable targets include `/proc/self/environ` (environment variables, potential secrets), `/proc/self/cmdline`, mounted Kubernetes secrets (commonly at `/var/run/secrets/kubernetes.io/serviceaccount/token`), and the application binary. Errors from `os.ReadFile` are silently discarded (`_`), so failed reads return an empty string — this enables oracle-style enumeration of paths.

### Prioritization
P1 together with Finding 1. This function is the primary exploitation primitive that Finding 1 enables. Fixing Finding 1 without removing or hardening `ReadUserFile` leaves a residual risk if any future template access is added.

### Exploitability Notes
- **Exploit Preconditions:** Requires Finding 1 (SSTI) to be exploitable. If SSTI is fixed, `ReadUserFile` is no longer callable from outside.
- **Uncertainty Boundary:** Impact depends on what secrets are mounted into the container at runtime. In a distroless base image, userland tools are absent, but proc filesystem and mounted secrets remain accessible.

### Remediation
Remove `ReadUserFile` from the FuncMap entirely. If a use case genuinely requires reading a file and reflecting its content, enforce a strict allowlist and canonicalize the path:

```go
func safeReadFile(filename string) (string, error) {
    const baseDir = "/app/user-files"
    // Resolve to absolute, canonical path
    abs, err := filepath.Abs(filepath.Join(baseDir, filename))
    if err != nil {
        return "", err
    }
    base, _ := filepath.Abs(baseDir)
    if !strings.HasPrefix(abs, base+string(filepath.Separator)) {
        return "", fmt.Errorf("path traversal detected")
    }
    data, err := os.ReadFile(abs)
    if err != nil {
        return "", err
    }
    return string(data), nil
}
```

### References
- [CWE-22: Path Traversal](https://cwe.mitre.org/data/definitions/22.html)
- [OWASP: Path Traversal](https://owasp.org/www-community/attacks/Path_Traversal)

## Finding 4: Internal Error Details Returned to Client

**Finding ID:** `APPSEC-2c8a1f034d79`
**File:** `main.go`
**Lines:** 32–34, 37–39
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```go
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

if err = t.Execute(w, user); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
}
```

### Description
Raw Go error strings are written into HTTP responses on both template parse failure and execution failure. Template parse errors can reflect portions of the malformed input back to the caller, and execution errors may include internal type information or field names from the data struct. This assists attacker reconnaissance and may leak structural details about the `User` type or template execution context.

### Prioritization
P3 — lowest priority. The dominant risks are Findings 1–3. However, this should be fixed as part of hardening regardless.

### Exploitability Notes
- **Exploit Preconditions:** Attacker sends a malformed template string that causes a parse or execution error.
- **Uncertainty Boundary:** Go template error messages are generally descriptive but not catastrophic in isolation. Impact is reconnaissance assistance, not direct data exfiltration.

### Remediation
Return a generic error message to clients and log the detail server-side:

```go
if err != nil {
    log.Printf("template parse error: %v", err)
    http.Error(w, "internal server error", http.StatusInternalServerError)
    return
}

if err = t.Execute(w, user); err != nil {
    log.Printf("template execute error: %v", err)
    http.Error(w, "internal server error", http.StatusInternalServerError)
}
```

### References
- [CWE-209: Information Exposure Through an Error Message](https://cwe.mitre.org/data/definitions/209.html)
