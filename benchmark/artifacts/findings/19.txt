## Finding 1: Server-Side Template Injection (Template Source Injection)

**File:** `main.go`
**Lines:** 22–36
**CWE:** CWE-94 — Improper Control of Generation of Code
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```go
tmpl := r.URL.Query().Get("tmpl")

funcs := template.FuncMap{
    "ReadUserFile": func(filename string) string {
        return user.ReadUserFile(filename)
    },
}

t, err := template.New("page").Funcs(funcs).Parse(tmpl)
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

if err = t.Execute(w, user); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
}
```

### Description
The `tmpl` query parameter is used directly as the **template source** — not as data to be interpolated into a trusted template, but as the template definition itself. An attacker fully controls the template program that executes in the server process. Although `html/template` provides XSS-safe HTML context escaping, it provides no restriction on which struct fields or registered functions a template can invoke. This means the attacker can access `.Password` via `{{.Password}}`, call `ReadUserFile` via `{{ReadUserFile "/etc/passwd"}}`, and call the same method directly via `{{.ReadUserFile "/etc/passwd"}}` (since it is an exported method on the `*User` data object passed to `Execute`). This is a direct, zero-precondition arbitrary data read and credential leak.

### Prioritization
Highest-priority finding. The source→sink path is direct: attacker-supplied string → `template.Parse()` → `template.Execute()` with privileged data and functions. No authentication, encoding, or other control interrupts this path.

### Exploitability Notes
- **Exploit Preconditions:** None — unauthenticated, no rate limit, no input validation. Single HTTP GET request.
- **Attacker-controlled input shape:**
  - `GET /?tmpl={{.Password}}` → returns `Password123!`
  - `GET /?tmpl={{ReadUserFile "/etc/passwd"}}` → returns `/etc/passwd` contents
  - `GET /?tmpl={{.ReadUserFile "/proc/self/environ"}}` → returns process environment variables (may include injected secrets)
- **Uncertainty Boundary:** Impact is bounded by what the container process user can read from the filesystem. The distroless base image reduces the available attack surface compared to a full OS, but `/proc/self/environ`, the application binary, and any mounted secrets/configs remain readable.

### Remediation
Never use attacker-supplied data as the template source. Store trusted templates on disk or in a safe store; accept only data that gets interpolated into those templates.

```go
// After — template loaded from trusted source; only data comes from request
const pageTmpl = `<html><body>Welcome, {{.Email}}</body></html>`

func handler(w http.ResponseWriter, r *http.Request) {
    user := &User{Email: "test@example.com"}  // Password not in template data
    t, err := template.New("page").Parse(pageTmpl)
    if err != nil {
        http.Error(w, "Internal error", http.StatusInternalServerError)
        return
    }
    if err = t.Execute(w, user); err != nil {
        http.Error(w, "Internal error", http.StatusInternalServerError)
    }
}
// Why: the template program is fixed and trusted; attacker can only influence
//      the values of whitelisted data fields, not the template logic itself.
```

**Counterfactual invalidation:** If `tmpl` were loaded from a trusted file path resolved server-side (e.g., an allowlisted name mapped to a file in a templates directory) rather than from query parameter content, this finding would not be valid.

- https://cwe.mitre.org/data/definitions/94.html
- https://pkg.go.dev/html/template#hdr-Security_Model

## Finding 2: Arbitrary File Read via Unrestricted `ReadUserFile`

**File:** `main.go`
**Lines:** 15–18, 24–28
**CWE:** CWE-73 — External Control of File Name or Path
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```go
func (u *User) ReadUserFile(filename string) string {
    data, _ := os.ReadFile(filename)
    return string(data)
}

funcs := template.FuncMap{
    "ReadUserFile": func(filename string) string {
        return user.ReadUserFile(filename)
    },
}
```

### Description
`ReadUserFile` accepts a caller-supplied `filename` with zero validation — no path canonicalization, no prefix check, no allowlist. It is exposed in two ways simultaneously: (1) registered in the template FuncMap so any template can call `{{ReadUserFile "/any/path"}}`, and (2) an exported method on `*User`, making it callable directly from any template via `{{.ReadUserFile "/any/path"}}`. Combined with Finding 1 (attacker controls the template source), this gives an unauthenticated attacker full read access to any file the server process can open: environment variables, mounted secrets, TLS private keys, or other services' credential files.

### Prioritization
Co-primary with Finding 1 — both are required for exploitation, and both must be fixed. This finding represents the dangerous capability; Finding 1 is the unlocking mechanism.

### Exploitability Notes
- **Exploit Preconditions:** Finding 1 must be exploitable (it is, unconditionally). Two equivalent payloads reach this sink:
  - `GET /?tmpl={{ReadUserFile "/proc/self/environ"}}`
  - `GET /?tmpl={{.ReadUserFile "/proc/self/environ"}}`
- **Uncertainty Boundary:** Exact files readable depend on the container user's UID and filesystem mounts. A distroless image limits available binaries but does not restrict mounted secrets or `/proc` entries.

### Remediation
Remove `ReadUserFile` from the FuncMap entirely — privileged file-reading helpers must never be exposed as callable template functions when any part of the template is attacker-influenced. If file reading is a legitimate feature, add strict path confinement:

```go
// If ReadUserFile must exist, confine it to a trusted directory
func (u *User) ReadUserFile(filename string) (string, error) {
    const baseDir = "/app/user-files/"
    safe := filepath.Join(baseDir, filename)
    safe, err := filepath.EvalSymlinks(safe)
    if err != nil || !strings.HasPrefix(safe, filepath.Clean(baseDir)+string(os.PathSeparator)) {
        return "", errors.New("invalid file path")
    }
    data, err := os.ReadFile(safe)
    if err != nil {
        return "", err
    }
    return string(data), nil
}
// Why: EvalSymlinks + HasPrefix enforces the path stays within baseDir,
//      preventing ../  and symlink traversal escapes.
```

**Counterfactual invalidation:** Removing `ReadUserFile` from the FuncMap and not exposing it via a data object with attacker-callable methods would eliminate this finding.

- https://cwe.mitre.org/data/definitions/73.html
- https://owasp.org/www-community/attacks/Path_Traversal

## Finding 3: Sensitive Credential Exposed in Template Execution Context

**File:** `main.go`
**Lines:** 21, 36
**CWE:** CWE-312 — Cleartext Storage of Sensitive Information (in accessible context)
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
user := &User{Email: "test@example.com", Password: "Password123!"}
// ...
if err = t.Execute(w, user); err != nil {
```

### Description
The full `User` struct — including its `Password` field — is passed as the root data object to template execution. Because Go's `html/template` makes all exported fields accessible from templates as `.FieldName`, the `Password` field is directly reachable. Even without Finding 1, if templates were ever sourced from a less-controlled location, `.Password` would leak. With Finding 1 active, the exploit is a one-liner: `GET /?tmpl={{.Password}}` returns `Password123!` in the response body. This is a distinct design defect: security-sensitive fields must never be included in template data objects when templates can be influenced by untrusted parties.

### Prioritization
Secondary to Findings 1 and 2 in terms of root cause, but directly exploitable as a consequence. Must be fixed alongside Finding 1 as defense-in-depth.

### Exploitability Notes
- **Exploit Preconditions:** Requires Finding 1 to be exploitable (no additional preconditions).
- **Attacker-controlled input:** `GET /?tmpl={{.Password}}` → response body: `Password123!`
- **Uncertainty Boundary:** None — the field name and value are static in source.

### Remediation
Pass only the minimum necessary data to templates using a dedicated view/DTO struct:

```go
type UserView struct {
    Email string
    // Password intentionally excluded
}

func handler(w http.ResponseWriter, r *http.Request) {
    user := &User{Email: "test@example.com", Password: "Password123!"}
    view := UserView{Email: user.Email}
    // ...
    if err = t.Execute(w, view); err != nil { ... }
}
// Why: the template can only access fields explicitly placed in the view struct;
//      credential fields are structurally unreachable from template logic.
```

**Counterfactual invalidation:** Passing a view struct that omits `Password` would make `.Password` undefined in the template context and eliminate this finding.

- https://cwe.mitre.org/data/definitions/312.html

## Finding 4: Hardcoded Credentials in Source Code

**File:** `main.go`
**Lines:** 21
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
user := &User{Email: "test@example.com", Password: "Password123!"}
```

### Description
A plaintext password is hardcoded directly in the handler function. Any developer with read access to the repository, any build artifact, or any process-memory dump can recover this credential. While these may be placeholder values in a challenge context, the pattern is dangerous in any real deployment: credentials committed to source are frequently discovered via git history, leaked repositories, or container image layer inspection even after being removed from the current HEAD.

### Prioritization
Lower than Findings 1–3 because it does not independently unlock a new exploit path — the same credential is already exposed by Finding 3. However, it must be remediated separately: even after fixing the template context exposure, the credential remains recoverable from source history and container images.

### Exploitability Notes
- **Exploit Preconditions:** Read access to the source repository, built binary, or container image.
- **Uncertainty Boundary:** Whether these are real production credentials or test placeholders changes impact; the code pattern is equally dangerous regardless.

### Remediation
Load credentials from environment variables or a secrets manager at runtime; never commit them to source:

```go
func main() {
    password := os.Getenv("APP_PASSWORD")
    if password == "" {
        log.Fatal("APP_PASSWORD environment variable is required")
    }
    // pass to handler via closure or config struct
}
```

**Counterfactual invalidation:** Moving credentials to environment variables (and ensuring no `.env` file is committed) eliminates this finding.

- https://cwe.mitre.org/data/definitions/798.html

## Finding 5: Internal Error Details Returned to Client

**File:** `main.go`
**Lines:** 32, 37
**CWE:** CWE-209 — Generation of Error Message Containing Sensitive Information
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```go
if err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
    return
}

if err = t.Execute(w, user); err != nil {
    http.Error(w, err.Error(), http.StatusInternalServerError)
}
```

### Description
Raw Go error messages from template parsing and execution are sent directly to the HTTP response. Template parse errors may include fragments of the template source (echoing attacker input back) and internal Go type names or paths. Execution errors may leak field names, type reflections, or partial data values. While the impact is low compared to Findings 1–4, returning unfiltered error strings is a bad-practice baseline that aids attacker reconnaissance.

### Prioritization
Lowest priority — useful signal for an attacker but not independently exploitable given the severity of Findings 1–4.

### Exploitability Notes
- **Exploit Preconditions:** Sending a malformed template string (e.g., `?tmpl={{`).
- **Uncertainty Boundary:** Exact information disclosed depends on the Go runtime error representation.

### Remediation
```go
// Log the full error server-side; return only a generic message to the client
if err != nil {
    log.Printf("template error: %v", err)
    http.Error(w, "Internal server error", http.StatusInternalServerError)
    return
}
```
