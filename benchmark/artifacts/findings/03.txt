## Finding 1: Missing Authentication on Admin Endpoint + Full Credential Exposure

**Finding ID:** `APPSEC-58ae8b52f5f0`
**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 49–52
**CWE:** CWE-862 — Missing Authorization
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
// retrieving all usernames (simulated admin functionality)
@GetMapping("/admin/usernames")
public Map<String, String> getAllUsernames() {
    return userDatabase;
}
```

### Description
The `/admin/usernames` endpoint has no authentication or authorization check of any kind. No Spring Security configuration exists in the project (only the low-level `spring-security-crypto` module is present in `pom.xml`, not `spring-boot-starter-security`), so Spring Boot applies no automatic access controls. Any unauthenticated HTTP client can call `GET /admin/usernames` and receive the complete `userDatabase` map — which contains every registered username mapped to its MD5 password hash. An attacker can enumerate all accounts in one request and then crack the unsalted MD5 hashes offline in seconds with a GPU.

### Prioritization
Highest priority. This is a no-precondition full credential dump. Combined with Finding 2 (MD5 hashing), an attacker can harvest then crack all user passwords with commodity hardware. Remediate before any other finding.

### Exploitability Notes
- **Exploit Preconditions:** None. The endpoint is publicly reachable on port 8081 (per `docker-compose.yml`). A single `curl` call suffices.
- **Concrete attacker input:** `GET /admin/usernames HTTP/1.1` — returns `{"alice":"5F4DCC3B5AA765D61D8327DEB882CF99","bob":"..."}`.
- **Uncertainty Boundary:** No runtime factors mitigate this; there is no middleware, reverse proxy, or Spring Security filter chain in scope.

### Remediation
Add a Spring Security configuration that protects `/admin/**` behind an admin role, and return only usernames (not hashes) if the endpoint is needed at all:

```java
// pom.xml — replace spring-security-crypto with the full starter
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

// SecurityConfig.java
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().permitAll())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}

// main.java — return only usernames, never hashes
@GetMapping("/admin/usernames")
public Set<String> getAllUsernames() {
    return userDatabase.keySet();
}
```

**Counterfactual:** If `/admin/usernames` required a valid `ADMIN`-role session, the endpoint would no longer be reachable by unauthenticated attackers. Stopping the `return userDatabase` dump (which exposes hashes) independently closes the credential-exposure path even without full auth.

## Finding 2: Weak Password Hashing — Unsalted MD5

**Finding ID:** `APPSEC-a84f2a4f62ce`
**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 38–46
**CWE:** CWE-916 — Use of Password Hash With Insufficient Computational Effort
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
private String hashPassword(String password) {
    try {
        MessageDigest md = MessageDigest.getInstance("MD5");
        md.update(password.getBytes());
        byte[] digest = md.digest();
        return DatatypeConverter.printHexBinary(digest).toUpperCase();
    } catch (NoSuchAlgorithmException e) {
        return "Error: Hashing algorithm not found";
    }
}
```

### Description
Passwords are hashed with raw MD5 — a general-purpose fast hash with no salt and no work factor. MD5 produces a 128-bit hash that a modern GPU can compute at billions of iterations per second, making dictionary attacks and rainbow-table lookups trivial. There is no per-user salt, so identical passwords produce identical hashes, enabling both rainbow tables and bulk cracking of the entire user database with one pass. Notably, `spring-security-crypto` — which provides `BCryptPasswordEncoder` — is already declared in `pom.xml` but not used.

### Prioritization
P1, second only to Finding 1 (the exposed hash dump). Once an attacker has the hashes via the admin endpoint, MD5 ensures they can recover plaintext passwords within minutes. Even if Finding 1 is fixed, an attacker with database read access (e.g., via future SQLi or backup leak) would have the same leverage.

### Exploitability Notes
- **Exploit Preconditions:** Access to the hashed passwords (trivially obtained via Finding 1, or through any future persistence-layer exposure).
- **Concrete attacker input:** `hashcat -m 0 hashes.txt rockyou.txt` — MD5 cracks at ~10 billion H/s on a consumer GPU; the entire `rockyou.txt` wordlist runs in under a second.
- **Uncertainty Boundary:** None. MD5's weakness is unconditional.

### Remediation
Use `BCryptPasswordEncoder` from the already-imported `spring-security-crypto` dependency:

```java
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

private final BCryptPasswordEncoder passwordEncoder = new BCryptPasswordEncoder(12);

@PostMapping("/register")
public String registerUser(@RequestParam String username, @RequestParam String password) {
    String hashedPassword = passwordEncoder.encode(password);
    userDatabase.put(username, hashedPassword);
    return "User registered successfully";
}

@PostMapping("/login")
public String loginUser(@RequestParam String username, @RequestParam String password) {
    String storedHash = userDatabase.get(username);
    if (storedHash != null && passwordEncoder.matches(password, storedHash)) {
        return "Login successful";
    }
    return "Invalid username or password";
}
// Remove hashPassword() entirely
```

`BCryptPasswordEncoder.encode()` auto-generates a per-password salt and applies a cost factor (12 = ~250ms per check), making rainbow tables and bulk GPU cracking infeasible.

**Counterfactual:** Replacing `MessageDigest.getInstance("MD5")` with a call to `BCryptPasswordEncoder.encode()` makes this finding invalid.

## Finding 3: Missing CSRF Protection on State-Changing Endpoints

**Finding ID:** `APPSEC-7466c46ef721`
**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 21–25, 28–35
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** MEDIUM

### Vulnerable Code
```java
@PostMapping("/register")
public String registerUser(@RequestParam String username, @RequestParam String password) { ... }

@PostMapping("/login")
public String loginUser(@RequestParam String username, @RequestParam String password) { ... }
```

### Description
Neither `POST /register` nor `POST /login` validates a CSRF token. Spring Boot does not auto-configure CSRF protection unless `spring-boot-starter-security` is on the classpath (only `spring-security-crypto` is present here). A malicious page can therefore submit cross-origin form posts to `/register` or `/login` on behalf of a visiting user. The most impactful path is **login CSRF**: an attacker forces a victim to log in as the attacker's account, then waits for the victim to enter sensitive data (e.g., billing info, notes) — which the attacker can later read. `/register` CSRF can create fake accounts to exhaust usernames.

### Prioritization
P2. Lower immediate impact than Findings 1–2 because the application currently has no session management (so riding a pre-authenticated session is not yet possible), but this will become HIGH once session cookies are introduced.

### Exploitability Notes
- **Exploit Preconditions:** Victim visits an attacker-controlled page while using a browser that sends cookies to the target origin (applicable once session management is added). Currently exploitable for login CSRF even without sessions.
- **Concrete attacker input:** `<form action="https://target:8081/login" method="POST"><input name="username" value="attacker"><input name="password" value="known"></form><script>document.forms[0].submit()</script>`
- **Uncertainty Boundary:** Impact is limited until the application introduces session cookies; at that point, confidence becomes HIGH.

### Remediation
Add `spring-boot-starter-security` and configure CSRF protection (enabled by default in Spring Security):

```java
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
        .csrf(csrf -> csrf
            .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse()))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/admin/**").hasRole("ADMIN")
            .anyRequest().permitAll());
    return http.build();
}
```

For REST API clients, consider using the `X-CSRF-Token` header pattern or Signed Double Submit Cookie.

- https://owasp.org/www-project-cheat-sheets/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html
- https://cwe.mitre.org/data/definitions/352.html

## Finding 4: Timing Attack on Password Hash Comparison

**Finding ID:** `APPSEC-06379a4ca503`
**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 31
**CWE:** CWE-208 — Observable Timing Discrepancy
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```java
if (hashedPassword != null && hashedPassword.equals(hashPassword(password))) {
```

### Description
`String.equals()` is not constant-time — it returns `false` on the first byte mismatch, leaking how many leading bytes of the hash matched via response latency. An attacker making thousands of login attempts can statistically recover the hash byte-by-byte. While network jitter reduces practical exploitability compared to local comparisons, repeated measurements over a reliable connection make this feasible. The risk is compounded by the use of MD5 (Finding 2): even if an attacker cannot recover the hash via timing alone, these two weaknesses combine destructively.

### Prioritization
P3. Lowest-priority standalone finding; in practice, an attacker who can crack MD5 has no need for timing side-channels. Remediate after Findings 1–3, but include the fix as part of the password-hashing rewrite (BCrypt's `matches()` uses constant-time comparison internally).

### Exploitability Notes
- **Exploit Preconditions:** Ability to send many login requests and measure response time with millisecond precision; stable low-latency network path to the target.
- **Uncertainty Boundary:** Network jitter in cloud-hosted environments significantly reduces practical exploitability. This becomes a non-issue once `BCryptPasswordEncoder.matches()` is adopted (see Finding 2 remediation), which uses `MessageDigest.isEqual()` internally.

### Remediation
The `BCryptPasswordEncoder.matches()` fix from Finding 2 resolves this automatically. If keeping a hex-comparison path for any reason, use `MessageDigest.isEqual()`:

```java
// Constant-time comparison of two byte arrays
boolean safe = MessageDigest.isEqual(
    expectedHash.getBytes(StandardCharsets.UTF_8),
    computedHash.getBytes(StandardCharsets.UTF_8)
);
```

## Finding 5: Non-Thread-Safe Shared State (`HashMap`)

**Finding ID:** `APPSEC-e5f90a4c01bd`
**File:** `src/main/java/com/example/demo/main.java`
**Lines:** 15
**CWE:** CWE-362 — Concurrent Execution Using Shared Resource with Improper Synchronization
**OWASP Category:** A04:2021 – Insecure Design
**Priority:** P3
**Severity:** LOW
**Confidence:** MEDIUM

### Vulnerable Code
```java
private Map<String, String> userDatabase = new HashMap<>();
```

### Description
`HashMap` is not thread-safe. Spring Boot handles HTTP requests on a shared thread pool, so concurrent `POST /register` writes and `GET /admin/usernames` reads (which iterate the map) on different threads can cause a `ConcurrentModificationException`, silent data loss (two threads inserting simultaneously), or infinite loops in the resize path. An attacker who can trigger concurrent registrations can potentially exploit this to cause a denial-of-service via an uncaught exception or corrupt the registration state.

### Prioritization
P3. Lowest-severity finding; primarily a reliability/availability risk under load rather than a confidentiality or integrity risk. Remediate as part of replacing the in-memory store with a real database.

### Exploitability Notes
- **Exploit Preconditions:** Concurrent requests — requires two or more simultaneous callers. Easily triggered by tooling (e.g., `ab -c 10`).
- **Uncertainty Boundary:** Spring Boot's default `tomcat` thread pool makes this reachable, but actual impact depends on JVM internals and timing.

### Remediation
Replace `HashMap` with `ConcurrentHashMap` as a minimal fix, or use a persistent database:

```java
// Minimal fix
private Map<String, String> userDatabase = new ConcurrentHashMap<>();

// Proper fix: replace in-memory store with a database (JPA/JDBC)
// and use BCryptPasswordEncoder as described in Finding 2
```
