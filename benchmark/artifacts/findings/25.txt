## Finding 1: NoSQL Operator Injection — Authentication Bypass

**Finding ID:** `APPSEC-63ac1d2f6adb`
**File:** `main.go`
**Lines:** 33–43
**CWE:** CWE-943 — Improper Neutralization of Special Elements in Data Query Logic
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```go
var creds map[string]interface{}
if json.NewDecoder(r.Body).Decode(&creds) != nil {
    http.Error(w, "Invalid request", http.StatusBadRequest)
    return
}

users := client.Database("testdb").Collection("users")
if users.FindOne(context.TODO(), creds).Err() != nil {
    http.Error(w, "Invalid credentials", http.StatusUnauthorized)
    return
}
```

### Description
The request body is decoded into `map[string]interface{}` — a fully untyped map that preserves JSON objects as nested maps — and then passed verbatim as a MongoDB BSON filter to `FindOne`. MongoDB's BSON driver interprets top-level keys beginning with `$` as query operators. Because the user controls both the keys and the value types in the decoded map, an attacker can inject operators such as `$gt`, `$ne`, `$regex`, or `$where` to manipulate the query semantics. The data flow is: HTTP body → `json.Decode(map[string]interface{})` → `FindOne(filter)` with zero sanitization at any step. This completely bypasses authentication.

### Prioritization
This is the highest-priority finding. It is a one-shot, no-preconditions authentication bypass: any unauthenticated attacker with HTTP access to port 8081 can log in as any user. No credentials, prior account, or elevated access are required.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the `/login` endpoint (port 8081). No account or prior knowledge of credentials required.
- **Attacker-controlled input shape:** `POST /login` with body `{"username":"admin","password":{"$gt":""}}` — the `$gt:""` operator matches any non-empty string, so the password check is satisfied for the `admin` account regardless of the stored value. Alternatively `{"username":{"$gt":""},"password":{"$gt":""}}` returns the first document in the collection.
- **Uncertainty Boundary:** None — the vulnerability and its impact are fully visible in code. The MongoDB driver passes the decoded map as a raw BSON document, and operator keys are processed unconditionally.

### Remediation
Decode into the typed `User` struct rather than an untyped map. The BSON driver will only serialize the declared string fields, making operator injection structurally impossible:

```go
// Before — untyped decode, full operator injection surface
var creds map[string]interface{}
json.NewDecoder(r.Body).Decode(&creds)
users.FindOne(context.TODO(), creds)

// After — decode into typed struct, then build a safe explicit filter
var creds User
if err := json.NewDecoder(r.Body).Decode(&creds); err != nil {
    http.Error(w, "Invalid request", http.StatusBadRequest)
    return
}
if creds.Username == "" || creds.Password == "" {
    http.Error(w, "Invalid request", http.StatusBadRequest)
    return
}
filter := bson.M{"username": creds.Username}
var stored User
if err := users.FindOne(context.TODO(), filter).Decode(&stored); err != nil {
    http.Error(w, "Invalid credentials", http.StatusUnauthorized)
    return
}
// Compare password using constant-time comparison (see Finding 2)
if !checkPassword(creds.Password, stored.Password) {
    http.Error(w, "Invalid credentials", http.StatusUnauthorized)
    return
}
```

**Counterfactual invalidation:** if `creds` were decoded into `User` (typed struct with `string` fields), operator keys injected by the client would be rejected by `json.Decode` or silently ignored, and the BSON filter could only ever contain string values — making this finding invalid.

### References
- [OWASP Testing Guide: Testing for NoSQL Injection](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/05.6-Testing_for_NoSQL_Injection)
- [CWE-943: Improper Neutralization of Special Elements in Data Query Logic](https://cwe.mitre.org/data/definitions/943.html)

## Finding 2: Plaintext Password Storage

**Finding ID:** `APPSEC-fa4a2916ee04`
**File:** `main.go`
**Lines:** 26–29, 40
**CWE:** CWE-256 — Plaintext Storage of a Password
**OWASP Category:** A02:2021 – Cryptographic Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
users.InsertMany(context.TODO(), []interface{}{
    bson.M{"username": "admin", "password": "password"},
    bson.M{"username": "user", "password": "123456"},
})
```
```go
if users.FindOne(context.TODO(), creds).Err() != nil {
```

### Description
Passwords are stored as plain UTF-8 strings in MongoDB and authenticated by including the plaintext password directly in the query filter — there is no hashing, salting, or key derivation at any point. Any database read access (backup, snapshot, log, or the unauthenticated MongoDB port — see Finding 4) exposes all credentials immediately with no offline cracking required. The authentication model itself structurally requires the stored value to equal the submitted value, which precludes retrofitting hashing without changing the login logic.

### Prioritization
P1, second only to the injection bypass. If an attacker cannot exploit Finding 1, they can read credentials directly via the exposed MongoDB port (Finding 4), and the plaintext storage makes the value immediately usable.

### Exploitability Notes
- **Exploit Preconditions:** Read access to the MongoDB database (directly exploitable via Finding 4; also reachable via backup/log exposure).
- **Uncertainty Boundary:** None visible in code.

### Remediation
Store a password hash (Argon2id or bcrypt ≥ cost 12) and verify at login time using constant-time comparison. The login flow must fetch by username only, then verify the hash out-of-band:

```go
import "golang.org/x/crypto/bcrypt"

// Storing a new user
hash, err := bcrypt.GenerateFromPassword([]byte(plainPassword), 12)
if err != nil { ... }
bson.M{"username": username, "password": string(hash)}

// Login verification — fetch by username, then verify hash
filter := bson.M{"username": creds.Username}
var stored User
if err := users.FindOne(ctx, filter).Decode(&stored); err != nil {
    http.Error(w, "Invalid credentials", http.StatusUnauthorized)
    return
}
if err := bcrypt.CompareHashAndPassword([]byte(stored.Password), []byte(creds.Password)); err != nil {
    http.Error(w, "Invalid credentials", http.StatusUnauthorized)
    return
}
```

### References
- [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- [CWE-256: Plaintext Storage of a Password](https://cwe.mitre.org/data/definitions/256.html)

## Finding 3: Hardcoded Credentials in Source Code

**Finding ID:** `APPSEC-4807d8bd667a`
**File:** `main.go`
**Lines:** 26–29
**CWE:** CWE-798 — Use of Hard-coded Credentials
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```go
users.InsertMany(context.TODO(), []interface{}{
    bson.M{"username": "admin", "password": "password"},
    bson.M{"username": "user", "password": "123456"},
})
```

### Description
Default credentials (`admin`/`password`, `user`/`123456`) are hardcoded in source and seeded into the database on startup. These are among the most common passwords in credential stuffing dictionaries. Any developer, contractor, or supply chain actor with repository access has the credentials. Even if the database is later populated with real users, the seeded accounts remain permanently present (the guard condition only skips insertion when the collection is non-empty, line 24 — but nothing removes these default accounts after real accounts are added).

### Prioritization
P2. Combined with the plaintext storage (Finding 2) and exposed MongoDB port (Finding 4), these credentials are exploitable through multiple paths. Remediation priority is behind the injection bypass (Finding 1) but equal to Finding 2 since both are required for a secure auth system.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the `/login` endpoint. No further knowledge needed — credentials are public.
- **Uncertainty Boundary:** If the comment "Assume this to be a fully grown database" implies seeded credentials are replaced by real data, the `admin` and `user` accounts still persist unless explicitly deleted.

### Remediation
Remove all hardcoded credentials from source code. For seeding test/demo environments, use environment variables or a secrets manager:

```go
// Remove the hardcoded InsertMany block entirely from production code.
// For test environments, inject via env:
adminPass := os.Getenv("SEED_ADMIN_PASSWORD")
if adminPass == "" {
    log.Fatal("SEED_ADMIN_PASSWORD not set")
}
hash, _ := bcrypt.GenerateFromPassword([]byte(adminPass), 12)
users.InsertOne(ctx, bson.M{"username": "admin", "password": string(hash)})
```

- [CWE-798: Use of Hard-coded Credentials](https://cwe.mitre.org/data/definitions/798.html)
- [OWASP Testing Guide: Testing for Default Credentials](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/02-Testing_for_Default_Credentials)

## Finding 4: MongoDB Exposed to Host Network Without Authentication

**Finding ID:** `APPSEC-279d438a5bc6`
**File:** `docker-compose.yml`
**Lines:** 16
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P2
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```yaml
mongo:
  image: mongo:5.0
  container_name: mongodb
  ports:
    - "27017:27017"
```

### Description
Port 27017 is published from the MongoDB container to the Docker host, making the database directly reachable from the host network (and potentially the public internet if the host has a public IP). MongoDB 5.0 ships with authentication disabled by default when no admin user exists, which is the case here — the application connection string `mongodb://mongo:27017` contains no credentials, and no `MONGO_INITDB_ROOT_USERNAME`/`MONGO_INITDB_ROOT_PASSWORD` is configured. An attacker with network access can connect directly using any MongoDB client, enumerate collections, read all user records (including plaintext passwords per Finding 2), and write or delete arbitrary data — with no credentials required.

### Prioritization
P2. This is independently exploitable without using the HTTP API at all, and directly enables credential harvesting from the plaintext password store.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 27017 on the Docker host. `mongosh mongodb://<host>:27017` requires no credentials with the current configuration.
- **Attacker-controlled input shape:** `mongosh "mongodb://<host>:27017" --eval "db.getSiblingDB('testdb').users.find()"` returns all user documents including plaintext passwords.
- **Uncertainty Boundary:** Impact is reduced if host firewall rules block 27017 externally. However, the docker-compose config as written provides no such protection itself.

### Remediation
Remove the host port binding so MongoDB is only reachable within the Docker network. Enable authentication:

```yaml
# docker-compose.yml
mongo:
  image: mongo:5.0
  container_name: mongodb
  # Remove the "ports:" block — no host binding needed; app reaches via Docker DNS
  environment:
    MONGO_INITDB_ROOT_USERNAME: "${MONGO_ROOT_USER}"
    MONGO_INITDB_ROOT_PASSWORD: "${MONGO_ROOT_PASSWORD}"
  volumes:
    - mongo_data:/data/db
```

Update the app connection string to include credentials (via environment variable, not hardcoded):

```go
// main.go
uri := os.Getenv("MONGO_URI") // e.g. mongodb://user:pass@mongo:27017
client, err = mongo.Connect(ctx, options.Client().ApplyURI(uri))
```

### References
- [MongoDB Security Checklist](https://www.mongodb.com/docs/manual/administration/security-checklist/)
- [CWE-306: Missing Authentication for Critical Function](https://cwe.mitre.org/data/definitions/306.html)

## Finding 5: No Rate Limiting on Authentication Endpoint

**Finding ID:** `APPSEC-5db0d01d7c13`
**File:** `main.go`
**Lines:** 32–45
**CWE:** CWE-307 — Improper Restriction of Excessive Authentication Attempts
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P3
**Severity:** LOW
**Confidence:** HIGH

### Vulnerable Code
```go
func login(w http.ResponseWriter, r *http.Request) {
    // No rate limiting, no account lockout, no delay
    var creds map[string]interface{}
    ...
    w.Write([]byte("Login successful"))
}
```

### Description
The `/login` endpoint imposes no request rate limit, delay, lockout policy, or exponential backoff. An attacker can submit unlimited credential guesses at network speed. While the NoSQL injection (Finding 1) already makes brute force unnecessary for this application, fixing Findings 1–3 without adding rate limiting would still leave the endpoint fully open to online password guessing attacks and credential stuffing.

### Prioritization
P3 — only relevant after Findings 1–4 are remediated. On its own the impact is low given that Findings 1 and 4 offer faster paths to compromise.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 8081 and a target username.
- **Uncertainty Boundary:** Infrastructure-level rate limiting (e.g., reverse proxy, WAF) may exist outside this scope.

### Remediation
Add per-IP and per-account rate limiting using a middleware. A minimal Go approach using `golang.org/x/time/rate` or a package like `github.com/ulule/limiter`:

```go
// Use a per-IP token bucket — e.g., 5 attempts per minute
limiter := rate.NewLimiter(rate.Every(time.Minute/5), 5)

func login(w http.ResponseWriter, r *http.Request) {
    if !limiter.Allow() {
        http.Error(w, "Too many requests", http.StatusTooManyRequests)
        return
    }
    // ... existing logic
}
```

### References
- [CWE-307: Improper Restriction of Excessive Authentication Attempts](https://cwe.mitre.org/data/definitions/307.html)
- [OWASP Authentication Cheat Sheet — Account Lockout](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#account-lockout)
