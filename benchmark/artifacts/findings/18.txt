## Finding 1: Insecure Deserialization / Authentication Bypass

**Finding ID:** `APPSEC-a3f29b1c7e4d`
**File:** `main.php`
**Lines:** 26–31
**CWE:** CWE-502 — Deserialization of Untrusted Data / CWE-287 — Improper Authentication
**OWASP Category:** A08:2021 – Software and Data Integrity Failures; A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```php
$data = $_POST['data'];
$user = @unserialize($data);
if ($user === false && $data !== 'b:0;') {
    echo "Failed to unserialize user. ";
} else {
    $_SESSION['user'] = $user;
}
```

### Description
`$_POST['data']` is attacker-controlled and fed directly into `unserialize()` with no validation or HMAC integrity check. PHP's deserializer will reconstruct any class available in scope, invoking `__wakeup()` and `__destruct()` magic methods on the constructed object. In this application, the reconstructed object is placed verbatim into `$_SESSION['user']`, then immediately evaluated by `isAdmin()` which trusts `->role === 'admin'`. An attacker submits `O:4:"User":2:{s:8:"username";s:5:"pwned";s:4:"role";s:5:"admin";}` and is granted admin access in the same HTTP request — requiring no credentials whatsoever. If the application or any included library autoloads classes with dangerous magic methods, this also enables full PHP Object Injection (potential RCE via gadget chain).

### Prioritization
Top priority — zero preconditions, trivially exploitable with a single POST, grants full admin access. All other findings are secondary.

### Exploitability Notes
- **Exploit Preconditions:** None. Any unauthenticated client can POST to this endpoint.
- **Uncertainty Boundary:** Full RCE via gadget chain depends on what other classes are autoloaded at runtime. The auth bypass is fully confirmed from code alone.

### Remediation
Replace `unserialize()` with JSON deserialization and explicit field extraction. Never reconstruct objects from untrusted bytes.

```php
// After
if (isset($_POST['submit'])) {
    $json = $_POST['data'];
    $decoded = json_decode($json, true);
    if (
        is_array($decoded)
        && isset($decoded['username'], $decoded['role'])
        && is_string($decoded['username'])
        && in_array($decoded['role'], ['user', 'admin'], true)
    ) {
        // In a real app, validate credentials server-side before trusting 'role'
        $_SESSION['user'] = new User(
            htmlspecialchars($decoded['username'], ENT_QUOTES, 'UTF-8'),
            $decoded['role']
        );
    } else {
        echo "Invalid user data.";
    }
}
```

The deeper architectural fix is that `role` must never be caller-supplied at all — it must be assigned by the server after verifying credentials against a database.

- https://owasp.org/www-community/vulnerabilities/PHP_Object_Injection
- https://cwe.mitre.org/data/definitions/502.html

## Finding 2: Reflected/Session-Stored XSS via Unencoded Username Output

**Finding ID:** `APPSEC-b7d42e8f1c3a`
**File:** `main.php`
**Lines:** 26–27 (source), 40 (sink)
**CWE:** CWE-79 — Improper Neutralization of Input During Web Page Generation (XSS)
**OWASP Category:** A03:2021 – Injection
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```php
// Source (line 26-27): attacker controls username via serialized POST
$user = @unserialize($data);          // username can be "<script>alert(1)</script>"
...
// Sink (line 40): username echoed via __toString() without HTML encoding
echo 'Hello ' . $_SESSION['user'];    // __toString() returns "User: <script>…"
```

### Description
`User::__toString()` interpolates `$this->username` and `$this->role` directly into a string that is `echo`'d into the HTML response without `htmlspecialchars()`. Because `username` is attacker-controlled via the serialized POST body (Finding 1), an attacker who submits `O:4:"User":2:{s:8:"username";s:27:"<script>alert(1)</script>";s:4:"role";s:4:"user";}` will have the script tag rendered in the browser. Without CSRF protection (Finding 3), an attacker can trigger this against a victim's session cross-origin, executing JavaScript in the victim's browser.

### Prioritization
P1 alongside Finding 1, as it is directly reachable via the same deserialization path and escalates to cross-user XSS when chained with Finding 3 (missing CSRF).

### Exploitability Notes
- **Exploit Preconditions:** Attacker submits a serialized `User` with an XSS payload as `username`. Without CSRF protection, can be delivered cross-origin to victim users.
- **Uncertainty Boundary:** Impact is self-XSS in isolation; cross-user only when combined with CSRF attack vector.

### Remediation
Encode output at the point of rendering, and sanitize `username` at ingestion:

```php
// In User::__toString() — fix the output sink
public function __toString() {
    return "User: " . htmlspecialchars($this->username, ENT_QUOTES, 'UTF-8')
         . ", Role: " . htmlspecialchars($this->role, ENT_QUOTES, 'UTF-8');
}
```

Also apply `htmlspecialchars()` when constructing the `User` object from input, as shown in Finding 1's remediation.

### References
- https://owasp.org/www-community/attacks/xss/
- https://cwe.mitre.org/data/definitions/79.html

## Finding 3: Missing CSRF Protection on Session-Modifying Endpoint

**Finding ID:** `APPSEC-c1e87a3f2b9d`
**File:** `main.php`
**Lines:** 25–33, 50–53
**CWE:** CWE-352 — Cross-Site Request Forgery
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```php
// No CSRF token generated or validated before processing
if (isset($_POST['submit'])) {
    $data = $_POST['data'];
    $user = @unserialize($data);
    ...
    $_SESSION['user'] = $user;
}
...
<form method="post">
    <input type="text" name="data" placeholder="Serialized data">
    <button type="submit" name="submit">Submit</button>
</form>
```

### Description
The POST handler modifies `$_SESSION['user']` — a state-changing operation — without verifying a synchronizer token or checking `Origin`/`Referer` headers. Any page the victim visits can silently auto-submit this form via JavaScript (`form.submit()`), causing the victim's session to be overwritten with an attacker-chosen serialized object. This amplifies Finding 2: CSRF delivers the XSS payload into the victim's session, executing attacker JavaScript in the victim's browser without any user interaction beyond page load.

### Prioritization
P2 — lower priority than Findings 1 and 2, but directly enables cross-user exploitation of the XSS.

### Exploitability Notes
- **Exploit Preconditions:** Victim must be logged in and visit an attacker-controlled page. Same-site cookie policies (Lax/Strict) on modern browsers may limit exploitability if session cookie is `SameSite=Lax`. If cookie has no `SameSite` attribute (default), exploit is straightforward.
- **Uncertainty Boundary:** Browser `SameSite` default behavior varies by version; PHP `session.cookie_samesite` setting not visible in scope.

### Remediation
Add a synchronizer CSRF token to all state-changing forms:

```php
// Session start already exists — add token generation on page load
if (empty($_SESSION['csrf_token'])) {
    $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
}

// Validate on POST
if (isset($_POST['submit'])) {
    if (
        empty($_POST['csrf_token'])
        || !hash_equals($_SESSION['csrf_token'], $_POST['csrf_token'])
    ) {
        http_response_code(403);
        exit("CSRF validation failed.");
    }
    // ... rest of handler
}
```

```html
<form method="post">
    <input type="hidden" name="csrf_token"
           value="<?= htmlspecialchars($_SESSION['csrf_token'], ENT_QUOTES, 'UTF-8') ?>">
    <input type="text" name="data" placeholder="Serialized data">
    <button type="submit" name="submit">Submit</button>
</form>
```

Also set the session cookie with `SameSite=Strict` in `php.ini` or `session_set_cookie_params()`.

### References
- https://owasp.org/www-community/attacks/csrf
- https://cwe.mitre.org/data/definitions/352.html

## Finding 4: Error Suppression Hides Deserialization Failures

**Finding ID:** `APPSEC-d9c41f6a0b82`
**File:** `main.php`
**Lines:** 27
**CWE:** CWE-390 — Detection of Error Condition Without Action
**OWASP Category:** A05:2021 – Security Misconfiguration
**Priority:** P3
**Severity:** INFO
**Confidence:** HIGH

### Vulnerable Code
```php
$user = @unserialize($data);
```

### Description
The `@` error-suppression operator silences all PHP warnings and notices from `unserialize()`. In a security context this means deserialization errors, malformed gadget chains, and class-not-found notices are swallowed, making intrusion detection and logging impossible. An attacker probing gadget chains generates no logged artifacts.

### Prioritization
Lowest priority — INFO-level, no direct exploit impact. Address after Findings 1–3.

### Exploitability Notes
- **Exploit Preconditions:** Attacker is already exploiting the deserialization (Finding 1); this only affects detectability.
- **Uncertainty Boundary:** Impact depends entirely on whether application logs are monitored.

### Remediation
Remove `@` and use proper error handling. After replacing `unserialize` with JSON (Finding 1 remediation), this issue disappears entirely.

```php
// Remove the @ operator; let errors surface to configured error handlers
$user = unserialize($data);  // Moot after adopting JSON — remove unserialize entirely
```

### References
- https://www.php.net/manual/en/language.operators.errorcontrol.php
