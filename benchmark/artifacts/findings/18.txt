## Security Review — `main.php`

**Pass 1 — Triage:**
Single PHP file, no framework. Entry point: `$_POST['data']` (fully attacker-controlled). Sensitive operations: `unserialize()`, `$_SESSION`, `isAdmin()` role check, `echo` of user-derived data. No third-party libraries. The entire authentication mechanism is built on trusting deserialized session data.

## Finding 1: PHP Object Injection via Insecure Deserialization

**File:** `main.php`
**Lines:** 26–27
**CWE:** CWE-502 — Deserialization of Untrusted Data
**OWASP Category:** A08:2021 – Software and Data Integrity Failures
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```php
$data = $_POST['data'];
$user = @unserialize($data);
```

### Description
`unserialize()` is called directly on `$_POST['data']`, which is fully attacker-controlled with no validation, allowlist, or HMAC signature. PHP's deserializer instantiates objects of any class currently in scope and invokes magic methods (`__wakeup`, `__destruct`, `__toString`) automatically during the process. With only the `User` class in scope here, an attacker can trivially instantiate a `User` object with `role = 'admin'` and write it into the session, bypassing all authorization. In deployments with additional classes loaded (autoloaders, framework code, Composer dependencies), full PHP Object Injection gadget chains enabling RCE or arbitrary file write become possible.

### Prioritization
Highest priority. Exploitation requires a single unauthenticated HTTP POST request with no preconditions. Admin impersonation is immediately achievable; RCE is likely in real deployments. No other finding compares in impact or ease of exploitation.

### Exploitability Notes
- **Exploit Preconditions:** None. Attacker needs only network access to the POST endpoint. No existing session, no credentials required.
- **Uncertainty Boundary:** Gadget chain availability for RCE depends on what other classes are in scope at runtime (autoloaders, framework libraries). Admin bypass is unconditional given the current code.

**Proof-of-concept payload (admin bypass):**
```
POST /main.php HTTP/1.1
Content-Type: application/x-www-form-urlencoded

submit=1&data=O:4:"User":2:{s:8:"username";s:5:"admin";s:4:"role";s:5:"admin";}
```
This sets `$_SESSION['user']` to a `User` object with `role = 'admin'`, causing `isAdmin()` to return `true` on the next request.

**Counterfactual invalidation:** If `unserialize()` were replaced with `json_decode()` and a manual object constructor, the deserialization vector would be eliminated.

### Remediation
Never deserialize attacker-controlled data. Replace the entire serialization-based session mechanism with server-side credential lookup:

```php
// Remove unserialize entirely. Use a real authentication flow:
if (isset($_POST['submit'])) {
    $username = $_POST['username'] ?? '';
    $password = $_POST['password'] ?? '';

    // Look up user from DB with parameterized query
    $stmt = $pdo->prepare("SELECT username, role, password_hash FROM users WHERE username = ?");
    $stmt->execute([$username]);
    $row = $stmt->fetch();

    if ($row && password_verify($password, $row['password_hash'])) {
        session_regenerate_id(true);
        $_SESSION['user'] = ['username' => $row['username'], 'role' => $row['role']];
    }
}
```

If serialization is genuinely required for another reason, use HMAC signing to prevent tampering:
```php
// Sign before storing, verify before trusting
$token = base64_encode(serialize($user_data));
$sig = hash_hmac('sha256', $token, SECRET_KEY);
// On receive: verify sig before calling unserialize
if (!hash_equals($expected_sig, $actual_sig)) { die("Tampered"); }
```

## Finding 2: Broken Authentication — No Credential Verification

**File:** `main.php`
**Lines:** 18–23, 25–33
**CWE:** CWE-287 — Improper Authentication
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```php
function isAdmin() {
    if (isset($_SESSION['user']) && $_SESSION['user'] instanceof User) {
        return $_SESSION['user']->role === 'admin';
    }
    return false;
}

if (isset($_POST['submit'])) {
    $data = $_POST['data'];
    $user = @unserialize($data);
    ...
    $_SESSION['user'] = $user;
}
```

### Description
The application has no credential verification of any kind. "Authentication" consists entirely of accepting a serialized blob from the client and trusting whatever role it contains. There is no password check, no secret, no token validation, and no server-side identity store. Even if the deserialization vulnerability were fixed (e.g., using a signed token), the current design places the role assignment entirely under client control. Any user can self-assign `role = 'admin'` by any means that sets the session.

### Prioritization
P1 alongside Finding 1, but causally downstream — the design flaw that makes Finding 1 so damaging. Fixing only the deserialization sink without replacing the authentication model still leaves a broken auth design.

### Exploitability Notes
- **Exploit Preconditions:** None. The form accepts any serialized data with no server-side secret or identity check.
- **Uncertainty Boundary:** None — the code is deterministic. There is no hidden credential check in this file.

**Counterfactual invalidation:** Adding a server-side user store and verifying credentials before setting the session would eliminate this finding.

### Remediation
Implement real authentication: verify credentials against a server-side store. Store only minimal, server-authoritative data in the session (e.g., a user ID), then re-fetch the role from the database per request rather than trusting what is in the session object.

```php
// isAdmin using DB-authoritative role, not session-stored role
function isAdmin(PDO $pdo): bool {
    if (!isset($_SESSION['user_id'])) return false;
    $stmt = $pdo->prepare("SELECT role FROM users WHERE id = ?");
    $stmt->execute([$_SESSION['user_id']]);
    $row = $stmt->fetch();
    return $row && $row['role'] === 'admin';
}
```

## Finding 3: Cross-Site Scripting (XSS) via Missing Output Encoding

**File:** `main.php`
**Lines:** 13–15, 40
**CWE:** CWE-79 — Improper Neutralization of Input During Web Page Generation
**OWASP Category:** A03:2021 – Injection
**Priority:** P2
**Severity:** MEDIUM
**Confidence:** HIGH

### Vulnerable Code
```php
// __toString — no HTML encoding
public function __toString() {
    return "User: $this->username, Role: $this->role";
}

// Echoed directly into HTML
echo 'Hello ' . $_SESSION['user'];
```

### Description
`$_SESSION['user']->username` and `->role` are deserialized from attacker input and echoed into the HTML response via `__toString()` without `htmlspecialchars()`. Any HTML/JavaScript injected into these fields is rendered in the browser. Combined with Finding 1, an attacker can inject an arbitrary XSS payload by submitting a crafted serialized object with a malicious `username`. This is session-stored XSS: the payload persists across requests for that session and fires every time the non-admin greeting branch is rendered.

**Proof-of-concept payload:**
```
O:4:"User":2:{s:8:"username";s:26:"<img src=x onerror=alert(1)>";s:4:"role";s:4:"user";}
```
This stores the XSS in the session and fires on every subsequent page load while the session persists.

### Prioritization
P2. Elevated by the session-persistence aspect, but in isolation this is self-XSS (attacker injects into their own session). Impact increases significantly if session fixation or another mechanism allows the attacker to plant this in a victim's session.

### Exploitability Notes
- **Exploit Preconditions:** Attacker must be able to set the session (trivially achieved via Finding 1). Victim impact currently requires session fixation (not demonstrated here).
- **Uncertainty Boundary:** PHP session fixation defenses depend on `session.use_strict_mode` and `session_regenerate_id()` usage; neither is present in this file, so cross-user exploitation cannot be ruled out.

**Counterfactual invalidation:** Wrapping all output in `htmlspecialchars()` eliminates the XSS sink.

### Remediation
Encode all user-derived values before outputting to HTML:

```php
public function __toString() {
    return "User: " . htmlspecialchars($this->username, ENT_QUOTES, 'UTF-8')
         . ", Role: " . htmlspecialchars($this->role, ENT_QUOTES, 'UTF-8');
}
```

Apply the same encoding at every other output site. The `ENT_QUOTES` flag covers both single and double quote contexts.

### References
- https://owasp.org/www-community/attacks/xss/
- https://cwe.mitre.org/data/definitions/79.html

```
### Key Risks
The dominant risk is PHP Object Injection: a single unauthenticated POST request with a
crafted serialized string grants admin access and, in any real deployment with Composer
dependencies or an autoloader, likely enables RCE via gadget chains. The underlying
authentication design is also fundamentally broken — there is no credential check at all,
so fixing the deserialization sink alone is insufficient. The XSS finding is currently
self-affecting but becomes cross-user if session fixation is possible.
```

### Prioritization Notes
Findings 1 and 2 are both P1 and must be fixed together — the deserialization is the immediate exploit vector, but the auth design flaw means any replacement mechanism must also introduce real server-side credential verification. Finding 3 (XSS) should be fixed in the same pass since all three findings share the same root cause: trusting attacker-controlled data without sanitization.
