## Finding 1: Path Traversal — Arbitrary File Read via `/files/download`

**Finding ID:** `APPSEC-1058423c6348`
**File:** `src/main/java/com/example/filemanagement/FileController.java`
**Lines:** 27–37
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** CRITICAL
**Confidence:** HIGH

### Vulnerable Code
```java
Path filePath = Paths.get(fileBasePath + filename);

if (!Files.exists(filePath)) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body(null);
}

Resource fileResource = new UrlResource(filePath.toUri());
return ResponseEntity.ok()
        .contentType(MediaType.APPLICATION_OCTET_STREAM)
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=\"" + fileResource.getFilename() + "\"")
        .body(fileResource);
```

### Description
The `filename` query parameter is directly concatenated with `fileBasePath` — `Paths.get("/var/www/uploads/" + filename)` — with no canonicalization or boundary check before the path is used to open a file. The JVM's `Files.exists()` and `UrlResource` both invoke OS-level syscalls that resolve `..` segments, so the declared base directory provides no containment. An unauthenticated attacker who sends `GET /files/download?filename=../../etc/passwd` causes the resolved path to be `/etc/passwd`, which is returned as a downloadable file. Files reachable include `/etc/passwd`, `/etc/shadow` (if the JVM runs as root), `/proc/self/environ` (leaks all environment variables and embedded secrets), application JARs, TLS private keys, and any other path accessible to the process.

### Prioritization
Top priority. This is an unauthenticated CRITICAL read of the entire server filesystem with a trivial single-parameter exploit. No preconditions beyond network access to the service.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the service on port 8081. No authentication required (see Finding 3). Any file readable by the JVM process is exposed.
- **Uncertainty Boundary:** Impact is bounded by the OS user the JVM runs as. In the Docker setup there is no explicit non-root user, so the container likely runs as root, exposing all files.

**Attacker input shape:** `GET /files/download?filename=../../etc/passwd`
`GET /files/download?filename=../../proc/self/environ` (environment variables / secrets)
`GET /files/download?filename=../../app/application.jar` (application bytecode)

**Counterfactual:** Adding `filePath = filePath.normalize(); if (!filePath.startsWith(Paths.get(fileBasePath).normalize())) { ... reject ... }` before the `Files.exists()` call makes this finding no longer valid.

### Remediation
```java
@GetMapping("/download")
public ResponseEntity<Resource> downloadFile(@RequestParam String filename) throws IOException {
    Path base = Paths.get(fileBasePath).normalize().toAbsolutePath();
    Path filePath = base.resolve(filename).normalize().toAbsolutePath();

    // Reject anything that escapes the base directory
    if (!filePath.startsWith(base)) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(null);
    }

    if (!Files.exists(filePath)) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(null);
    }

    Resource fileResource = new UrlResource(filePath.toUri());
    return ResponseEntity.ok()
            .contentType(MediaType.APPLICATION_OCTET_STREAM)
            .header(HttpHeaders.CONTENT_DISPOSITION,
                    "attachment; filename=\"" + filePath.getFileName() + "\"")
            .body(fileResource);
}
```
`normalize()` collapses `..` segments lexically, `toAbsolutePath()` anchors the check, and `startsWith(base)` enforces the containment boundary. Using `filePath.getFileName()` (not `fileResource.getFilename()`) ensures only the final path component appears in the response header.

## Finding 2: Path Traversal + Absolute Path Injection — `/files/metadata`

**Finding ID:** `APPSEC-d3858f9a1be8`
**File:** `src/main/java/com/example/filemanagement/FileController.java`
**Lines:** 42–54
**CWE:** CWE-22 — Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')
**OWASP Category:** A01:2021 – Broken Access Control
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
Path filePath = Paths.get(fileBasePath, filename);

if (!Files.exists(filePath)) {
    return ResponseEntity.status(HttpStatus.NOT_FOUND).body("File not found");
}

String metadata = String.format(
        "File: %s%nSize: %d bytes%nLast Modified: %s",
        filename,
        Files.size(filePath),
        Files.getLastModifiedTime(filePath)
);
```

### Description
`Paths.get(String first, String... more)` in Java resolves the `more` arguments against `first` — but if any element in `more` is an **absolute path** (begins with `/`), it silently **discards** all prior components and uses only the absolute path. An attacker can send `GET /files/metadata?filename=/etc/shadow` and `filePath` becomes `/etc/shadow` with no traversal sequences required. Additionally, relative traversal sequences like `../../etc/passwd` are also effective. The response echoes `filename` verbatim and leaks file size and last-modified timestamps for any path on the filesystem, enabling attacker reconnaissance of sensitive file existence and metadata.

### Prioritization
P1 alongside Finding 1 — the absolute-path-injection vector requires no `..` encoding and bypasses naive `..` filters. Slightly lower impact than Finding 1 (metadata only, not file contents), but trivially exploitable and directly serves as a reconnaissance primitive for targeted follow-up attacks.

### Exploitability Notes
- **Exploit Preconditions:** Network access to the service. No authentication required.
- **Uncertainty Boundary:** A `filename` filter checking only for `..` would not block the absolute-path variant; only a proper boundary check eliminates both vectors.

**Attacker input shapes:**
- `GET /files/metadata?filename=/etc/shadow` — absolute path bypass, leaks shadow file metadata
- `GET /files/metadata?filename=../../etc/passwd` — relative traversal, probes root filesystem

**Counterfactual:** Resolving `filename` against `base` with `base.resolve(filename).normalize().toAbsolutePath()` and checking `startsWith(base)` before reading would make this finding no longer valid, because an absolute-path argument passed to `base.resolve()` still remains absolute and would fail the `startsWith(base)` check.

### Remediation
```java
@GetMapping("/metadata")
public ResponseEntity<String> getFileMetadata(@RequestParam String filename) throws IOException {
    Path base = Paths.get(fileBasePath).normalize().toAbsolutePath();
    Path filePath = base.resolve(filename).normalize().toAbsolutePath();

    if (!filePath.startsWith(base)) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body("Invalid path");
    }

    if (!Files.exists(filePath)) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body("File not found");
    }

    String metadata = String.format(
            "File: %s%nSize: %d bytes%nLast Modified: %s",
            filePath.getFileName(),   // never reflect raw user input
            Files.size(filePath),
            Files.getLastModifiedTime(filePath)
    );
    return ResponseEntity.ok(metadata);
}
```
Note that `filename` is not reflected in the `"File: %s"` field — `filePath.getFileName()` is used instead, preventing any future reflected XSS or header-injection risk if this endpoint is extended.

### References
- https://cwe.mitre.org/data/definitions/22.html
- https://docs.oracle.com/en/java/docs/api/java.base/java/nio/file/Path.html#resolve(java.lang.String)

## Finding 3: Missing Authentication on File Endpoints

**Finding ID:** `APPSEC-7cb235dab7ca`
**File:** `src/main/java/com/example/filemanagement/FileController.java`
**Lines:** 25–55
**CWE:** CWE-306 — Missing Authentication for Critical Function
**OWASP Category:** A07:2021 – Identification and Authentication Failures
**Priority:** P1
**Severity:** HIGH
**Confidence:** HIGH

### Vulnerable Code
```java
@GetMapping("/download")
public ResponseEntity<Resource> downloadFile(@RequestParam String filename) throws IOException {
    // No authentication or authorization check
    ...
}

@GetMapping("/metadata")
public ResponseEntity<String> getFileMetadata(@RequestParam String filename) throws IOException {
    // No authentication or authorization check
    ...
}
```

### Description
Neither endpoint checks whether the caller is authenticated. There is no Spring Security configuration in the project (no `SecurityFilterChain`, no `@PreAuthorize`, no API key validation). Any network-reachable client — including unauthenticated internet users — can invoke these endpoints freely. While the path traversal vulnerabilities (Findings 1 and 2) are independently critical, the complete absence of authentication means no access barrier exists even for the intended functionality: an external attacker can enumerate and download any file the JVM user can read without needing to compromise a valid session or credential.

### Prioritization
Shares P1 priority with the path traversal findings because it is a required precondition that makes those exploits reachable to any attacker rather than only authenticated ones. Remediate authentication alongside, not after, the path traversal fixes.

### Exploitability Notes
- **Exploit Preconditions:** Network access to port 8081 only.
- **Uncertainty Boundary:** If a reverse proxy (not present in the provided scope) enforces authentication, the effective exposure would be reduced, but no such config is visible.

**Counterfactual:** Adding a Spring Security dependency with a `SecurityFilterChain` that requires authentication for `/files/**` would make this finding no longer valid.

### Remediation
Add Spring Security and require authentication for all `/files/**` routes:

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

```java
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/files/**").authenticated()
                .anyRequest().denyAll()
            )
            .httpBasic(Customizer.withDefaults()); // or JWT/OAuth2 as appropriate
        return http.build();
    }
}
```

Additionally, add object-level authorization so that an authenticated user can only access files they are permitted to view — authentication alone does not prevent one authenticated user from reading another's files.

### References
- https://cwe.mitre.org/data/definitions/306.html
- https://owasp.org/www-project-top-ten/2021/A07_2021-Identification_and_Authentication_Failures
